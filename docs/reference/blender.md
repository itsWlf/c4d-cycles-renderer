# Blender reference

The Blender behaviour this project depends on. Evidence labels:

- **[T]** tested here on Blender 5.0.0 and 5.2.3 LTS (Windows 11, RTX 4090, OpenGL back end) with the project's prototype scripts and bridge tests (`prototypes/`, `tests/bridge/`; both are kept locally and are not part of the repository). Both versions behaved the same unless a line says otherwise. Since 0.2.0 the bridge tests and the whole baseline ran on 5.0.0, 5.1.2, 5.2.3 LTS and 5.3.0 (F8); from then on the tests run on 5.2 and the other versions get the baseline before a major release (`docs/development.md`, "Which versions, when"). What differs between them is under "Version coupling".
- **[S]** read in the Blender 5.2.3 source, not run.
- **[I]** inferred from source; treat as a hypothesis.

Source paths below are relative to the root of the Blender 5.2.3 source tree (this project keeps a copy in `references/blender-v5.2.3_source/`, which is not part of the repository).

## Version coupling

The bridge reaches into Blender in places that are not public API, so it runs on listed Blender versions only. Supported since 0.2.0: **5.0, 5.1, 5.2 (the long-term support release, the default of the tests) and 5.3**, measured with 5.0.0, 5.1.2, 5.2.3 LTS and 5.3.0. The list stands in four places that change together: `SUPPORTED_BLENDER` (`bridge/c4d_bridge/__init__.py`), `SUPPORTED_VERSIONS` (`plugin/cyclesrender/source/session/blender_install.cpp`), `VERSIONS` (`tools/make_nodes.py`, which checks it against the plugin's list) and `blender_version_min` / `blender_version_max` (exclusive) in `bridge/blender_manifest.toml`. **Which Blender is used:** the one chosen in the Preferences; while none is chosen, detection takes, of the supported Blenders installed, the one whose own profile (or portable folder) holds the bridge, else 5.2, else the newest (`DetectBlender`; the preferred version is `PREFERRED_MAJOR`/`PREFERRED_MINOR` in `session/blender_install.cpp`: 5.2, the long-term support release, because 5.3 has open bugs, the maintainer's decision of 2026-11-16). Before adding a version, check each of these on it:

- **The offset of Cycles' status text** inside the engine struct ("Cycles status text" below). It is what the IPR's sample counter reads.
- **The wrapped methods of Cycles' Python class**: `view_draw` (viewport) and `render_frame_finish` (final frames), in `intern/cycles/blender/addon/__init__.py`.
- **Viewport readback**: the draw handlers and the framebuffer they read ("Reading viewport pixels").
- **The window set-up** the viewport driver performs ("Window and viewport setup"), including the operators it calls.
- **The shader nodes**: run `tools/make_nodes.py` and review the tables it holds by hand, as Blender does not tell Python which panel a socket is in.
- **Defaults of render properties**: compare `tools/make_settings.py` with a new scene.
- **The extensions folder** the plugin looks into for the bridge (`FindBridgeScript`): `<user folder>/<major>.<minor>/extensions/user_default/`.

All seven held on 5.0, 5.1, 5.2 and 5.3 (2026-11-16): the status text at offset 64, both wrapped methods, the readback and the window set-up (`tests/bridge/test_viewport.py`, `test_render.py`, the IPR tests of the baseline on each version), the shader nodes (below), the extensions folder (same layout; the manifest validates in 5.0 and 5.3).

**The material lighting nodes of 5.3** [T: a probe script and `tests/bridge/test_versions.py`; the 5.3 manual]: Light Accumulation, Light Evaluation, Light Info and Shadow Raycast are Eevee only. Light Accumulation sums, per light, its Diffuse, Glossy and Transmission inputs times their colours; the other three (and Attribute of type Light, Vector Transform in Light space) give values of the light being evaluated and work only inside the input tree of a Light Accumulation. Built from Python as the bridge builds any material, they render in Eevee (an orange light gives red : green : blue = 4 : 2 : 1 through Light Evaluation times Light Info; Shadow Raycast alone gives 1.0 where nothing is in the way), also with Position and Normal sent as (0, 0, 0): Blender then uses the shading point, as for an unwired input. The console names every node left out, and an input or setting only when it is wired or not at its default: a socket or setting a version added is at a default that does what the older version does (checked for the 5.1 Normal Map's `base`, Displaced, and `convention`, OpenGL, in the 5.1 manual), so naming every untouched Thin Wall of every Principled BSDF in 5.0 would only hide the lines that matter. The version is the one the bridge reports in `hello` for final frames, and for the IPR and thumbnails the one of the executable chosen in the Preferences (`GetBlenderInUse`, `prefs/settings.h`: stored with the path since 0.2.0, else asked with `--version` once per session and path).

## Launch

**IPR (windowed):**

```
blender --factory-startup --no-window-focus -p 0 0 W H --gpu-backend opengl --gpu-vsync off
        --python bridge/c4d_bridge/main.py -- <bridge args>
```

**Final frames (background):**

```
blender -b --factory-startup --offline-mode -Y --python-exit-code 1 --log-file <file>
        --python bridge/c4d_bridge/main.py -- <bridge args>
```

- `--factory-startup` skips user preferences, so the bridge sets everything it needs on each launch. [S]
- `-p sx sy w h`: lower-left origin, client size, minimum 640×480, clamped to the monitor work area. [S]
- `--no-window-focus` opens the window behind others without activating it. [S]
- `--gpu-vsync off` stops the window swap from throttling the loop. [I]
- The prototypes ran without `--gpu-backend`; the default back end on Windows was OpenGL. [T]
- Arguments after `--` belong to the script. [T]
- `--python` runs after the window exists but before the main loop starts. [S] Doing the real setup from `bpy.app.timers.register(fn, first_interval=0)` works. [T]
- Python is 3.13 with numpy 2.3 bundled; `socket`, `mmap`, `threading`, `ctypes` work. `PYTHONPATH` is ignored unless `--python-use-system-env` is passed. [S]

## The bridge

`bridge/c4d_bridge` implements protocol version 0 (`protocol/protocol.md`). Tested on 5.2.3 with `python tests\bridge\test_protocol.py "<blender.exe>"` and from the plugin's session self-test. [T]

- The bridge is packaged as a Blender extension (`bridge/blender_manifest.toml`, id `cycles_render_bridge`). `blender --command extension validate <zip>` accepts the package, and `blender --command extension install-file -r user_default -e <zip>` (what "Install from Disk" does) unpacks it into `<user folder>/extensions/user_default/cycles_render_bridge/`. The user folder is `%APPDATA%\Blender Foundation\Blender\5.2` (`bpy.utils.user_resource('EXTENSIONS', path='user_default')` gives the same place under `--factory-startup`), or the folder named by `BLENDER_USER_RESOURCES`. The plugin starts Blender with `c4d_bridge/main.py` from there as `--python` script; with `--factory-startup` the add-on itself is not loaded, and need not be. Its `__init__.py` registers only a line of explanation for Blender's Preferences. [T: installed into a throw-away profile; self-test and a render through it]
- `main.py` is the script Blender runs. Its arguments after `--`: `--handshake <file>`, `--token <text>`, and `--show-window` to keep the window visible for debugging. It refuses Blender versions outside `SUPPORTED_BLENDER` (`__init__.py`) by writing an error into the handshake file and exiting with code 4.
- `server.py` holds the `Bridge` class: a socket thread that only queues frames, and handlers that run on the main thread. A background Blender serves from a blocking loop (`run_blocking`); a windowed Blender serves from a `bpy.app.timers` callback plus the 2 ms window timer (`run_on_timer`). Add an operation by adding a method and an entry in `self.handlers`; a handler returns `(reply fields, reply blobs)` or raises `RequestError(code, message)`.
- `protocol.py` encodes and decodes frames and imports no `bpy`, so tests use it directly.
- From launch to an answered `hello`: 2.3 s in background mode, 2.9 s windowed. A `ping` carrying 1 MiB takes about 1 ms in background mode and 3 ms windowed.
- A frame may carry up to 2^20 blobs (`MAX_BLOBS` in `protocol.py`; 4096 up to 0.1.0, which a scene of 820 meshes reached, five blobs a mesh). A ping with 5000 blobs comes back intact in both modes [T: `tests/bridge/test_protocol.py`].
- In background mode the script ends with `sys.exit(code)` and Blender exits with that code. In windowed mode it calls `bpy.ops.wm.quit_blender()` after `shutdown` (exit code 0) and `os._exit(code)` otherwise.
- To refuse a client and still deliver the error reply, close only the sending side (`sock.shutdown(SHUT_WR)`); closing the socket outright while the reader thread is blocked on it resets the connection and the client never sees the reply.
- `scene/` builds scene items; `scene/__init__.py` holds the `Scene` class and the `BUILDERS` table, one module per kind next to it (`meshes`, `objects`, `cameras`, `lights`, `materials`, `world`). Items are kept by the plugin's ids, so sending an id again replaces that item; `Scene.clear()` removes everything, including Blender's start-up cube. A new kind is one builder function plus an entry in `BUILDERS`. A builder reports problems that should not stop the render with `scene.warn(text)`. [T: `tests\bridge\test_scene.py`]
- `scene/materials.py` builds materials and the world from node graphs described by the plugin in Blender's own names (`build_nodes`); it knows nothing about Cinema 4D. Materials are assigned on the object (`slot.link = 'OBJECT'`), so objects sharing a mesh can differ. [T]
- `render/settings.py` applies `settings` requests: engine, device, working colour space, and `[path, value]` pairs set with `scene.path_resolve`. `render/devices.py` enables a GPU back end. [T]
- `final/__init__.py` is the final driver: it sets the resolution, runs `bpy.ops.render.render()` and returns the pixels, flipped so the top row comes first. Cycles: the `Combined` pass captured by the wrapped `CyclesRender.render_frame_finish`. Eevee: rendered to an uncompressed 32-bit EXR in a temporary folder and read back with the bundled `OpenImageIO`; the file's linear colour space is set to the working space so values come back unchanged (0.8, 0.2, 0.1 in ACEScg reads back as 0.7998, 0.2, 0.1). A 160×90, 32-sample frame takes well under a second. Passes and progress events are not wired up yet. [T]
- The window is hidden right at start (`main.py`). The live viewport is `viewport/`; see "The viewport driver" below.
- Scene items are updated in place where possible, because other things point at them: a mesh keeps its datablock and its material slots (clearing `mesh.materials` empties the slots of every object that shows the mesh [T]); a camera keeps its object and data; an object whose mesh is unchanged only gets its matrix and materials set. `remove` deletes objects before meshes: removing a mesh that an object still uses takes the object along and leaves a dead reference [T].

## The viewport driver

`bridge/c4d_bridge/viewport/` is the live render of the IPR: `__init__.py` (the `Viewport` class: set-up, the `view_` operations, the draw callbacks), `frame_block.py` (shared-memory writer, no `bpy`), `window.py` (find, hide, show and resize Blender's window through Win32; the process's priority is the plugin's to set). Tested by `tests\bridge\test_viewport.py`. What building it taught, all [T] on 5.2.3:

- **A property set from Python does not restart the viewport render.** After a `settings` request the bridge calls `scene.update_tag()`; without it a changed `cycles.preview_samples` is ignored until something else changes.
- **Cycles' "Rendering Done" is not trustworthy right after a change.** The text belongs to the render thread, which picks a change up a moment later (a resize is also held back 0.2 s), so for a while the viewport still says "done" about the previous render, with a black picture after a resize. The driver therefore reports "done" only when 0.6 s have passed since the last change (`_SETTLE_SECONDS`), and asks for one more redraw at that time in case the change restarted nothing.
- **Start in the right size.** `view_start` resizes the window and switches to Rendered only once the region has the new size. Switching at once renders the old size first, restarts, and for a session being created that restart took longer than the settle time.
- **Adaptive sampling ends a viewport render early.** With `cycles.use_preview_adaptive_sampling` on (Blender's default) a simple scene reports "Rendering Done" after a few samples whatever `preview_samples` says. The plugin sets it from the same Cinema 4D setting as final-frame adaptive sampling.
- **Cycles' viewport shows no negative values in data passes:** a face with normal −Y is black in the `NORMAL` pass; Eevee shows the negative value.
- **The viewport's own view can stand in for a camera** (`view_camera`). With `view_perspective = 'PERSP'` Blender treats the view as a 36 mm sensor fitted to the larger side of the region, at half the nominal focal length (`BKE_camera_params_from_view3d`, zoom 2). So a camera with lens L and sensor width S spanning the image width is matched by `space.lens = 2 · L · 36 / S`, times width/height for a tall image (`free_view_lens`). `space.lens` accepts 1–250 mm. `region_3d.view_matrix` is the inverse of the camera's world matrix. Pictures through the view and through the camera object differ by 0.0–0.6 %.
- **Process priority** (since 0.2.0 the client's, not the bridge's). Up to 0.1.0 the viewport Blender set itself to below normal; that changed nothing against a Cinema 4D that lowers itself to below normal too (SDK reference, "Priority and cores of the IPR's Blender"). Now the bridge leaves its class alone and the plugin sets it for the Blender it started. Measured with the bridge alone (`internal/b11/priority_probe.py`, Blender 5.2.3, i9-13900K with 8 P and 16 E cores, 960 × 540, a free-view move every 50 ms; a "burner" is one spinning process per logical processor at below normal, standing in for Cinema 4D using every core) [T, 2026-11-17]:
  - Without a burner, idle and below normal make no difference, on the GPU or the CPU: 80 to 88 samples a second on the CPU in both (no sign that Windows keeps an idle-class render off the performance cores on this hybrid CPU), replies in 1.3 to 2.1 ms, a frame 15 to 18 ms after the reply (median).
  - With the burner, a Blender at **idle stands completely still**: no reply to a request within 10 s, no frame, no sample, 0 cores, on the GPU and on the CPU, also with its main thread raised to `THREAD_PRIORITY_HIGHEST` (6, as the burner's threads) or `TIME_CRITICAL` (15). At below normal it goes on: GPU replies 1.3 ms (max 5.9), 28 frames a second; CPU 15 cores (half the machine), replies 2.6 ms (max 12), 39 samples a second against 80.
  So idle is not used.
- **Frames are published at most 30 times a second** (since 0.2.0; `PUBLISH_SECONDS` in `viewport/__init__.py`). Every redraw updates the progress fields; only a redraw at least 1/30 s after the last published one (or the one at which the render becomes done or paused, or one of a new size) reads the framebuffer back and publishes. A redraw that was not published registers a timer that tags the area for redraw when the time has come, so the last picture of a burst is published even when Blender draws nothing more by itself. The viewport status counts `redrawn` and `published` [T: `tests/bridge/test_frame_rate.py`].
- **Draw callbacks may register timers** (`bpy.app.timers.register`), which is how the driver schedules its late redraw.
- **Timing, 480×270, CPU:** first finished 32-sample picture 0.7–0.8 s after `view_start`; an object edit reaches the frame block in 30–95 ms as seen by the pure-Python test reader, which is itself slow.

- **A view set during a resize can come out shifted.** Cycles takes a new region size a moment after the region has it. When `view_camera` arrives in between, the finished picture is sometimes (2 of 16 tries) the right picture drawn around the centre of the old size, off by half the size difference. The driver sets the view once more 0.25 s after the region has reached its new size (`_after_resize`: a change of 0.001 % in the lens, alternating in sign); 60 of 60 tries were right with it.

## Main loop, timers and threads

- In `-b` mode there is no event loop: `bpy.app.timers`, modal operators and render jobs never run, and `render.render()` blocks. [S]
- In windowed mode timers run once per loop iteration. The loop sleeps 5 ms when idle. [S]
- `context.window_manager.event_timer_add(0.002, window=win)` shortens that sleep to about 2 ms. Measured over a socket, it cut the median edit-to-frame round trip from 18.0 ms to 12.6 ms (Cycles on GPU). [T] It makes the loop spin continuously, so remove it (`event_timer_remove`) while the IPR is stopped or paused.
- A worker thread can also wake the loop with `PostMessageW(hwnd, WM_NULL, 0, 0)`. Without the timer this saved about 3 ms; with the timer running it saved under 1 ms, within noise. [T]
- A socket thread plus a `queue.Queue` drained by a `bpy.app.timers` callback works as the command path; commands waited about 1 ms in the queue. The bridge does this in `bridge/c4d_bridge/server.py`. [T]
- Inside a timer `area` and `region` are None. [S] Get the window from `bpy.context.window_manager.windows[0]` and run operators inside `with bpy.context.temp_override(window=win, area=area, region=region):`. [T]
- All `bpy` work happens on the main thread. A socket thread only moves bytes into a `queue.Queue`. [S]
- All edits made in one timer call produce one scene evaluation and one render restart, provided the code does not force evaluation (`evaluated_depsgraph_get()`, `view_layer.update()`). [S]
- `bpy.ops.wm.quit_blender()` from a timer exits cleanly; set `preferences.view.use_save_prompt = False` first. [T]

## Window and viewport setup

Sequence that works [T]:

1. `preferences.view.show_splash = False`; `preferences.view.render_display_type = 'NONE'`.
2. Find the `VIEW_3D` area and its `WINDOW` region; inside `temp_override` call `bpy.ops.screen.screen_full_area(use_hide_panels=True)`.
3. **In a later timer call**, find the area again (the screen was swapped). The region is now exactly the window's client size.
4. On the space: `overlay.show_overlays = False`, `show_gizmo = False`, `shading.use_scene_lights_render = True`, `shading.use_scene_world_render = True`, `shading.type = 'RENDERED'`.
5. On `space.region_3d`: `view_perspective = 'CAMERA'`, `view_camera_zoom = 50 * (2 - sqrt(2))` (≈ 29.2893), `view_camera_offset = (0, 0)`. With the render aspect equal to the region aspect, the camera frame then fills the region exactly. [T: viewport frame matched the final render pixel for pixel]
6. `scene.render.preview_pixel_size = '1'` forces one render pixel per region pixel regardless of display scaling.

Window control (Windows) [T]:

- Blender's window class is `GHOST_WindowClass`. Find the handle with `EnumWindows` filtered by the Blender process id.
- A client size as small as 320×180 works with `SetWindowPos`, below the 640×480 minimum of the `-p` argument. [T]
- `ShowWindow(hwnd, SW_HIDE)` hides it and rendering continues. Blender skips drawing only for *minimized* windows, so keep it un-minimized.
- `Window.x/y/width/height` are read-only in Python. [S] Resize with Win32 `SetWindowPos`; Blender follows the external resize and the region stays equal to the client area. [T] Cycles debounces a resize by 0.2 s. [S]
- Pass `SWP_NOSENDCHANGING` (0x0400). Without it Windows clamps the window to the desktop (a 1920×1080 request on a 1600×900 desktop gave 1604×881). With it the client size is exact and can exceed the desktop: 3840×2160 rendered and read back correctly on a 1600×900 desktop, for both engines. [T]
- Compute the outer window size from the difference between `GetWindowRect` and `GetClientRect` (`set_client_size` in `bridge/c4d_bridge/viewport/window.py`). [T]
- After a resize set the render resolution to the region size again, so the camera frame keeps filling the region. [T]
- Readback cost grows with pixel count: about 1.3 ms at 960×540, 3–6 ms at 1600×881, 20–23 ms at 3840×2160. [T]
- A DPI change makes Blender resize its own window; keep it on one monitor. [S] Display scaling other than 100 % is untested.

## Reading viewport pixels

- The viewport render texture is RGBA16F and holds scene-linear values. View transform, look, exposure, gamma and dither are applied later, when Blender composites to its window. (`source/blender/gpu/intern/gpu_viewport.cc`, `source/blender/draw/engines/external/external_engine.cc`) [S, confirmed T]
- Row order is the same as `RenderPass.rect` from a final render. [T] Both are bottom-up. [S]
- Values are in the file's working colour space. [T] Alpha is premultiplied [S]; untested, because every test scene had alpha 1.

**Route A — draw handlers, both engines** [T]:

```python
_fb = [None]
def pre_view():  _fb[0] = gpu.state.active_framebuffer_get()
def post_view():
    fb, region = _fb[0], bpy.context.region
    with fb.bind():
        fb.read_color(0, 0, region.width, region.height, 4, 0, 'FLOAT', data=buf)
bpy.types.SpaceView3D.draw_handler_add(pre_view, (), 'WINDOW', 'PRE_VIEW')
bpy.types.SpaceView3D.draw_handler_add(post_view, (), 'WINDOW', 'POST_VIEW')
```

**Route B — wrap Cycles' draw method** [T]: assign a wrapper to `cycles.CyclesRender.view_draw` that calls the original, then reads `gpu.state.active_framebuffer_get()` the same way. Blender looks the method up on every call, so the wrapper takes effect immediately. Route B is also where the engine object (`self`) is available for the status text.

Both routes returned identical pixels on every frame.

**Zero-copy into shared memory** [T]:

```python
mm  = mmap.mmap(-1, w * h * 16, tagname="<name>")
arr = numpy.frombuffer(mm, dtype=numpy.float32)
buf = gpu.types.Buffer('FLOAT', (h, w, 4), arr)     # wraps arr, no copy
```

- Read pixels from `arr`. Converting a multi-dimensional `gpu.types.Buffer` with `numpy.asarray` returns scrambled data. [T]
- Cost at 960×540: 1.2–1.7 ms median, occasional spikes to 10–35 ms. [T]
- `read_color(x, y, w, h, channels, slot, format, data=)`; formats `'FLOAT'`, `'UBYTE'`, `'INT'`, `'UINT'`. [S]

Rules inside draw callbacks:

- Leave scene data untouched there: Blender rejects writes to scene data during drawing. Make edits from timers. [S]
- Keep the engine object out of long-lived variables, or its session is never freed. [S]

What to expect in the frames:

- After a restart Cycles first draws low-resolution frames scaled up, then full resolution. [S]
- A redraw without a new sample redraws the last image, so frames can repeat. Tag frames with an id. [S]
- Eevee redraws continuously while shaders compile. The first non-black frame of the default scene arrived 8.9 s after start on the first 5.0 run and 0.33 s on 5.2.3, so first-frame time varies widely with shader compilation and caching. [T]

## Cycles status text

- Cycles writes `Sample N/M`, `Rendering Paused`, `Rendering Done`, `Updating Shaders` into `RenderEngine.text`. Blender exposes no Python property for it. [S]
- Read it with `ctypes.string_at(engine.as_pointer() + 64, 512).split(b"\0", 1)[0]` inside the `view_draw` wrapper. Offset 64 was found by scanning on both 5.0 and 5.2.3 [T] and matches the struct in `source/blender/render/RE_engine.h`.
- Validate at start-up by scanning offsets 0–512 for a printable string matching a known status; refuse to guess.
- The text updates on change or once per second, so sample numbers skip. [T]
- Fallback: `--log cycles --log-level info --log-file <f>` emits "Rendered N samples". [S]
- Eevee exposes no sample count. Count redraws since the last restart; it has converged when redraws stop. [S]

## What a live scene edit costs

Measured with a prototype script on 5.2.3, hidden, 960×540, Cycles on OptiX. [T]

- Creating a 1,000,000-quad mesh with `foreach_set` and `mesh.update(calc_edges=True)` takes 0.41–0.46 s; the first frame follows about 0.1 s later.
- Replacing all positions of that mesh (`vertices.foreach_set("co", …)`, `mesh.update()`) takes about 0.1 s to apply and 0.3 s to the first frame.
- With only that mesh in the scene, a camera-object move reaches pixels in 14 ms: polygon count alone does not slow edits.
- With 100,000 Geometry Nodes instances added, **every** scene edit costs 0.16–0.21 s before the first frame, including a camera-object move, because Cycles walks all object instances on each scene update.
- Changing the viewport's own view (`region_3d.view_distance`, `view_location`, `view_rotation`, `view_matrix` with `view_perspective = 'PERSP'`) changes no scene datablock and reaches pixels in 18 ms in the same scene. Depth of field and camera-only features need camera view.
- Eevee redraws all instances for every sample: about 0.07–0.15 s per update and 2 s for 32 samples with 100,000 instances.
- **What an instance costs per update, and what does not help** (0.3.0, F1; measured 2026-11-23 with `internal/f1/blender_instancing.py`, Blender 5.2.3, GPU, 640 x 640, a cylinder of 48 triangles; the time from a `scene` request with new matrices until a picture with one sample, median of ten updates) [T]:

  | Copies | As | Cycles | Eevee |
  |---|---|---|---|
  | 120,000 | a `pointcloud` (Blender's spheres) | 35 ms | 21 ms |
  | 12,000 | one `instancer` | 34 ms | |
  | 120,000 | one `instancer` | 242 ms | 106 ms |
  | 120,000 | the same without Set Instance Transform (places only) | 238 ms | 102 ms |
  | 120,000 | the same with Realize Instances after it (one mesh of 5.8 million triangles) | 308 ms | |
  | 120,000 | 20 instancers with the same matrices (an object of 20 meshes before 0.3.0) | 5,202 ms | |
  | 120,000 | one `instancer` with 20 `parts` (0.3.0) | 256 ms | 119 ms |

  So an instance costs about 2 microseconds per update in Cycles and 1 in Eevee, whatever the nodes that make it, and the bridge's own part is small (the request was answered after 13 to 18 ms in every row but the 20 instancers', 250 ms). It is the engines' walk over the instances (the first bullet above), which a point cloud does not have: a point cloud is one geometry. Instances therefore cannot be as fast as the spheres; what can be avoided is multiplying them. Twenty meshes on 120,000 copies were 2.4 million instances and are 120,000 with `parts`. (The point cloud's own updates were sometimes 0.67 s instead of 35 ms in this measurement, in about half of the updates at 120,000 points and nine of ten at 12,000: not looked into, and not seen in the plugin's own measurement below; open.)
- **Joining an instancer's parts** (0.3.0, F1; `bridge/c4d_bridge/scene/instancers.py`; `internal/f1/blender_join_probe.py` on 5.0.0, 5.2.3 and 5.3.0, the same on all three) [T]: geometry taken from an object with Object Info leaves the materials of the object's slots behind (two parts of one mesh with different materials on their objects came out with no material at all, and all faces in slot 0). Set by nodes they stay: per part and material slot a Set Material whose selection is `material_index` equal to the slot, before the Join Geometry (the joined mesh then lists every part's materials and each face has its own). The parts' places come from their objects' matrices with Object Info set to Relative. The prototype that carries the join is in no collection, like the single-mesh prototype, and is evaluated because the instancer's node group refers to it.

## Building scene data fast

- Mesh fill order: `vertices.add`, `loops.add`, `polygons.add`; `attributes["position"].data.foreach_set("vector", …)`; `polygons.foreach_set("loop_start", …)` then `foreach_set("vertices", …)`; `mesh.update(calc_edges=True)`. Pattern: `from_pydata` in `scripts/modules/_bpy_types.py`. [S]
- `foreach_set`/`foreach_get` take numpy arrays directly when the dtype matches (float32, int32, bool). [T for `foreach_get`]
- Normals: a `FLOAT_VECTOR` attribute named `custom_normal` on the `CORNER` domain sets shading normals directly, in the mesh's own axes: `mesh.attributes.new("custom_normal", 'FLOAT_VECTOR', 'CORNER').data.foreach_set("vector", values)` before `mesh.update()`. Tilting them by 60° halves a plane's diffuse brightness, as it must. `use_auto_smooth` no longer exists. [T]
- UVs: `uv_layers.new(name=…, do_init=False)`, then `layer.uv.foreach_set("vector", …)` [T]. Colours: `color_attributes.new(name, 'FLOAT_COLOR', 'POINT' | 'CORNER')`. Vertex maps: a float `POINT` attribute, read in shaders with the Attribute node. [S]
- Instancing at scale, as built in `scene/instancers.py` [T, `tests\bridge\test_geometry.py`]: a mesh of loose vertices with a `FLOAT4X4` point attribute (`c4d_transform`) and a `FLOAT_COLOR` point attribute (`mograph_color`); a Geometry Nodes modifier with Object Info (As Instance) → Instance on Points → Set Instance Transform fed by a Named Attribute node of type `FLOAT4X4`. Point attributes travel to the instances, so a shader reads the colour with an Attribute node of type `INSTANCER`, in Cycles and in Eevee.
  - Do not call the matrix attribute `instance_transform`: that is the instances' own built-in attribute, and a point attribute of that name is dropped (every instance then sits unrotated and unscaled at its point).
  - `foreach_set("value", …)` on a `FLOAT4X4` attribute takes each matrix column by column.
  - The prototype object need not be in any collection: Object Info still instances it, with the materials of its object-linked slots, and it does not render by itself.
  - 100,000 instances are built in 0.02–0.05 s.
- Numbers per object and per instance, as built in `scene/objects.py` and `scene/instancers.py` [T, `tests\bridge\test_geometry.py`, `check_numbers`, Cycles and Eevee, Blender 5.2.3]: a custom property of the object (`obj[name] = value`) and a `FLOAT` point attribute of the instancer's points. One Attribute node of type `INSTANCER` reads both: Blender looks up (source, `BKE_object_dupli_find_rgba_attribute`) a particle system's property, then the geometry-nodes instance attribute, then the instancer object's (dupli parent's) property, then the object's own property, then its data's; nothing found gives 0. Deleting the property (`del obj[name]`) makes it read 0 again. Cycles' Object Info Random is the hash of the object's name for an object and of its dupli's persistent id for an instance (`intern/cycles/blender/object.cpp`, `object_dupli.cc`); the plugin does not use it for Redshift's random nodes, because Redshift gives objects of equal paths, and copies of one render instance, one value. *Open:* Eevee (5.2.3, 5.3.0; not 5.0.0) showed 12 of 256 objects with another object's property in one order of renders (`docs/roadmap.md`, "Open bugs").
- Mesh attributes [T]: `mesh.attributes.new(name, 'FLOAT', 'POINT')` with `foreach_set("value", …)`; `'FLOAT_COLOR'` on `'POINT'` or `'CORNER'` with `foreach_set("color", …)`. An Attribute node of type `GEOMETRY` reads either; its Color output gives a float attribute as grey. `uv_layers[i].active_render = True` chooses the set image textures use without a UV Map node. `polygons.foreach_set("material_index", …)` assigns slots.
- Changing only positions: `vertices.foreach_set("co", …)`, the `custom_normal` attribute's `foreach_set`, then `mesh.update()`; no need to rebuild the topology. `clear_geometry()` on a mesh keeps its material slots but not its attributes.
- Images from memory: `bpy.data.images.new(name, w, h, float_buffer=True)` and `pixels.foreach_set`. [S]

## Scene property notes

- Light brightness, measured on a white diffuse surface facing the light [T: `tests/bridge/measure_lights.py`]: sun of strength S gives S / π; point or spot of power P at d metres gives P / (4 π² d²); a small area light gives P / (π² d²) on its axis. `use_shadow = False` lets a light shine through objects.
- Lights: `type` `POINT`/`SUN`/`SPOT`/`AREA`; `energy` in watts (sun: W/m²); `spot_size`, `spot_blend`; area `shape`, `size`, `size_y`. Light linking: `object.light_linking.receiver_collection` / `blocker_collection`. [S]
- **A light Blender adds** (Add > Light, `bpy.ops.object.light_add`, Blender 5.2.3, measured): 10 W (a sun 1 W/m²), radius 0, soft falloff on, spot 45° with blend 0.15, area square 1 m (the operator's size times 4), spread 180°, sun angle 0.526°, exposure 0, normalize on, temperature 6500 K and off, Cast Shadow on, `cycles.max_bounces` 1024, multiple importance on, shadow caustics and portal off; the object's `visible_camera` is off (the other ray visibilities on). The Cycles Light object and tag start with these values. Properties per type: `spread` on area lights only, `use_soft_falloff` on point and spot, `use_absolute_resolution` and `cutoff_distance` not on a sun: setting one a type lacks raises `AttributeError` (the bridge names it in a warning) [T: `tests/bridge/test_lights.py`].
- **What changes the picture** [T: `tests/bridge/test_lights.py`, Cycles and Eevee alike]: one stop of `exposure` doubles the light (2.00); `use_temperature` with 2000 K gives (15.8, 4.1, 0.13) where white gives equal channels (`BKE_light_color` multiplies the colour by the black body's); `normalize` off multiplies the power by the light's area (`BKE_light_area`; 4.00 for a 2 m square); an area light facing the camera is seen only with `visible_camera` on; Eevee's `diffuse_factor` 0.5 halves the light (0.50).
- Ray visibility: `visible_camera`, `visible_diffuse`, `visible_glossy`, `visible_transmission`, `visible_volume_scatter`, `visible_shadow`; `is_holdout`, `is_shadow_catcher`. [S]
- "Indirect only" (`LayerCollection.indirect_only`) is nothing but "not seen by the camera" in Cycles: `intern/cycles/blender/object.cpp` clears `PATH_RAY_VISIBILITY_CAMERA` for it and does nothing else. So `visible_camera = False` on an object is the same thing, per object. Holdout and shadow catcher are object properties and work per object. [T: `tests/c4d/object_tag.py` for holdout and camera; S for the source]
- Principled Volume: the `Temperature` input (1000) times the temperature attribute is the black body's kelvin. A fire grid in the range 0 to 4 (EmberGen's `flames`) barely glows that way; for such a grid an Attribute node's `Fac` drives `Emission Strength`, and a Blackbody node at `Fac` times kelvin gives `Emission Color`. [T: `tests/c4d/fire_vdb.py`]
- A volume object shows the file's grids at the file's own coordinates (its transform included), in the object's axes: a .vdb written Y-up lies along Blender's Y until the object matrix swaps the axes. [T]
- `ShaderNodeMix` has several inputs and outputs of one name: address them by identifier (`Factor_Float`, `A_Color`, `B_Color`, `Result_Color`); a Math node's inputs are `Value`, `Value_001`, `Value_002`. A Light Path node's `Is Shadow Ray` and `Is Diffuse Ray` let a material be something else for shadow and gathering rays. [T: `tests/c4d/redshift_material.py`]
- Every scene property of the settings page was read from Blender 5.2.3 with its default and its options (`scene.path_resolve(owner).bl_rna.properties[name]` gives `default`, `hard_min`, `hard_max` and `enum_items`); `cycles.denoiser`, `preview_denoiser` and `sampling_pattern` list only what this machine offers. Eevee's `ray_tracing_options` has no `screen_trace_precision` in 5.2. [T: `tests/c4d/settings.py` sets all 101]
- Camera: `lens`, `sensor_width`, `sensor_fit`, `shift_x`, `shift_y`, `clip_start`, `clip_end`, `ortho_scale`, `type` `PERSP`/`ORTHO`/`PANO`; `dof.use_dof`, `dof.focus_distance`, `dof.aperture_fstop`. [S] More under "Cameras" below.
- Principled BSDF inputs: Base Color, Metallic, Roughness, IOR, Alpha, Normal, Subsurface Weight, Specular IOR Level, Specular Tint, Anisotropic, Transmission Weight, Coat Weight, Coat Roughness, Sheen Weight, Emission Color, Emission Strength, Thin Film Thickness. Use `ShaderNodeMix`, not the legacy MixRGB. [S]
- World panorama: `ShaderNodeTexEnvironment` puts the image centre towards +X and runs on towards −Y. A Mapping node (type `POINT`) between `ShaderNodeTexCoord`'s `Generated` output and the texture rotates or mirrors it. [T]
- Node sockets are best named by identifier: a Mix node in colour mode has `Factor_Float`, `A_Color`, `B_Color`, `Result_Color`; Math has `Value`, `Value_001`; Vector Math has `Vector`, `Vector_001`, `Vector_002`. A colour output linked to a float input is converted to its brightness. [T]
- `use_nodes` on materials, worlds and lights is deprecated and always on. `Material.displacement_method` lives on the material. [S]
- Volumes: `bpy.data.volumes.new()`, `filepath`, `is_sequence`, `frame_start`, `frame_duration`, `sequence_mode` [S]. Grids cannot be created in memory from Python; write `.vdb` files. As built in `scene/volumes.py` [T]: a volume with a file path, an object with a matrix (a mirroring matrix is fine), and a material slot holding a Principled Volume whose "Density Attribute" names the grid. `volume.render.space` is `'OBJECT'` by default, which scales density with the object: a file in centimetres shown at scale 0.01 was a hundred times too thick; `'WORLD'` takes density per metre. The Principled Volume's emission lights every active voxel of the grid, whatever the density. Eevee renders the same volume with a softer edge.
- Hair curves [T]: `bpy.data.hair_curves.new(name)`, `curves.add_curves([points per curve, …])`, `curves.points.foreach_set("position", …)`, a float `POINT` attribute `radius`. Point clouds [T]: `bpy.data.pointclouds.new(name)`, `cloud.resize(n)`, `cloud.points.foreach_set("co" | "radius", …)`, a `FLOAT_COLOR` point attribute read by an Attribute node of type `GEOMETRY`. Cycles renders the points as spheres.
- Light linking [T]: `light_object.light_linking.receiver_collection` and `.blocker_collection` take a collection; an entry's `collection.collection_objects[i].light_linking.link_state = 'EXCLUDE'` turns "only these" into "all but these". Ray visibility [T for camera and shadow]: `object.visible_camera`, `visible_shadow`, `visible_diffuse`, `visible_glossy`, `visible_transmission`.
- Motion blur [T, `tests\c4d\motion_blur.py`]: `render.use_motion_blur`, `motion_blur_shutter` (in frames; the interface offers up to 1, the property accepts more), `motion_blur_position`. Cycles asks the scene for the frame at shutter open, centre and close (`RE_engine_frame_set`) and reads every object's and the camera's matrix there, so an object must be animated in Blender to blur: three keys on location, quaternion rotation and scale. With a shutter of 2 and keys on the frames before and after, the samples fall exactly on the keys. A new object needs no animation check: Cycles samples all of them.
- Deformation blur in Cycles [T]: a `POINT` float-vector attribute named `velocity`, in units per second. Cycles places each point at position ± velocity × shutter / (2 × fps). Eevee does not read it [T]; it blurs moving objects only.
- `render.use_persistent_data = True` with one changed object per frame rendered 50 frames correctly [T, `sequence.py`].
- Region [T]: `render.use_border` with `border_min_x` … as fractions from the lower left corner; `use_crop_to_border = False`. For the viewport: `space.use_render_border` and `space.render_border_min_x` … for the viewport's own view, the scene's border for the camera view. The viewport then renders the region only and leaves the rest of its framebuffer as it was.
- Denoising [T]: `cycles.denoiser` / `preview_denoiser` (`OPENIMAGEDENOISE`, `OPTIX`; setting an option the machine lacks raises `TypeError`), `cycles.denoising_input_passes` / `preview_denoising_input_passes` (`RGB`, `RGB_ALBEDO`, `RGB_ALBEDO_NORMAL`).
- Working colour space is per file: read `bpy.data.colorspace.working_space` (default `Linear Rec.709`), change with `bpy.ops.wm.set_working_color_space(working_space='ACEScg', convert_colors=False)`. Call it before the viewport starts rendering: it stops all viewport renders and cancels while a job is running or an image is unsaved. [T]
- Colour values pass through numerically unchanged in the working space: an emission colour of (0.8, 0.2, 0.1) reads back as (0.8, 0.2, 0.1) from both the viewport and a final render, in `Linear Rec.709` and in `ACEScg`. The viewport value is rounded to half-float (0.7998). [T]
- `scene.view_settings.view_transform` (`Standard`, `AgX`, `Filmic`, `Raw`, …) does not affect the readback. A custom OCIO config is set with the `BLENDER_OCIO` environment variable at launch (untested). Texture colour space: `image.colorspace_settings.name`. [S]
- `bpy.data.images.load(path, check_existing=True)` hands back the image already loaded from that file, and a colour space set on it applies to everyone who uses it. Two materials reading one PNG as `sRGB` and as `Linear Rec.709` (a bitmap set to the Linear profile in a "Basic" document) then both rendered with the colour space set last [T: `tests/c4d/colour.py`, strips "PNG sRGB 128" and "PNG 128, bitmap profile Linear", 0.737 instead of 0.502 before the change]. The bridge loads one image per `image` item (`check_existing=False`, `scene/materials.py`); the plugin sends one item per file and colour space.

## Attributes a material reads

For data per particle, per copy of an instancer and per object (0.3.0, F12 and F13; the names are in `protocol/protocol.md`, "Attributes a material reads"). Measured 2026-11-24 with `prototypes/attribute_check.py` in a background Blender, final frames, on 5.0.0, 5.1.2, 5.2.3 and 5.3.0, Cycles and Eevee: all eight gave the same numbers (Eevee within 0.0004) [T]. The scene: a point cloud whose point has the attributes, instances of a cube on a point that has them (Instance on Points), a plain cube, a cube whose object has custom properties of the same names, a cube whose mesh has vertex attributes of those names, and instances of that cube on a point that has them too; one emission material read by an Attribute node.

- **Where an Attribute node looks.** Type `GEOMETRY`: the attributes of the geometry itself (a point cloud's points, a mesh's vertices). Type `INSTANCER`: the attributes of the instance (what the points had before Instance on Points made them instances); where the instance has none of that name, or the object is not instanced, the object's own custom property of that name. Type `OBJECT`: the object's custom property only. A custom property can be a number, or a list of three or four numbers, read as a vector or as a colour with its alpha.
- **A missing attribute reads as 0**: from the Color, the Vector and the Factor output, for all three types, in both engines and all four versions. So `GEOMETRY` + `INSTANCER` added up is right on a point cloud, on instances, on a plain object with the property and (as 0) on an object with neither: one material serves all of them. The plugin's translations of Redshift's user data nodes read particle and clone data this way (`materials/redshift_scene_data.cpp`).
- **The Alpha output cannot be added up.** For a missing attribute it is 1 with `GEOMETRY` (but 0 in Eevee on a point cloud) and 0 with `INSTANCER`; for an attribute that is a number it is 1. So a colour's alpha is sent as a number of its own (`particle_alpha`) and read from the Factor output.
- **The Factor output of a colour or vector is the mean of its three numbers** ((0.2, 0.4, 0.6) reads 0.4; a property (0.9, 0.1, 0.3) reads 0.433). Redshift's Scalar User Data node gives the same of a colour (measured: `docs/reference/c4d-sdk.md`).
- **Both present add up to twice the data**: instances of a mesh that has a vertex attribute of the name, on points that have it too. The plugin's names for particle and clone data (`particle_...`, `mograph_...`) are no names a mesh's tags get by themselves.
- **Blender 5.0's point clouds** (a mesh's loose vertices through Mesh to Points, `scene/pointclouds.py`) keep the vertices' attributes, and the node reads them like a real point cloud's [T: `tests/bridge/test_geometry.py`, `element_attributes`, on 5.0.0]. The material has to sit on the object's slot there (as the bridge puts it): put on the mesh alone, the points rendered without it.
- **Cycles at 16 samples shows a flat emission up to 8 % off** in `tests/bridge/test_geometry.py` (1.0 as 1.077, 0.75 as 0.775; Eevee exact). Not followed further: the test allows 9 % for Cycles; the tests in Cinema 4D (`tests/c4d/scene_data.py`, 4 samples, compared with Redshift) agree within 0.0005.
- **What the bridge does with them** (`scene/common.py`, `named_attributes`): an `attributes` entry becomes a point attribute of type `FLOAT`, `FLOAT_VECTOR` or `FLOAT_COLOR` on the point cloud, or on the loose points an instancer is made from (which Instance on Points turns into the instances' own). An instancer's `properties` are custom properties of the object that carries the modifier: Blender looks there for an instance without the attribute, before the instanced object itself.

## Several output nodes (0.3.0, F11 step 4)

Measured 2026-11-24 with `internal/f11/step4/probe_outputs.py` (results beside it), final frames in a background Blender, 5.0.0, 5.1.2, 5.2.3 and 5.3.0, Cycles and Eevee, all four alike in every case [T]; read in `ntreeShaderOutputNode` (`nodes/shader/node_shader_tree.cc`) and `node_tree_set_output` (`blenkernel/intern/node.cc`) of 5.2.3 [S]. Each output fed by an Emission (a world's by a Background) of its own colour; the colour seen says which output rendered.

- **An output node has two settings:** `is_active_output` ("Active Output", the node's `NODE_DO_OUTPUT` flag) and `target` (`ALL`, `EEVEE`, `CYCLES`; "All" by default). Cycles asks for the output of target `CYCLES`, Eevee for `EEVEE` (`ntreeShaderOutputNode(tree, SHD_OUTPUT_CYCLES)` in `intern/cycles/blender/shader.cpp`; `SHD_OUTPUT_EEVEE` in the GPU material); `tree.get_output_node(target)` from Python gives the same answer as the render, in every case below.
- **One active output per kind and tree.** Setting `is_active_output` on one clears it on the others of the same node type (`rna_ShaderNode_is_active_output_set`); `node_tree_set_output` (run on every update) keeps only the first of several marked and, when none of a type is marked, marks the first of that type in the tree's node order (the order they were made). So "both marked" and "none marked" do not exist in a saved Blender file: setting both made only the second active, unsetting both made the first active again.
- **The choice for an engine:** only outputs whose target is All or the engine's count; one whose target is the engine's beats any of All, even an active one; among those of the same standing the active one, else the first in node order. Measured, as (Cycles, Eevee) for red, green, blue made in that order: two All, nothing set: red, red; two All, green set active: green, green; red All active and green Cycles: green, red; red Eevee and green Cycles: green, red; three where red and green are Cycles and blue is All and active: red (the first Cycles one, since the active flag is blue's), blue; red All, green and blue Cycles, blue active: blue, red. **No output for the engine** (two outputs of target Cycles, rendered in Eevee): nothing renders, the surface is black. The same for a world's World Outputs, case by case.
- **A World Output and a Material Output in one material:** on a mesh the Material Output renders in Cycles and Eevee, whichever of the two was made first (although `get_output_node()` answers the World Output when it came first: it looks at every kind of output node together).
- What the plugin makes of it: the Material Output node and the World Output node of the Cycles node space have both settings (ports `prop.is_active_output` and `prop.target`, `tools/make_nodes.py`); "Active Output" starts off, so "none marked" is every material saved before and gives the first output in the walk, as before; the exporter chooses per engine by the rule above (`ChooseOutput` in `materials/cycles_node_material.cpp`), the Material Outputs for an object and the World Outputs for a Cycles Environment, and sends one output to Blender. Two marked (which the Node Editor allows): the first marked in the walk. [T: `tests/c4d/cycles_nodes.py`, sections 13 and 14; `tests/c4d/environment_object.py`, part w.]

## A light's node tree, Eevee's custom distance (0.3.0, F13 W29)

## Cameras

Built by `bridge/c4d_bridge/scene/cameras.py` [T: `tests/bridge/test_cameras.py`, Cycles and Eevee, Blender 5.2.3; `tests/c4d/camera_tag.py`] unless marked.

- **Panorama settings are properties of the camera**, not of `camera.cycles` (they moved there some versions before 5.2; `rna_camera.cc`, and the versioning code in `blenkernel/intern/camera.cc` that still copies them to `camera.cycles`): `panorama_type` (`EQUIRECTANGULAR`, `EQUIANGULAR_CUBEMAP_FACE`, `MIRRORBALL`, `FISHEYE_EQUIDISTANT`, `FISHEYE_EQUISOLID`, `FISHEYE_LENS_POLYNOMIAL`, `CENTRAL_CYLINDRICAL`), `fisheye_fov`, `fisheye_lens`, `latitude_min`/`_max`, `longitude_min`/`_max`, `fisheye_polynomial_k0` to `_k4`, `central_cylindrical_range_u_min`/`_max`, `_v_min`/`_max`, `central_cylindrical_radius`. Defaults (`DNA_camera_types.h`): Fisheye Equisolid, field of view 180°, lens 10.5 mm, latitude ±90°, longitude ±180°, the polynomial of a real lens (k0 -1.17e-5, k1 -0.020, …), cylinder ±180°, height ±1, radius 1. Which settings Blender's panel shows per type: `properties_data_camera.py`, `DATA_PT_lens`. [S; all read back after being set, T]
- **Equirectangular:** the range fills the whole image; longitude grows from the camera's forward axis (-Z) towards its right (+X), `longitude_min` at the left edge; latitude 90° at the top. A 2:1 picture of the whole sphere put ahead at (0.50, 0.49), 90° right at (0.74, 0.49), 90° left at (0.25, 0.50) and 45° up at (0.50, 0.25) (marker centres, a few pixels across); longitude -90° to 90° with latitude 0° to 90° put 45° up in the middle. The equidistant fisheye maps an angle t from the axis to t / (fov/2) of the half width (270°, square picture: 90° right at 0.832 for 0.833). Fisheye Equisolid and Lens Polynomial use the sensor; with `sensor_fit` HORIZONTAL Cycles takes `sensor_width` and derives the height from the picture (`intern/cycles/blender/camera.cpp`). [S for the last]
- **Eevee has no panoramic camera before 5.3** (5.3.0 renders all seven types as Cycles does, "Version coupling"). In 5.2.3 the panorama branch of `eevee_camera.cc` is compiled out (`#if 0`) and a `PANO` camera falls to the perspective default: it renders as a perspective camera with its `lens` (measured: ahead in the middle, 90° left and right not in the picture of a 36 mm lens).
- **Depth of field:** `dof.aperture_blades` (0 or 3 to 16; the setter turns 1 and 2 into 3 or 0, `rna_CameraDOFSettings_aperture_blades_set`), `aperture_rotation` (radians), `aperture_ratio`. A `dof.focus_object` is measured along the camera's view axis, `|dot(view axis, camera - object)|` (`blender_camera_focal_distance` in `intern/cycles/blender/camera.cpp`), as Cinema 4D measures its own focus object; the plugin sends that distance instead of the object. An orthographic camera's aperture is 1 / (2 · f-stop) in scene units, a perspective one's lens / (2 · f-stop). [S]
- **A slanted (oblique) orthographic camera.** Cycles takes a camera's world matrix and only normalises its three axes (`transform_clear_scale`), so a third axis that is not perpendicular to the first two makes the rays travel slanted through the picture: an oblique parallel projection. Blender stores an object's own matrix as location, rotation and scale, which cannot hold a slant (`matrix_world` decomposes); the parent inverse matrix can. The bridge hangs such a camera from an empty at the origin, puts the matrix into `matrix_parent_inverse` and sets the camera's own matrix to the identity. Measured: a 1 m pole under a camera looking down with rays slanted by 45° is drawn 17 pixels long at 16 pixels per metre (1.1 m with its depth), 2 wide, in Cycles; 18 in Eevee, so Eevee keeps the slant too. Cinema 4D's four oblique views match the Standard renderer this way.
- **An orthographic camera sees nothing behind its `clip_start`** (minimum 1e-6 in Blender; the plugin sends at least 1 mm, next point). Where Cinema 4D clips nothing, the plugin moves the camera back along its rays instead (`docs/reference/c4d-sdk.md`, "Cameras and views").
- **Eevee shows no light at all with too wide a clip range** (0.2.0, B10) [T: c4dpy 2027 with Blender 5.0.0, 5.2.3 and 5.3.0 alike, final frames; `tests/c4d/editor_camera.py`]. A ball on a floor under one point light, through a perspective camera, Eevee: lit (mean 0.581) with Blender's defaults; nothing but the world's colour (0.041: neither the light nor anything it lights) once `clip_end / clip_start` exceeds about 10^7 (3e-4 m to 10 km, 1e-5 m to 1 km, 1e-6 m to 100 m; 1e-3 m to 10 km and 1e-4 m to 1 km still light). Below that a very small `clip_start` makes the light too bright (1e-4 m: +4 %, 1e-5 m to 100 m: +40 %); from 1 mm and within 10^6 the picture is Blender's default one within 0.4 %. Cycles renders the same at every range. The same holds for the viewport's own view (`region_3d.clip_start`/`clip_end` through `view_camera`, the IPR). Cause of B10: the editor camera of Cinema 4D 2024 and 2026 reports near clipping on at a distance of 0, which the plugin sent as Blender's smallest `clip_start`, 1e-6 m, against its default `clip_end` of 10 km; 2027's editor camera reports it off. The plugin now sends a near clipping of 0 as its default start (1 cm) and keeps every start at 1 mm or more and at least `clip_end / 10^6` (`ClipRange` in `scene/camera_export.cpp`). Where in Eevee's code the range breaks the lights was not looked up.

## The Cycles Fog object

0.3.0, F5 (`scene/fog_export.cpp`; [T: `tests/c4d/fog_object.py`, Cinema 4D 2027, Blender 5.2.3, 2026-11-23] unless marked). A cube mesh whose material has a Principled Volume on the Material Output's Volume socket and nothing on Surface: the box has no surface in Cycles or Eevee (outside the box the white world stays 1.0 to the fourth decimal), and what is inside is fog.

- **Extinction is the density per metre** of the scene (a mesh's volume is in world units: Cycles' `object_volume_density` scales only a Volume object in object space, `intern/cycles/scene/object.cpp`). With Color and Absorption Color black the Principled Volume is a pure absorber of extinction = density (`svm_node_principled_volume`: scattering = colour x density, absorption = (1 - colour)(1 - sqrt(absorption colour)) x density). Through the 2 m of a box in front of a white world: density 0.25, 0.5, 1.0 left 0.6065, 0.3679, 0.1353 in Cycles (exp(-2d) to the fourth decimal), 0.6045, 0.3691, 0.1357 in Eevee (within 0.4 %, the blue channel up to 1.2 % lower).
- **Absorption Color** (0, 1, 1) on an absorber of density 1 absorbed red only: (0.1353, 1.0, 1.0) in both engines. **Color** (1, 0.2, 0.2), density 1, white world: Cycles (0.46, 0.20, 0.20), Eevee (0.99, 0.31, 0.30): both red, Eevee much brighter (its volume light is single scattering of the world probe; not compared further). **Emission** 1 on an absorber of density 0.5, black world: e / d (1 - exp(-2d)) = 1.2642 expected, Cycles 1.2643, Eevee 1.250.
- **The default density is 0.2, not Blender's 1.0.** With the Principled Volume's default colour (0.5 grey) in a 2 m box in front of a white world the centre keeps 0.80 at 0.2 (0.90 at 0.1, 0.71 at 0.3, 0.55 at 0.5) and 0.30 at 1.0: Blender's default is a grey block at Cinema 4D's scale of a few metres, 0.2 reads as fog. (An absorber of 0.2 would keep exp(-0.4) = 0.67; the scattered world light brings it to 0.80.)
- **Shape and place:** a dense fog box (density 40) of 160 x 120 x 200 moved, turned (35°, 20°, 10°) and scaled (1.4, 0.7, 1.0) covers the pixels of a Cube of the same size and matrix rendered by Cinema 4D's Standard renderer: overlap 0.983 in Cycles, 0.959 in Eevee, centres 0.5 px apart.
- **With a noise** the fog is a `volume` item (a .vdb file of one grid "density", `render.space = 'WORLD'` as for every volume of the plugin) whose material reads "density" times the Density. A noise of 1 everywhere renders as the plain fog: 0.368 for density 0.5 through 2 m (Cycles), 0.369 (Eevee); the box against the Standard renderer's Cube 0.980 and 0.952. A pure absorber with a parallel camera against exp(-optical depth) summed from Python's `C4DNoise` along each ray (FBM, 2 octaves, scale 80, clips 0.3 and 0.7, density 1, 96 cells), the rays whose 5 x 5 pixels lie inside the box's sides: correlation of the transmittance 0.9997 (Cycles, 128 samples) and 0.9999 (Eevee) from the front and from the side, the mean within 0.3 % (0.3917 and 0.3929 against 0.3920); the same noise mirrored along the depth gives 0.47 from the side, one standing still along it 0.72 and 0.59; a slice 4 units deep in Eevee 0.9997, its mean 3.9 % brighter (two cells deep, the fade over half a cell at its faces is half the slab). Summed from the file's cells with trilinear interpolation instead of the noise itself: also 0.9997; the comparison shifted by half a cell or one pixel: 0.998 to 0.999, so there is no half-cell offset. Before the rays at the sides were left out the correlation was 0.81 to 0.88 and the mean 4 to 10 % off: a mean over pixels on both sides of a face is no transmittance of one ray. Eevee's default volume resolution (cells of 8 pixels) blurred the noise to a correlation of 0.70 on the front view with those rays included (at one pixel and 256 steps, the numbers above). Cycles renders a dense slab two cells thin with speckles (rays that pass as if it were not there), so the slice is compared in Eevee only.
- **Blender 5.0 and 5.1:** the noise's file is written by Cinema 4D, and Cinema 4D 2027 writes format 225, which their Cycles renders empty (Version coupling, above): a fog with a noise renders nothing there in Cycles and the console says so; Eevee shows it. The same holds for a fog with a texture (the same file) [untested on 5.0 and 5.1].
- **With a texture** (0.3.0, F11 step 2) [T: `fog_object.py` part 8, 2026-11-24]: the same `volume` item and material; each voxel is the shader's value there (times the noise when it is on). A pure absorber of density 1 in a 2 m cube with a Gradient "2D - V" from white (bottom) to black (top), a parallel camera from the front, 64 voxels: the transmittance along the height follows exp(-2 x the gradient's value at that height) within 0.0016 in Cycles (128 samples) and 0.0037 in Eevee (one-pixel volume cells, 256 steps): 0.15 at the bottom, 0.89 near the top.
- **What the grid costs** [T: `fog_object.py` part 8 with `{"costs": "64,128,256,512"}`, Cinema 4D 2027.0.0, Blender 5.2.3, 2026-11-24; a cube of 2 m, every voxel with fog; the noise FBM with 3 octaves, the texture a Gradient; made on a render thread of a final render; the IPR makes it on the main thread in the same time, `internal/f11/probe_fog_ipr_cost.py`]:

  | Voxels | Noise: sample + save, file | Texture: sample + save, file | Both | Final frame (320 x 180, 1 sample) |
  |---|---|---|---|---|
  | 64 (262,144) | 6 + 14 ms, 0.9 MB | 2 + 16 ms, 0.2 MB | 8 + 14 ms, 0.9 MB | 1.8 s |
  | 128 (2.1 million) | 30 + 79 ms, 7.2 MB | 11 + 55 ms, 1.7 MB | 36 + 72 ms, 7.2 MB | 1.9 s |
  | 256 (16.8 million) | 134 + 514 ms, 54 MB | 52 + 415 ms, 13 MB | 170 + 539 ms, 55 MB | 2.4 to 2.7 s |
  | 512 (134 million) | 713 + 4126 ms, 403 MB | 280 + 3306 ms, 103 MB | 881 + 4111 ms, 410 MB | 6.3 to 7.9 s |

  Saving costs more than sampling at every resolution (`GridAccessorRef::SetValue` per voxel and the file), and the time and memory grow with the cube of the resolution. A smooth gradient compresses four times better than a noise. **In the IPR** every change that alters the grid (a value of the Noise tab, the texture's settings, the size, the resolution) makes it again on Cinema 4D's main thread, and a fog with a grid is written by whole exports only, so each step of a drag of such a value holds the main thread for as long: from the step to the next picture 0.69 s at 64 voxels, 0.75 s at 128, 1.3 s at 256, 5.9 s at 512 (a noise's seed changed in a step and at the change event; a change of the Density keeps the grid: 0.66 s at every resolution, which is Blender's frame). **Voxel size instead of a count** was considered: a size in scene units keeps a fog's detail when the box is resized, but makes a box made larger cost the cube of it without the user touching the setting; the count keeps the cost fixed, so the count stays (the maintainer may want it otherwise).

## Linked files (the Cycles Proxy)

0.3.0, F7 (`bridge/c4d_bridge/scene/proxies.py`). [T: `prototypes/proxy_check.py` on Blender 5.0.0, 5.1.2, 5.2.3 and 5.3.0, in a background Blender set up as the bridge sets it up (start-up scene emptied, working space switched to ACEScg without converting colours); `tests/bridge/test_proxy.py` on 5.0.0 and 5.2.3, final frames and a rendering viewport; 2026-11-23] unless marked. The test file is made by `tests/bridge/make_proxy_blend.py`: 7 objects, 6 meshes, 5 materials, one image, one light, one action, 3 collections, a world. The four versions gave the same answer to every point; nothing version-specific was found in the 5.2.3 source or the manuals of 5.0 to 5.3.

- **Linking** is `with bpy.data.libraries.load(path, link=True) as (source, target): target.collections = [name]` (or `target.scenes`); `source.scenes` and `source.collections` list the file's names without loading anything. The small file linked in 3.6 to 4.5 ms; everything a collection or scene uses comes with it (objects, meshes, materials, images, actions; with a scene also its world, which nothing then uses). Linked images keep their path relative to the library (`//proxy_texture.png`, resolved with `bpy.path.abspath(path, library=...)`) and their colour space.
- **A proxy is a collection instance:** an empty with `instance_type = 'COLLECTION'` and `instance_collection` the linked collection, placed by its `matrix_world`. Making two took 0.02 to 0.03 ms. Two proxies of one file: one library, and the count of linked datablocks stayed the same. **Linking the same file a second time** (2.8 to 3.1 ms) made no second library and no second copy of anything: the data of a file is in memory once however often it is asked for. In the final driver and in a rendering viewport alike: the instance appears, moves with the empty's matrix and goes when the empty is removed (pixels at the expected places to the pixel, a turned and half-size copy included).
- **A scene's own collection can be instanced** (`empty.instance_collection = scene.collection` is accepted), but an instance shows everything in a collection: a child collection the file's view layer excludes shows too (measured: an instance of a collection listed the object of its excluded child). So the bridge shows a scene through collections it makes itself, which hold the linked objects and collections the first view layer does not exclude (`_wrap`); linked data can be put into a local collection. An object with its render dot off does not render in an instance (Cycles, final frame: 0.0 where it stands; Eevee not looked at). Not looked at: a file's other view layers, and a collection hidden for renders inside a collection that is instanced whole.
- **Freeing.** `bpy.data.libraries.remove(library)` (or `bpy.data.batch_remove`) removes the library with everything linked from it, in 0.03 ms for the test file; an empty that instanced one of its collections is left with none. Nothing stays behind: no linked datablock, no orphan mesh, material, image, action, collection or world; twenty rounds of linking and freeing left nothing. Removing the linked objects, meshes, materials, images, collections and so on one kind at a time, as `Scene.clear()` did before, leaves the library and the linked scene in the file. So `clear()` frees the libraries first, removing a proxy frees its file when no other proxy shows it, and a path changed to another file frees the old one. The reply of every `scene` request counts the libraries left (`libraries`), which is what the test checks: 1 with two proxies of one file, 1 after removing one of them, 0 after removing both, [2, 0] in each of five rounds of two files and a clear, 0 after "Stop" in the viewport.
- **A file that changed on disk is not noticed,** and linking it again while its library exists gives the old data (a block made 2 m wide stayed 1 m). `library.reload()` reads it anew (3.5 to 4.3 ms; the instances keep their collections), and so does removing the library and linking again. The bridge does the second (it also rebuilds the collections it made around the linked ones): the `proxy` item carries a `stamp`, for which the plugin sends the file's date, and another stamp than the file was linked with links it anew for every proxy that shows it (tested: of two proxies only one was sent with the new stamp, both showed the new file; with the old stamp the old data stayed).
- **Colours: Blender converts what it links.** Linking runs `IMB_colormanagement_working_space_convert` on the newly linked data (`source/blender/blenloader/intern/readfile.cc`, at the end of library linking; the same function a file gets when it is opened in another working space) [S]. Measured: an emission colour stored as (0.8, 0.2, 0.1) in a file whose working space is Blender's default, Linear Rec.709, read (0.56312, 0.24077, 0.12539) after linking into the ACEScg scene, which is Rec.709 to ACEScg by the matrix to the fifth decimal, and rendered so (0.5631, 0.2408, 0.1254 in Cycles, 0.563, 0.2407, 0.1254 in Eevee and in the viewport). An sRGB image texture of one colour (0.2, 0.4, 0.8 as stored) rendered (0.094, 0.1321, 0.54): sRGB to linear to ACEScg. So against the same file rendered in Blender's own default set-up the colours of a linked file are the same colours, written in the scene's space: no difference to correct, and the plugin adds no conversion. What Blender's conversion does not reach is Blender's own limit (it converts stored colours: material, light and world colours, colour attributes; values a node computes are in whatever space the nodes assume).
- **The conversion happens only when linking.** `bpy.ops.wm.set_working_color_space(convert_colors=False)`, which the bridge uses for the document's render space, leaves linked data as it was: after a switch from ACEScg to Linear Rec.709 the linked colour still read the ACEScg numbers (wrong by exactly the conversion), and (0.8, 0.2, 0.1) after `library.reload()`. The bridge therefore links every file again when a `settings` request changed the working space (tested both ways: (0.8, 0.2, 0.1) in Linear Rec.709, (0.5631, 0.2408, 0.1254) back in ACEScg).
- **Units and axes** are Blender's on both sides of the link: the instance's matrix places the file's origin and axes, and a scale in it scales the file. The plugin sends the object's matrix as a mesh's object has it (`Coords::ObjectMatrix`), so one metre of the file is one metre of the Cinema 4D scene along the object's axes and the file's Z is the object's Y (`tests/c4d/proxy_object.py`: against the same boxes built in Cinema 4D, numbers in `docs/reference/c4d-sdk.md`).
- **Animation plays by the scene's frame.** A linked object keyed from x = -2 at frame 1 to x = 2 at frame 11 stood at -2, 0, 2, 2 at the scene's frames 1, 6, 11, 16 and at -1 at frame 3.5 (`frame_set(3, subframe=0.5)`). There is one frame for the whole scene, so there is no frame offset per proxy: the bridge sets the scene's frame to the proxies' `frame` before it builds a request's items, and says so when they differ. Two things had to follow. Objects the bridge keyed for motion blur (`common.place`: three keys around the frame) are moved along, key by key, when the frame changes (tested: the streak of a blurred box before and after a proxy moved the frame from 1 to 40, five positions, equal to the third decimal). And in a rendering viewport a proxy linked at another frame than the file was saved at showed its animated object at the file's saved place until the frame was set again, so the bridge sets the frame once more after the items are built (found by the test; a final render evaluates the frame by itself). [I] The file's own animation gets Blender's motion blur over the bridge's fixed shutter of two frames, whatever the plugin's shutter is; not measured.
- **The file's lights light the scene, in both engines.** A point light of 200 W in the linked collection, 1.5 m above a white diffuse square: 2.28 in Cycles and 2.25 in Eevee (expected 200 / (4 pi^2 x 1.5^2) = 2.25). To leave the lights out the bridge instances a collection of its own that holds the linked objects but the lights (the square then showed 0.018: the glow of the emissive boxes beside it). **The file's world is not taken:** it is linked with a scene and used by nothing (the background stayed black, 0.0, around a file whose world is green).
- **Many copies** (`matrices`) are a mesh of loose points with a matrix attribute and a Geometry Nodes modifier: Collection Info (the whole collection as one instance, `transform_space` 'ORIGINAL', its default) on Instance on Points, then Set Instance Transform, as `instancers.py` does for a mesh. Three copies, one of them turned and one half size, rendered at their places. Geometry Nodes instances carry geometry only: the file's lights are not copied, which the bridge says in a warning when the file has lights and they were asked for.
- **Ray visibility of the empty counts for what it instances** in Cycles (`intern/cycles/blender/object.cpp`: an instance's visibility is its own and its instancer's; the holdout and the shadow catcher are the instancer's too, and light linking takes the instancer) [S]; a proxy with camera visibility off rendered 0.0 where its box was [T]. Eevee and the other switches: not measured.
- **Linked data is not protected from Python:** `bpy.data.objects["Block"].location.x = 5.0` on a linked object was accepted (in memory only). The bridge writes nothing into linked data.
- **`blend_info`** links the file's scenes and collections, measures each as a proxy of it would show it (the box around the evaluated instances of an empty that instances it: `depsgraph.object_instances`, each object's `bound_box` by its `matrix_world`, objects with a size only, render dot on) and frees the file again: 0.02 s for the test file in a Blender that is running; the plugin's "Read File" starts a Blender for it, which is what takes its 1.7 s. Linking tells neither which scene was open when the file was saved nor which view layer is used, so "the file's scene" is its first scene by name and its first view layer.

The file also holds groups that calculate with vectors and frames (Combine and Separate Cylindrical and Spherical, Retime; from 5.2 3D to Screen Space, Screen to 3D Space, Project with Depth, Transform and Project): no effects, left out. Nothing a version has is gone from a later one. The full list with every identifier, default and range is generated into `plugin/cyclesrender/source/tags/imager_effects_table.h` by `tools/make_effects.py`, which asks each Blender.

- **Reaching them from a script:** `with bpy.data.libraries.load(path, link=False, assets_only=True) as (source, target): target.node_groups = [name]` appends one group with the groups it uses (Vignette brings "Rounded Square Mask"); all groups of the file append in 18 ms (5.0) to 55 ms (5.3). It works in a background Blender and with `--offline-mode`. An appended asset keeps itself alive (a fake user): `group.asset_clear()` and `use_fake_user = False` make it go when nothing uses it.
- **Identifiers:** the inputs are `Socket_<n>`, the number being Blender's own and unique within the group; the names are not unique (Bloom has two inputs called Kernel). The same identifiers in every version that has the effect.
- **A menu input's options** are not readable as a property (the enum is dynamic and lists nothing): assigning an option that does not exist raises `TypeError: ... enum "x" not found in ('Offset', 'Scale', ...)`, and the generator reads the options from that message.
- **Which inputs a menu's choice uses** (Bloom's Streaks only for the type Streaks) is not in the table: every setting is shown. Not looked into.

**How the tree is attached.** The same in 5.0 to 5.3: `scene.compositing_node_group = <a node group of type CompositorNodeTree>` and `scene.render.use_compositing` (true in a new scene; `scene.node_tree` is gone, `scene.use_nodes` still exists and is not needed). The tree's output is a `NodeGroupOutput` fed through an output socket of the tree's interface (`tree.interface.new_socket("Image", in_out="OUTPUT", socket_type="NodeSocketColor")`); the render comes from a `CompositorNodeRLayers`. No difference between the versions was found, so the bridge has no feature test here. Old node types are gone: `CompositorNodeGamma` and `CompositorNodeMixRGB` do not exist, the compositor uses `ShaderNodeGamma` and `ShaderNodeMix`; the Exposure node's amount is an input socket.

**A chain with a mix per layer.** Per effect a `ShaderNodeMix` (`data_type = 'RGBA'`, `blend_type = 'MIX'`) with A what came before, B the effect's output and Factor the opacity. Measured on a world of the colour (0.8, 0.2, 0.1): Exposure 1 gives (1.6, 0.4, 0.2), at factor 0.5 (1.2, 0.3, 0.15), at 0 the render; Gamma 2 then Exposure 1 gives 2x², Exposure then Gamma 4x², so the order is the chain's. The Mix keeps A's alpha: an effect never changes the picture's alpha (not measured with a transparent film). The plugin applies the list's bottom layer first and its top layer last, as Cinema 4D's field lists do.

**Final frames** (a background Blender):

- The composite is **not** in what Cycles hands out in memory: `render_frame_finish` and the render result's passes hold the render before the compositor, in every version. `bpy.data.images['Render Result'].pixels` is empty, and the "Viewer Node" image is not filled in the background (it stays 256 x 256).
- The composite is in the file Blender writes: `render.render(write_still=True)` into a float EXR (the linear colour space set to the working space, as the Eevee route already does) holds the composite, exactly (Exposure 1: 1.6, 0.4, 0.2). A multilayer EXR holds two parts, `Composite.Combined` and `ViewLayer.Combined` (and the view layer's other passes), so the render before the compositor is there as well.
- So with a tree the final driver renders Cycles with `write_still` into a single-layer EXR and reads it back for the picture, while the passes still come from memory; Eevee goes through its file as always, the picture taken from the `Composite` layer when there are passes.
- **What it costs** (Blender 5.2.3, Cycles, 16 samples, the probe's scene; medians of three): 320 x 180: 7 ms in memory, 9 + 7 ms written and read; 960 x 540: 58 ms against 66 + 13 ms (**21 ms more**); 1920 x 1080: 239 ms against 254 + 31 ms (**46 ms more**, the file is 33 MB). The compositing itself adds 2 to 6 ms at 960 x 540 for Exposure, Sepia and Vignette and 21 ms for Tune Image (100 ms at 1920 x 1080, on the CPU). Eevee pays nothing new: it writes and reads a file anyway.
- **CPU and GPU compositor** (`render.compositor_device`; a new scene has CPU in 5.0 and 5.1 and GPU in 5.2 and 5.3) give the same pixels to the fifth decimal (Tune Image: 0.20907 against 0.20906) and work in a background Blender; the bridge leaves the device as Blender has it.
- A render region (`use_border`) composites the region and leaves the rest black.

**The IPR** (a hidden Rendered viewport, read in a `POST_VIEW` draw handler before the view transform, "Reading viewport pixels"):

- `space.shading.use_compositor = 'ALWAYS'` switches the viewport's compositor on (`'DISABLED'` off; `'CAMERA'` only while looking through a camera). **Its result is in what the handler reads**, for Cycles and for Eevee, in all four versions: Exposure 1 reads (1.5996, 0.3999, 0.1999). With `'ALWAYS'` the viewport's own view (`view_perspective = 'PERSP'`, the plugin's fast way to move a camera) is composited too; with `'CAMERA'` it is not. So the place the IPR reads today is the right one.
- **What it costs per frame** (960 x 540, the redraw with the read-back, median of 30 forced redraws): 4.0 to 4.7 ms without a tree and with `'ALWAYS'` and no tree; 3.7 to 4.7 ms with Exposure, 4.9 to 5.4 ms with Vignette, 4.8 to 5.1 ms with Sepia, 5.6 to 6.9 ms with Tune Image, 6.2 to 7.0 ms with Sepia and Vignette. So one or two of the presets cost **up to 3 ms per published frame**, against 33 ms between frames. Not measured: larger pictures, Bloom, Film Grain, weaker graphics cards.
- `render.compositor_device` makes no difference in the viewport (the same pixels and times with CPU and GPU: the viewport's compositor runs on the graphics card either way [I]).
- **A value set on a node of the attached tree does not start the render over:** Cycles stayed at "Rendering Done" and the next redraw showed the new picture. **Another tree attached starts it over** in most cases but not always (Cycles sometimes stayed at "Rendering Done"), and Eevee's samples are counted by its redraws; the bridge therefore calls `scene.update_tag()` after it attaches or removes a tree, and only redraws after it set values.
- **Half floats.** With `render.compositor_precision = 'AUTO'` (a new scene) the viewport's compositor calculates with half floats and the final frame's with whole ones: Tune Image read 0.2078 in the viewport against 0.2091 in the final frame at the same size (0.6 % off, 1 % beside the centre), Vignette's untouched centre 0.2003 against 0.2. With `'FULL'` the viewport reads 0.2089 (0.1 % off, the half-float texture it is read from) at the same cost. The bridge sets `'FULL'` while a tree is attached and puts the scene's own value back when it is removed.
- **A single pass** (`view_pass`): the viewport's compositor would treat the pass as the picture; the bridge switches it off while another pass than the combined one is shown.

**Colour.** The compositor works on the scene's working-space values in both drivers. Measured in ACEScg through the bridge (`tests/bridge/test_compositor.py`, 320 x 180, the whole picture's mean absolute difference between the viewport's frame and the final frame, relative): Sepia 0.0004 (Cycles) and 0.0003 (Eevee); Vignette then Tune Image 0.0008 in both; the viewport's own view 0.0008. The colours inside an appended group (Split Toning's two defaults) are converted by Blender when it appends [I, as for linked files; not measured]. A colour the plugin sends is the document's render-space colour, as a light's.

**Exposure** (0.3.0, F13 W6: the Cycles Camera tag's Color tab, the Imager layer "Exposure" and a Redshift camera's exposure). Measured on 5.0.0, 5.2.3 and 5.3.0 in a background Blender set up as the final driver, Cycles and Eevee (`internal/f13/probe_exposure_blender.py`, the F10 probe scene in ACEScg); the end to end checks are `tests/c4d/camera_exposure.py` and `tests/c4d/redshift_camera.py` [T]. The candidates:

- **The compositor's Exposure node** (`CompositorNodeExposure`, inputs `Image` and `Exposure`, output `Image`, the same in 5.0 to 5.3): the composite is 2^stops times the render to float precision in both engines (+1 2.0000, -1 0.5000, +10 1024.0002). Blender declares the input from -10 to 10, but its property reports no limit (hard ±3.4e38, soft ±10000) and the node takes any value: 12 set from Python reads 12 and gives 4096.0007 (also when fed by a linked `ShaderNodeValue`; `CompositorNodeValue` does not exist in 5.x). It acts where every Imager effect acts, on the working-space values before the view, so in the IPR's frame and in the final frame alike (above). The passes stay as rendered (`test_compositor`, `<engine>_passes_uncomposited`, an Exposure node: Environment and Combined asked as a pass unchanged while the picture doubles), and the file Blender writes itself (F6) holds the composite as its `Combined` and its other passes as rendered (`test_files`, case 5).
- **Cycles' Film Exposure** (`scene.cycles.film_exposure`, a plain factor, the Render Settings' own "Exposure"): 2 doubles Combined and the light passes read in memory (Environment 0.8 to 1.6 measured; by Cycles' `PassInfo::use_exposure`, `intern/cycles/scene/pass.cpp` [S], also Emission and the diffuse, glossy, transmission and volume light passes) and leaves the data passes (Normal, Depth: measured). **Eevee has none** (`scene.eevee` has no exposure property in 5.0 to 5.3; `eevee_film.cc` reads `view_settings.exposure` only to weigh its filter).
- **The view's Exposure** (`view_settings.exposure`, limits -32 to 32, a slider from -10 to 10 by 0.01): not in what the plugin gets: the float EXR Blender writes is unchanged at 1 stop in both engines, and the viewport's render texture is read before the view (above, "Reading viewport pixels").
- **A factor applied outside Blender** (numpy on the picture): 2.3 ms at 960 x 540 and 9 to 15 ms at 1920 x 1080 on 5.2 and 5.3 (8 and 25 ms on 5.0), where the compositor's route costs a final Cycles frame 21 and 46 ms (the file written and read, above). But Blender's own file (F6) would not get it, and the IPR's frames would need it too.

**Chosen:** the Exposure node for all three, the camera's exposure (the Color tab plus a Redshift camera's, in stops) as the tree's first node and the layer as an effect of the chain. One mechanism in both engines, final frames and the IPR; the two user controls give the same pixels (difference 0.0 in `camera_exposure`, Cycles and Eevee, final frames and IPR) and treat the passes and Blender's file alike; a changed value is a value on the tree and the IPR's render goes on (measured: one request, the compositor alone). Film Exposure was left out because Eevee has none (one control would then act in one engine only, and on passes in one engine only) and because it is the Render Settings' own setting; the factor outside Blender because Blender's file would lack it. The first node is there at 0 stops too while the tree exists (a layer, or an exposure), so that moving the exposure off 0 with layers present is a value and not a new tree; without layers, exposure 0 sends no tree and the frame is read as before, and the first exposure attaches one (the IPR's render starts over once). What it costs: a Cycles final frame with only an exposure goes through the compositor's file route (21 ms more at 960 x 540, 46 ms at 1920 x 1080); the IPR pays nothing measurable (Exposure alone 3.7 to 4.7 ms per frame against 4.0 to 4.7 without a tree, above).

**Effects the plugin builds of several nodes** (0.3.0, F13: the layer source "built", `scene/imager_built.cpp`; their settings are in the generated table like every other effect's, `tools/make_effects.py`, `BUILT_EFFECTS`). Every node they use exists with the same sockets in 5.0 and 5.3 (dumped 2026-11-25; the generator stops when a version lacks one): `CompositorNodeFilter` (inputs `Image`, `Fac`, the menu `Type`: Soften, Box Sharpen, Diamond Sharpen, Laplace, Sobel, Prewitt, Kirsch, Shadow), `CompositorNodeDilateErode` (`Mask`, `Size`, `Type`), `CompositorNodeGlare` (the same sockets in 5.0 to 5.3: `Type` Bloom, Ghosts, Streaks, Fog Glow, Simple Star, Sun Beams, Kernel; `Highlights Threshold`, `Strength` limited to 0 to 1, `Size`, `Streaks`, `Iterations`, `Fade` ...), `CompositorNodeSeparateColor` and `CombineColor`, `CompositorNodeRGBToBW`, and the shader nodes the compositor takes (`ShaderNodeMath`, `ShaderNodeVectorMath`, `ShaderNodeMapRange`, `ShaderNodeMix`; a Mix with `clamp_factor` off extrapolates: factor 2 adds twice what B differs from A, used by "Lens Glare"). The Render Layers node has an output for a pass only while the pass is on in the view layer (a fresh scene's node has `Image` and `Alpha` only): the `compositor` item's `view_layer` switches them on first (protocol, "The compositor").

- **Edges** (Sobel, Prewitt, Kirsch or Laplace on the depth's logarithm, the normals or the logarithm of the picture's brightness; the threshold's 1 is a step of 10 % in distance, a crease of 30 degrees or 25 % in brightness). Measured with `tests/c4d/imager_edges.py` (a cube turned to show three faces glowing in one grey, 320 x 240) on 5.2.3 [T]: final frames, Cycles and Eevee alike, "Depth" lines the whole outline (895 pixels within 3 px of it, none inside), "Normal" also the two inner creases (355 pixels inside in Cycles, 304 in Eevee), "Picture" the outline only; a threshold of 8 drops the 90-degree creases; Width 2 makes 2678 line pixels of 895; Strength 0.5 is halfway to the colour. **The IPR, measured in the real IPR** (the plugin's, with the Edges layer on the Depth and the Normal pass and the Cycles fallback switched off for the measurement): with **Cycles no line at all** (0 line pixels with either pass: Blender's viewport gives Cycles' compositor no passes; the outputs are empty, as `compositor_engine.cc` reads [S]); with **Eevee the same lines as its final frame** (895 outline pixels with the depth; 305 crease pixels with the normals, final 304). So the plugin draws the picture's edges in a Cycles IPR, says so once in the console, and sends no `view_layer` for it (then 982 outline pixels, no crease: the creases are not in the picture). Not measured: other Blender versions than 5.2 for the IPR, Cryptomatte or index passes as sources, the cost per frame.
- **Tone Mapping, White Balance, Lens Vignetting**: Redshift's camera tone mapping and white point as measured (`docs/reference/c4d-sdk.md`, "The Redshift camera's effects"); built of Mix, Math, Separate and Combine Color nodes, exact against Redshift to 0.05 % (tone mapping, 32 cases) and 0.04 % (white point) [T, `tests/c4d/redshift_effects.py`]. They calculate in the working space: exact where it is Redshift's (ACEScg, an OCIO document); in a Basic document Cycles Render's working space is linear Rec.709 while Redshift's stays ACEScg, so a per-channel curve and the luminance weights act on other primaries there [untested; small for greys, larger for saturated highlights].
- **Lens Glare** (Blender's Glare node at Strength 1, plus Intensity times what it adds: Glare's own Strength stops at 1). Measured on Redshift's own picture of a bright patch (a Redshift area light seen by the camera, 128 and 256 px, its picture read from Redshift and fed to the Glare node in a background Blender; `internal/f13/probe_w7.py` and the fit scripts of the run): Bloom at Size 1 adds 0.72 (5.2, 128 px) to 0.82 (256 px) of the patch's light at threshold 1, 0.58 and 0.68 at 4, 0.42 and 0.50 at 8 (Blender's threshold takes light away); half of it within 7.6 px (128) and 12.6 px (256), nine tenths within 47.7 and 90 px; Size 0.5 to 0.9 give the same picture (the size is in steps). Streaks (5 iterations) add 0.74 (3 streaks) and 0.98 (4); Ghosts 0.83 (128) and 0.75 (256). 5.0 gives 3 % less bloom than 5.2 and 5.3, the same streaks and ghosts. On a uniform picture Bloom adds 1 − T/x of each pixel at Smoothness 0.1 (nothing below the threshold) and, at Smoothness 1, x/(4T) below 2T and 1 − T/x above (measured at 0.05 to 10 times the threshold, 5.2). **The 5.3 asset "Bloom" is a group around the same Glare node with the same sockets and limits** (the table), and gives the same picture to the bit (measured on 5.3.0: Bloom, Size 1, threshold 1, Quality Medium, on Redshift's patch picture: largest difference 0.0); so the plugin uses the Glare node in all four versions. Against Redshift: see the SDK reference.
- **A 3D LUT:** Blender 5.0 to 5.3 have no LUT node in the compositor (the node list of the 5.2.3 source, `source/blender/nodes/composite/nodes`, and the compositor pages of the four manuals: no node that reads a `.cube`). `CompositorNodeConvertColorSpace` converts only between the colour spaces of Blender's OCIO configuration, `CompositorNodeConvertToDisplay` applies the scene's view. What a LUT would take is in `docs/roadmap.md`, "Known limits".
- **Lens Vignetting** (cos(θ)^Strength, θ a pixel's angle to the axis from Blender's `CompositorNodeImageCoordinates` "Uniform" output: centred on the picture, the pixel centres, over half the longer side, in 5.0 to 5.3; `compositor/cached_resources/intern/image_coordinates.cc` [S]): Redshift's vignetting, exact against Redshift to 0.005 [T]. *Tried and dropped:* Blender's Vignette preset fitted to Redshift's falloff (Feather, Scale and Factor per value, fitted on 96 x 64 and 64 x 64 in a background Blender 5.2; within 0.011 to 0.023 of Redshift's pictures for vignetting 1 to 11.5 at 35 mm): Redshift's falloff follows the lens's angle of view, which the preset knows nothing of, and its Feather stops at 1 where Redshift's never flattens.

**Leaving nothing behind.** Removing the tree leaves the appended groups (they are data of their own): the bridge removes those nothing uses any more, again and again until none is left (a group only a removed group used). After `remove` and after a cleared scene `len(bpy.data.node_groups)` is what it was (0 in the tests, 4 with Sepia and Vignette attached).

## Files Blender writes (the Output tab's own files, Cryptomatte)

Measured on 2026-11-24 for F6 (0.3.0) with Blender 5.0.0, 5.1.2, 5.2.3 LTS and 5.3.0, Cycles and Eevee each, in a background Blender started as the bridge starts it, working space ACEScg (`prototypes/output_files_check.py`: three cubes with emission materials, two Geometry Nodes instances of a fourth, 320 x 180, 16 samples, CPU, medians of three renders after a warm-up). All eight runs agreed in everything but the times. The bridge's part is tested by `tests/bridge/test_files.py` (passed on all four versions, both engines). Everything here is [T] unless marked.

- **The picture does not change.** Cryptomatte (object, material and asset, 6 levels) and a Depth pass switched on for a file only: the picture as the plugin reads it (Cycles in memory, Eevee from its float EXR) is the same to the bit (largest difference 0.0) in all eight runs, also with the File Output node below in the tree, and the Depth pass the plugin takes is the same too. Cryptomatte costs a little: Cycles 74.5 ms against 76.7 ms (5.2; 2 to 4 ms in all four), Eevee 64.3 against 68.6 ms (2 to 9 ms).
- **Two ways to have Blender write the render it just made, without rendering twice:** (a) the render output, `render.render(write_still=True)` with `image_settings` a multilayer EXR: it holds *every* pass of the view layer (also "Noisy Image" when denoising is on, and the Picture Viewer's passes), as `ViewLayer.<pass>`; one file per render, which the Eevee route (`final/__init__.py`) and the compositor route of F10 already use for their own temporary file. (b) **A File Output node** (`CompositorNodeOutputFile`, multilayer EXR) in the compositor's tree, fed from the Render Layers node: it writes exactly the inputs it has, named as its items (`Combined.R`, `CryptoObject00.r`), during the same render, in background renders, also when Cycles' pixels are read in memory (the compositor runs after `render_frame_finish`). Both write the Cryptomatte metadata (`cryptomatte/<hash>/name`, `hash` `MurmurHash3_32`, `conversion` `uint32_to_float32`, `manifest`), and in both the file's picture equals the plugin's picture exactly (32-bit). The bridge uses (b): only it lets the file hold the passes chosen for it and not the others, and it leaves the render output free for the temporary files.
- **What the node costs** (32-bit, ZIP, the picture, Depth and nine Cryptomatte layers, 41 channels, 0.6 MB): Cycles 96.8 ms against 76.7 with Cryptomatte alone on 5.2 (5.0: 131.8 against 97.4, 5.1: 90.4 against 74.9, 5.3: 95.5 against 77.1); Eevee 83.5 against 68.6 (5.0 69.9/61.9, 5.1 74.2/62.4, 5.3 59.1/46.2). The render output's file of the same render (45 channels): Cycles 91 to 119 ms, Eevee 54 to 75 ms. So writing such a file costs 15 to 35 ms at this size, the same either way. Not measured at larger sizes.
- **The node's API is the same in 5.0 to 5.3:** `file_output_items.new(socket_type, name)` (`FLOAT`, `VECTOR`, `RGBA`), `directory`, `file_name`, `format` (`media_type` `MULTI_LAYER_IMAGE`, `file_format` `OPEN_EXR_MULTILAYER`, `color_depth`, `exr_codec`, `linear_colorspace_settings`), `save_as_render`; `use_file_extension` from 5.2 (before, the extension is always added). The EXR codecs: `NONE`, `ZIP`, `PIZ`, `DWAA`, `DWAB`, `ZIPS`, `RLE`, `PXR24`, `B44`, `B44A` in all four, `HTJ2K` from 5.1. A new node's format: 32-bit, codec `NONE`; the render output's multilayer EXR in a new scene: 32-bit, `ZIP` (the plugin's defaults are the render output's).
- **The Render Layers node's outputs** are named as the passes the plugin reads in memory ("Final frames in background mode"), except the picture, which is `Image` (and `Alpha`); Cryptomatte gives `CryptoObject00` to `02`, `CryptoMaterial00` to `02`, `CryptoAsset00` to `02` at 6 levels (two ranks per layer; `pass_cryptomatte_depth` 2 to 16, default 6). The same in 5.0 and 5.3 for both engines; Eevee has no UV, Object Index, Material Index, indirect, transmission, Shadow Catcher or Debug Sample Count output.
- **Half float** (`color_depth` `16`): only the colour layers are half; Cryptomatte (written with lowercase `rgba` channels), Depth, Normal and the other data layers stay full float (read back: `tests/bridge/test_files.py`; the rule in the source: `RE_RenderPassIsColor`, `compositor/intern/render_context.cc` [S]). So Cryptomatte's ids survive a half-float file.
- **Colour.** With the format's linear colour space set to the working space (the bridge does; a node made in an ACEScg scene already had it) the file holds the rendered values (the red cube 0.9959, as in memory) and says so: `colorInteropID` `lin_ap1_scene` on the picture and the light passes, `data` on Cryptomatte and data passes (5.0 writes no `oiio:ColorSpace`, 5.1 on do). The render output's file says the same.
- **Names in the manifest are Blender's names:** objects by their object's name, materials by the material's, assets by the topmost parent's; an instance of Geometry Nodes is listed under the *instanced* object ("Yellow Proto"), its instancer object is listed too (the asset manifest holds both). The bridge's objects are named by item ids, so without the items' `name` (protocol, "Files Blender writes") a manifest would list `object_1a2b…`. The bridge's objects have no parents, so an asset matte is an object matte; the plugin does not offer it.
- **File names.** A File Output node's file name goes through Blender's path templates and frame numbers even in a single render: "p {{x}} ## a.b" became "p {x} 07 a.b.exr" at frame 7 (braces doubled stand for one, "#" is the frame number, the extension is added), in all four versions. The render output's path in a still render keeps its "#" (`use_frames` is false for `write_still`, `render/intern/pipeline.cc` [S]). The bridge therefore lets the node write a name of its own into the folder (braces doubled) and moves the file to the path it was given (`final/files.py`).

## The curve nodes (`CurveMapping`)

RGB Curves (`ShaderNodeRGBCurve`), Vector Curves (`ShaderNodeVectorCurve`) and Float Curve (`ShaderNodeFloatCurve`) keep their curves in `node.mapping`, a `CurveMapping`. Built by `_set_mapping` in `bridge/c4d_bridge/scene/materials.py` [T: `tests/bridge/test_scene.py`, `check_curve_mapping`, in Cycles and Eevee; `tests/c4d/cycles_nodes.py`; and a measuring script, Blender 5.2.3, 2026-11-12].

- **A new node** [S: `node_shader_curves.cc`, `BKE_curvemapping_set_defaults` in `blenkernel/intern/colortools.cc`; T]: `mapping.curves` holds 4 curves for RGB Curves (R, G, B, then C, the combined one), 3 for Vector Curves (X, Y, Z), 1 for Float Curve; each two points with handle `AUTO` in the corners of the area, 0 to 1, or -1 to 1 for Vector Curves; the clipping rectangle is that area, `use_clip` is on and `extend` is `EXTRAPOLATED`.
- **Points:** `curve.points.new(x, y)` inserts a point where its x belongs, selected and with the curve's default handle; `curve.points.remove(point)` refuses to go below two points (`BKE_curvemap_remove_point`); `point.location`, `point.handle_type` (`AUTO`, `AUTO_CLAMPED`, `VECTOR`; a point has no tangents of its own), `point.select`. [S, T]
- **`mapping.update()`** (`BKE_curvemapping_changed_all`) sorts the points of each curve by x (stable) and builds its table; with `use_clip` on it first moves the **selected** points into the clipping rectangle, all by the same amount. So the bridge deselects every point before `update()`, and the plugin sends a rectangle around all its points. It removes no doubles (only Blender's editor asks for that). [S]
- **`clip_min_x`, `clip_min_y`, `clip_max_x`, `clip_max_y`** lie within -100 to 100, and each is bounded by its opposite (`clip_min_x` up to `clip_max_x`): set the outer limits first. [S: `rna_color.cc`]
- **How a curve is evaluated** [S]: the points become Bezier segments (handles from `AUTO`, `AUTO_CLAMPED` or `VECTOR`, `calchandle_curvemap`), drawn with 32 points each, then resampled into a table of 256 even steps over the clipping rectangle widened to the points (`curvemap_make_table`). `mapping.evaluate(curve, x)` (`BKE_curvemap_evaluateF`) reads that table, and outside it continues along the first or last handle (`EXTRAPOLATED`) or flat (`HORIZONTAL`); it does not clamp to the rectangle. Cycles samples `BKE_curvemap_evaluateF` again in 256 steps between the first and the last point of the curves (`curvemapping_float_to_array`, `curvemapping_color_to_array` in `intern/cycles/blender/util.h`) and continues the last step's slope when `extend` is `EXTRAPOLATED` (`float_ramp_lookup`, `kernel/svm/ramp.h`). RGB Curves apply C first, then R, G and B (`R(C(x))`).
- **Precision** [T]: `VECTOR` points give straight segments, so a curve sent as many points follows them exactly up to the table: a corner is rounded by up to a quarter step times the change of slope (0.0028 for slopes 2 and -1 over 0 to 1). Two points `(0, 0)` and `(1, 1)` with `VECTOR` handles evaluate exactly as a new node's two `AUTO` points (difference 0.0 at 1001 positions; the same for -1 to 1).
- **Constant inputs are folded with a clamp** [T: rendered, Cycles; S: `nodes/intern/shader_nodes_inline.cc`, `node_shader_curves.cc`]: Blender 5.2 evaluates a node whose inputs are all constants itself, with the node's multi-function, before Cycles sees the material. Float Curve's multi-function calls `BKE_curvemapping_evaluateF`, which clamps the result to the clipping rectangle while `use_clip` is on: a new Float Curve at a constant 1.5 renders 1.0, whatever `extend` says, although `evaluate()` gives 1.5 and Cycles' own table extends the line for an input that varies. RGB and Vector Curves' multi-functions do not clamp. The plugin sends Blender's rectangle for an untouched curve, so its renders keep this behaviour.
- **What shader nodes ignore** [S]: `tone`, `black_level` and `white_level` of RGB Curves (Cycles does not read them; Eevee passes black 0 and white 1, "Shader nodes don't do white balancing"). Vector Curves' `Vector` input is declared from -1 to 1.

## Devices

With `--factory-startup` no GPU device is enabled. On each launch [T: OptiX on an RTX 4090, viewport rendering, OpenGL and Vulkan back ends]:

```python
prefs = bpy.context.preferences.addons['cycles'].preferences
prefs.compute_device_type = 'OPTIX'      # or CUDA, HIP, ONEAPI, METAL, NONE
prefs.refresh_devices()
for d in prefs.devices: d.use = True
bpy.context.scene.cycles.device = 'GPU'
```

Setting `compute_device_type` to a back end the build lacks raises `TypeError`; try `OPTIX`, `CUDA`, `HIP`, `ONEAPI`, `METAL` in turn and keep the first that lists devices (`bridge/c4d_bridge/render/devices.py`).

- **The device list** [S: `intern/cycles/blender/addon/properties.py`; T: `tests/bridge/test_devices.py`]: `refresh_devices()` asks for the devices of every back end (CUDA, OptiX, HIP, Metal, oneAPI), whichever `compute_device_type` is, and adds an entry per device and type to `preferences.devices`: `name`, `type`, `id` (persistent: on this machine `CUDA_NVIDIA GeForce RTX 4090_0000:01:00` for CUDA, the same with `_OptiX` for OptiX, and `CPU`), `use` (new entries: on except the CPU). Blender's preferences show the devices of the chosen type and the CPU after them; a ticked CPU renders together with the GPU (`gpu_and_cpu`: both names in use). On this machine: OptiX and CUDA, one RTX 4090 each, and the CPU (i9-13900K).
- **The user's preferences are never written** [S: `creator_args.cc`, `arg_handle_factory_startup_set` sets `G_FLAG_USERPREF_NO_SAVE_ON_EXIT`; `wm_init_exit.cc` saves the preferences on exit only without that flag; T: `userpref.blend` of Blender 5.2 kept its date and its MD5 (78018406aead7792e26cc4e632ead6b6) through every test run of 2026-11-12, among them every device type]. The plugin starts Blender with `--factory-startup`, which also does not read them, and the bridge never calls `save_userpref`: device settings live in that Blender's memory only. Found on the way: a windowed Blender (the IPR's) still rewrites `config/recent-searches.txt` on exit (`wm_init_exit.cc`, `write_recent_searches_file` when not in the background), with the same content it read; its date changed during the tests. Not changed here.
- **HIP and the IPR** [S only, untested: no AMD card here]: the IPR reads Blender's viewport framebuffer after it is drawn (`gpu` module, `viewport/__init__.py`), whatever device rendered it. Cycles on HIP does not use graphics interop with OpenGL or Vulkan in 5.2.3 (`device/hip/device_impl.cpp`, `should_use_graphics_interop` returns false: a driver bug, Vulkan not implemented) and copies each frame through the CPU into the display texture instead, as CUDA does when interop is off; so the picture arrives the same way, perhaps a little later per frame.

- **What Cycles renders on is exactly what the bridge set** [S: `intern/cycles/blender/device.cpp`, `blender_device_info`; T: `tests/c4d/ipr_device.py`, 2026-11-17]: for a session it reads `scene.cycles.device` (GPU or CPU), the preferences' `compute_device_type` and the ticked `devices` that `Device::available_devices` lists for that type; with no ticked device of the type it falls back to the CPU device silently, which the bridge never leaves to it (it names every such case in the reply's `warnings`). `BlenderSync::get_session_params` compares the device and the thread count with the running session's at every sync and makes a new session when they differ, so switching the device in a running viewport switches the render (measured: Blender's CPU time over 1.5 s of an IPR render at 640 × 360: 1.1 cores on OptiX, 29.6 on the CPU with 30 threads, back to 1.1 on Automatic). The reply's `threads` is `render.threads`, whose getter returns `BKE_render_num_threads` (the fixed count, or `GetSystemInfo`'s logical processors). Up to 0.2.0 the IPR dropped the reply's warnings, so in the IPR a GPU render that fell back to the CPU said nothing (final frames said it).
- **A machine without a GPU** can be stood in for on an NVIDIA machine with `CUDA_VISIBLE_DEVICES=-1` in Blender's environment: CUDA and OptiX then list no device [T: `tests/bridge/test_frame_rate.py`, "AUTO" and "GPU" render on the CPU with a warning; `tests/c4d/ipr_device.py`, the variable set in Cinema 4D's own environment reaches the Blender the plugin starts: Automatic renders on the CPU, the console names it, the status line says "(no GPU found)"].

Alternatively pass `-- --cycles-device OPTIX` on the command line. [S]

`--gpu-backend vulkan` also works for both engines with the window hidden. [T]

## A material edited in Blender's Shader Editor

Measured for the Cycles Native Material, all [T: a prototype script, Blender 5.2.3, windowed with the main window hidden]; what the bridge does with it (`bridge/c4d_bridge/scene/native.py`) follows below, [T: `tests/bridge/test_native.py`, `tests/c4d/native_material.py`].

- **One material as bytes:** `bpy.data.libraries.write(path, {material}, fake_user=True, compress=True)` writes a .blend with that material and what it uses; `with bpy.data.libraries.load(path, link=False) as (source, target): target.materials = list(source.materials)` brings it back (`target.materials` then holds the datablocks; assigning the same list object to it replaces the names in that list, so copy it). A material of four nodes with a colour ramp: 63,594 bytes, 11 to 20 ms to write and read back from disk, 14 ms to load, identical afterwards (node types, links, ramp stops, values, `surface_render_method`).
- **A window with only the Shader Editor:** `with bpy.context.temp_override(window=main): bpy.ops.wm.window_new()`; the new window is `wm.windows[-1]`, has one area; `area.ui_type = "ShaderNodeTree"`. The editor shows the active material of the active object of the window's scene: give the window a scene of its own (`window.scene = scene`) with one object carrying the material and make it active (`window.view_layer.objects.active`). `space.edit_tree` is the material's node tree one tick later. The new window is visible although the main window was hidden with `ShowWindow(SW_HIDE)`.
- **Changes:** a `bpy.app.handlers.depsgraph_update_post` handler sees `Material:<name>` and `ShaderNodeTree:...` among `depsgraph.updates` within 1 ms of a changed socket value, a new node with a link, and a changed setting of the material; a moved colour-ramp stop and a moved node report the node tree only. Changes were made from a script; that edits by mouse take the same path is inferred, not seen.
- **Closing:** a WM_CLOSE to the editor window (what its close button sends) removes it from `wm.windows` and leaves Blender running, the main window still hidden, the material as edited. Blender quits only when its last window closes, and the hidden main window counts.
- **`wm.window_new` and `wm.window_new_main` refuse in the IPR's Blender:** their poll wants the active window's screen not to be maximised (`screen->state` normal, or not full), and the IPR's window shows one maximised area. `bpy.ops.screen.area_dupli("INVOKE_DEFAULT")` with `temp_override(window=main, area=..., region=...)` has no such condition and gives a second window with one area. Set its `ui_type` in the same call, before Blender draws: the duplicate of a Rendered viewport would start a render of its own otherwise.
- The editor window: `space.show_region_header = True`, `space.show_region_ui = False`; size, title and focus through Win32 on the new `GHOST_WindowClass` window of the process (`SetWindowPos`, `SetWindowTextW`, `SetForegroundWindow`).
- **A material's preview picture without blocking:** `with bpy.context.temp_override(id=material, window=window): bpy.ops.ed.lib_id_generate_preview()` starts Blender's preview job; some ticks later `material.preview.image_pixels_float` holds 128 x 128 RGBA, the ball over transparency (rows and columns 11 to 115). It renders with the engine of the window's scene: 0.3 s in Cycles, 7.7 s the first time in Eevee (shaders are compiled) [T: a prototype script]. Compare the pixels with the ones before asking to know when the new picture has come.
- **Working space:** a .blend carries its working colour space; `libraries.load` converts a material's colours into the working space of the file it is loaded into, so it looks the same. Setting the working space of a running Blender (`wm.set_working_color_space(convert_colors=False)`, as the bridge does) leaves existing values as they are: set it before a material is made or loaded [T: `native_material.py`, IPR and final render of one material agree to 0.001 only then].
- `bpy.data.libraries.write(..., path_remap="ABSOLUTE")` writes the paths of images as full paths, which another Blender reading the bytes from another folder needs [T: `tests/bridge/test_native.py`, a texture chosen in the editor renders elsewhere].
- A change notice is not the only way to know a material changed: a hash over its nodes (settings, socket values, links, what images, colour ramps and curves hold, node groups) compared twice a second catches whatever gives no notice (`_fingerprint` in `native.py`).
- `bpy.data.libraries.write` of the same material twice does not always give the same bytes; compare a hash only to skip what the bridge itself wrote.
- Datablocks an open editor shows must survive `Scene.clear()`: `bpy.data.batch_remove` gets the list without them (the material, the object and mesh that carry it, images and node groups its tree uses).
- **Undo (Ctrl+Z) in the editor window is Blender's global undo** [T: `tests/bridge/test_native.py`, and by simulated key presses]. It reads every datablock that changed anew: Python references to the material, its scene and its object go stale (`ReferenceError`), while `ID.session_uid` stays the same across undo and redo and finds them again; `bpy.app.handlers.undo_post` and `redo_post` are the moment to do it. Nothing made from Python is an undo step: without `bpy.ops.ed.undo_push()` after the editor is set up, the first Ctrl+Z returns to the state of the start-up file, where the material does not exist. Blender offers no way to cut the history off, so an undo beyond that step is answered with `bpy.ops.ed.redo()`.
- Simulated input for a test: start Blender with `--enable-event-simulate` and call `window.event_simulate(type, value, x=, y=, ctrl=)` from a timer, one event per tick; real input is ignored meanwhile. A node's sockets are found from `node.location` and `region.view2d.view_to_region` (first output 34 units below the node's top, each further row 22).
- A preview picture whose alpha is zero everywhere is what the buffer holds while the preview job runs, and also the finished picture of a material that shows nothing; only time tells them apart.
- `bpy.ops.screen.screenshot(filepath=...)` with `temp_override(window=window)` photographs one window of Blender, also when Blender did not start it from a key press.
