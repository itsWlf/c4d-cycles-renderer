# Cinema 4D SDK reference

Identifiers, build rules and example paths for the C++ plugin. Entries marked **[T]** were built or run in this project. Everything else was read in the 2027 SDK headers, manuals and examples and is untested; what differs in the SDKs of 2024, 2025 and 2026 is under [Cinema 4D versions](#cinema-4d-versions). Correct this file when work proves an entry wrong. The tests named as evidence (`tests/...`) are kept locally and are not part of the repository; see `docs/development.md`.

Path aliases:

- `SDK` = the Cinema 4D 2027 C++ SDK. It is not part of the repository; this project keeps its copy in `references/Cinema_4D_CPP_SDK_2027_0_0` (`docs/development.md` says where to get it).
- `CF` = `SDK/frameworks/cinema.framework/source`
- `DESC` = `CF/description`
- `PY` = the Cinema 4D 2027 Python SDK, kept likewise in `references/Cinema_4D_Python_SDK_2027_0_0`

## Build

**Build this project with `tools\build_plugin.ps1`** (`-Version 2024|2025|2026|2027|all`, `-Config Debug`, `-Reconfigure`, `-Sdk <folder>`). [T] For 2027, the default, it runs (the other versions: [Cinema 4D versions](#cinema-4d-versions)):

```
$env:PYTHONDONTWRITEBYTECODE = "1"
cmake -S references\Cinema_4D_CPP_SDK_2027_0_0 -B build\plugin -G "Visual Studio 18 2026" -T v143 `
      -A "x64,version=10.0.26100.0" "-DMAXON_SDK_MODULES_DIR=<repo>\plugin"
cmake --build build\plugin --config Release --target cyclesrender -- /m /nr:false /v:minimal
```

- The project is developed with Visual Studio Community 2026, MSVC 14.44 (toolset v143) and Windows SDK 10.0.26100.0; these are the build script's defaults. The SDK's preset `windows_vs2022_v143_x64` asks for the Visual Studio 2022 generator and Windows SDK 10.0.20348.0, so with another Visual Studio the generator, toolset and architecture are passed explicitly (parameters of the build script). [T]
- The unmodified SDK example `example.hello_world` built this way in 152 s with no warnings and loaded in Cinema 4D 2027.0.0. [T]
- The SDK is the CMake source tree; `-B` puts every output, including the source processor's generated files, in the build directory. Paths containing spaces work. [T]
- Without `PYTHONDONTWRITEBYTECODE=1` the SDK's source processor leaves `__pycache__` folders inside `SDK/tools/sourceprocessor`. [T]
- CMake ≥ 3.30, C++20. Presets: `SDK/CMakePresets.json`.
- The top-level `SDK/CMakeLists.txt` discovers every module under `MAXON_SDK_MODULES_DIR` (a cache path, default `SDK/plugins`).
- `SDK/cmake`, `SDK/frameworks` and `SDK/tools` stay unmodified.

**Test inside Cinema 4D with `tests\c4d\run_c4d_test.ps1`** [T]; how to use it is in `docs/development.md`. With `-Headless` it runs a script in `c4dpy.exe`; otherwise it starts the regular Cinema 4D with the harness plugin `tests\c4d\harness\cyclesrender_test_harness.pyp`, which runs the script once the application has started and quits. Cinema 4D's console goes to a log file through the `g_logFile` setting.

- Cinema 4D reads settings such as `g_additionalModulePath` (several paths separated by `;`) and `g_logFile` from environment variables as well as the command line; the full list is in `<C4D install>\resource\config.txt`. [T]
- `c4dpy.exe` and `Commandline.exe` need a licence of their own kind; licensed through the Maxon App they run without questions. [T] Both load the plugin from `g_additionalModulePath` and render with it: `c4dpy <script.py>` runs a script (it has its own preferences folder, so settings stored by the regular application are not visible to it), `Commandline.exe -nogui -render <file.c4d>` renders a saved scene with its saved render settings, including frame sequences.
- Module layout: `<module>/project/CMakeLists.txt`, `<module>/source/`, `<module>/res/`. Template to copy: `SDK/plugins/example.image/project/CMakeLists.txt`.
  - `target_settings` JSON lists `apis` (the frameworks whose headers the module may include), `"c4d": true`, `moduleid`, `"type": "DLL"`.
  - Likely `apis` here: `cinema.framework`, `core.framework`, `image.framework`, `image_ocio.framework`, `network.framework`, `exchange.framework`, `nodes.framework`, `nodespace.framework`, `graph.framework`, `volume.framework`, `asset.framework`.
  - `enable_rtti OFF`, `enable_exception_handling OFF`.
- Code rules: use the maxon types and error handling (`maxon::Result`, `iferr_scope`, `iferr_return`); the standard library is unsupported in SDK modules; lambdas capture `this` explicitly.
- Idioms that compile cleanly here, with the module's style check at level 3 [T]:
  - `Type value = Function() iferr_return;` inside a function that starts with `iferr_scope;`.
  - `iferr (Type value = Function()) return fallback;` — `value` stays usable afterwards.
  - `maxon::Result<T> r = Function(); if (r == maxon::OK) use(r.GetValue());` when an error must not propagate.
  - `iferr (Function()) { ApplicationOutput("… @", err); }` to log an error.
  - `return maxon::IllegalStateError(MAXON_SOURCE_LOCATION, "message"_s);` to raise one.
  - `MAXON_DISALLOW_COPY_AND_ASSIGN(Class);` for classes that own a process or socket; `std::move` to return or append move-only values such as `BaseArray`.
  - Tabs for indentation, braces on their own lines, `override` on virtual overrides, `///` comments on declarations.
- Description headers (`res/description/*.h`) and `c4d_symbols.h` are on the include path by bare name.
- Where a description id lives [T]: the SDK's description headers (`olight.h`, `ocamera.h`, `mmaterial.h`, …) declare plain global enums, so write `LIGHT_TYPE`, not `cinema::LIGHT_TYPE`. The exception is headers that `c4d.h` already includes inside its namespace, such as `ddoc.h`: write `cinema::DOCUMENT_DOCUNIT`. Type ids (`Olight`, `Mmaterial`, `Xbitmap`, `Ttexture`) and `ConstDescIDLevel`, `CreateDescID` are macros and take no namespace.
- `FormatString("@@-@", a, b, c)` fails to compile ("Argument mismatch" in `string.h`): `@@` is not two placeholders. Concatenate instead. The style check also rejects an `else` with braces after an `if` without them. `HashMap::Insert` returns the entry, not the value (`entry.GetValue()`). [T]
- Names the SDK claims as macros: a method called `Describe` does not compile. Enums need `MAXON_ENUM_LIST(NAME)` after the closing brace (`MAXON_ENUM_LIST_CLASS` inside a class). `iferr_return` inside an `if` needs braces. `static const Vector NAME(0.05);` is flagged as a badly named function: write `= Vector(0.05)`. A `for` with an empty condition (`for (Int i = 0;; ++i)`) warns "Style guide requires whitespace behind ;" in every version's style check: put the condition in. [T]
- `res/` layout (see `SDK/plugins/example.image/res/`): `c4d_symbols.h`, `description/<name>.res` + `.h`, `strings_en-US/description/<name>.str`, `strings_en-US/c4d_strings.str`.
- Entry points in `main.cpp`: `cinema::PluginStart()`, `PluginEnd()`, `PluginMessage()` (handle `C4DPL_INIT_SYS` with `g_resource.Init()`). Example: `SDK/plugins/example.image/source/main.cpp`.
- Output: `<build>/bin/<cfg>/plugins/<module>/<module>.xdl64`. Start C4D with `g_additionalModulePath=<build>/bin/<cfg>/plugins/` to load it.
- Classic API types live in namespace `cinema::`; headers keep their old names (`c4d.h`, `c4d_gui.h`) under `CF`.
- ABI: a module built with the 2026 SDK also loads in Cinema 4D 2027 (both have ABI 2026000); one built with the 2027 SDK does **not** load in 2026 (its core framework is newer). [T, 2026-11-16; an earlier line here said the opposite, unmeasured.] The rest: [Cinema 4D versions](#cinema-4d-versions).
- Manuals: `SDK/docs/manual_build_systems.html`, `manual_quickstart_win.html`, `page_requirements.html`, `manual_migrating_to_2027.html`.

## Cinema 4D versions

The plugin supports Cinema 4D 2024, 2025, 2026 and 2027 (since 0.2.0, F9). One source tree is built once per version, each against that version's SDK (`tools\build_plugin.ps1 -Version <year>`); what differs in the code is answered in one header, `plugin/cyclesrender/source/sdk_compat.h`. Measured on 2026-11-16 with Cinema 4D 2024.5.1, 2025.3.3, 2026.3.4 and 2027.0.0 and the SDKs of their `sdk.zip` (API_VERSION 2024500, 2025302, 2026300, 2027000).

**How Cinema 4D chooses among several builds in one folder** [T, each version started with a preferences folder of its own; c4dpy reporting `FindPlugin(1073816).GetFilename()`, the regular application's log, console and windows]. A module exports `g_maxon` (`core.framework/source/maxon/module.h`), whose first members are the ABI version and the core framework version it was built with (`apibase_version.h`):

| SDK | ABI | core framework | backward compatible to |
|---|---|---|---|
| 2024.5 | 2023904 | 2024501 | |
| 2025.3.2 | 2025000 | 2025303 | |
| 2026.3 | 2026000 | 2026200 | 2026100 |
| 2027.0 | 2026000 | 2027000 | 2026100 |

Cinema 4D refuses a binary of another ABI ("@ has wrong binary version @, expected @"), skips one whose core framework is newer than its own, and of several with the same module id that remain loads the best match ("Skipping module @ for better matching version @"). So no one binary loads in all four versions, but one folder holding all four builds works everywhere: with `cyclesrender_2024.xdl64` to `cyclesrender_2027.xdl64` and one `res` side by side, 2024 loaded `_2024`, 2025 `_2025`, 2026 `_2026` and 2027 `_2027`, each without a dialog and without a console line about the others. Only 2027 writes about them, into its log file, not the console: a `WARNING: Error loading ...: ... has wrong binary version 2023904, expected 2026000.` for the 2024 and 2025 builds and a "Skipping module" line for the 2026 build. A folder with only the 2027 build loads nothing in 2024 to 2026, silently; a folder with only the 2026 build loads it in 2027. `Commandline.exe` of every version prints the loader's lines on its standard output [T, the release folder of `make_release.ps1`, a scene rendered with Cycles Render in all four, 2026-11-16]: one `WARNING: Error loading ...: ... has wrong binary version <its ABI>, expected <own ABI>.` per build of another ABI (three in 2024 and 2025, two in 2026 and 2027), in 2026 also "Skipping module ...cyclesrender_2027.xdl64 because its core framework is newer than supported 2027000" (sic) and "... for better matching version ...cyclesrender_2026.xdl64", in 2027 "Skipping module ...cyclesrender_2026.xdl64 for better matching version ...cyclesrender_2027.xdl64". Each then rendered with its own build, and the four pictures agree (mean RGB equal to four digits; the largest 8 x 8 block differs by 0.19 on values of several hundred, 2027 against the other three). The install notes say these lines are expected. The file name of the binary does not matter, and every build finds `res` next to it. Not measured: whether an earlier update of a year (2026.0, say) refuses that year's build as newer.

**Build set-up per SDK** [T]:

| | 2024 | 2025 | 2026 | 2027 |
|---|---|---|---|---|
| CMake | none in the SDK (it came with Maxon's Project Tool); the 2025 SDK's CMake files on a copy of the 2024 SDK in `build\sdk\2024` | yes | yes | yes |
| module definition | `project/projectdefinition.txt` | the same | the same | `project/CMakeLists.txt` |
| C++ | 17 (the SDK's `Base.props`) | 20 | 20 | 20 |
| classic API namespace | none (global) | `cinema` | `cinema` | `cinema` |
| build folder | `build\plugin-2024` | `build\plugin-2025` | `build\plugin-2026` | `build\plugin` |

- The 2025 and 2026 SDKs read a module from `project/projectdefinition.txt` and take a `CMakeLists.txt` next to it as a ready-made replacement, so the repository's 2027 `CMakeLists.txt` cannot sit beside one. The build script writes `projectdefinition.txt` (frameworks, module id, style check level taken from the `target_settings` of `CMakeLists.txt`) into a module folder of its own under the build folder, whose `source` and `res` are junctions to the repository's. The SDK's CMake finds every source through the junctions (165 files, as with a copy). Deleting such a folder with PowerShell's `Remove-Item -Recurse` would delete the repository's files through the junction: remove the junctions first (`cmd /c rmdir`).
- The 2024 SDK's frameworks carry `projectdefinition.txt` files like 2025's, and the 2025 SDK's CMake files build them, with three changes to the copy: its source processor writes `using decltype(X)::Name;`, which MSVC 14.44 rejects (C7810, "decltype cannot be used in declarative nested name specifiers"): the copy gets the 2025 source processor's two lines for it; the instruction set is AVX as in 2024's `Base.props` (the 2025 files say AVX2); and C5264 is muted, which a macro of the 2024 framework raises in Maxon's own `c4d_pmain.cpp`. Its compiler settings otherwise match: 2024's and 2025's `Base.props`, `MSVCBase.props` and `ReleaseWin64.props` are identical files.
- One toolset (v143, MSVC 14.44) for all four; nothing else is installed but v145.

- With the 2024 SDK the macro `cinema` is defined as nothing, so the sources' `cinema::X` reads `::X`. It breaks only a definition like `cinema::Bool cinema::PluginStart()`, which reads `::Bool::PluginStart`; `main.cpp` writes those with a trailing return type. No identifier `cinema` occurs in the 2024 SDK's code.
- What a missing call costs: in 2024 the IPR's snapshot goes to the Picture Viewer without the name "Cycles Render IPR"; a Blender the plugin started is not ended by Windows when Cinema 4D 2024 is killed while Blender hangs (it still ends when its connection closes); before 2026.2 the renderer cannot tell Cinema 4D that it evaluates the scene itself (next point).

**Differences in behaviour** [T unless marked]:

- *The render document before 2026.2.* Without `EVALUATES_SCENE` Cinema 4D prepares the render document for its own renderer. Primitive generators carry `BIT_CONTROLOBJECT` in any document and their caches do not (Python, a plain document after evaluation, 2024.5 and 2027.0 alike, Render Perfect on and off). In the render document 2024.5 prepares, a Sphere with "Render Perfect" (on by default) is the exception: the sphere itself is unmarked and its polygon cache carries the mark (a trace of the walk in `coords.py`), so the walk took the cache as a generator's input and the sphere went missing from the render. The walk now ignores the mark on the cache of a Sphere that is not itself consumed (`Inherited::sphereCache` in `scene/scene_exporter.h`); a sphere that is the input of a generator is marked on the object and stays hidden. Other objects Cinema 4D prepares this way were not looked for [untested]. 2025 is taken to behave like 2024 [untested: no Python there]; a 2026 build in a Cinema 4D 2026.0 or 2026.1, which do not know the flag, likewise [untested].
- *The grey of an object without a material*, Standard renderer, OCIO document, a plane under an infinite light: 2024.5 renders 0.7352 where 2026.3 and 2027.0 render 0.5653 (ratio 1.30 = 0.8 / 0.604: 2024 takes the 80 % grey as it stands, later versions as sRGB); a material of 80 % grey without reflection gives 0.6928 in all three, and with Basic colour management all three agree (0.7768). The plugin's default material follows (`DEFAULT_GREY_OCIO`). 2025 [untested] is taken to be like 2026.
- *A scene saved with 2027 in an older version*: a document stores its OCIO render space as an index into the configuration of the version that saved it (`DOCUMENT_OCIO_RENDER_COLORSPACE`). 2027's built-in configuration (ACES 2.0, view "ACES 2.0 SDR-video") has ACEScg at 0; 2026's (ACES 1.0) has ACES2065-1 at 0 and ACEScg at 1. So 2026.3 opens a scene saved with 2027 in ACES2065-1 [T: the four scenes of `tests/scenes`]. Blender has no working space for that; the plugin says so in the console and renders on, and colours and textures then differ (the `golden` pictures by 0.07 and 0.25 before the test set ACEScg by name). Saved the other way round (older to newer) was not tried; 2024 and 2025 were not checked [untested].
- *A new document*: in c4dpy 2024 `BaseDocument()` and the document Cinema 4D makes itself have Basic colour management (Linear Workflow on); in 2026 and 2027 OCIO with ACEScg. The tests switch theirs to OCIO (`crtest.new_document`, `crrun`).
- *Raw render space from `RenderDocument`*: `RENDERFLAGS_OCIO_RAW_RENDERING` exists from 2026 on; the SDK calls it a shorthand for `RDATA_BAKE_OCIO_VIEW_TRANSFORM_RENDER` (5220) set off in an OCIO document, which 2024 and 2025 have (`crtest.render_flags`). The plugin reads 5220 in every version.
- *Baking a shader in the render document, 2024*: `BakeShaderIntoBaseBitmap` failed for the shaders with a bitmap inside (Filter, Fusion, Layer over a bitmap) in the render document 2024.5 prepares, while shaders without a bitmap baked; 2026 and 2027 bake them all in place [T: `shaders.py`, the three cells came out white]. When baking in place fails, the plugin bakes a copy of the shader in a document of its own (`BakeCopy` in `materials/material_export.cpp`): the render document's settings and path, the shaders' links translated to the copies (`AliasTrans`), and the colour settings set one by one as parameters followed by `UpdateOcioColorSpaces()`, since a new document of 2024 has Basic colour management. With that the three cells match 2027's.
- *Links in a render copy, 2024*: a link in a shader's settings is written by `HyperFile::WriteContainer` as the identity of its target, and 2024 gives those identities anew in every render's copy of the document, so the bake cache's fingerprint changed with every render and a Filter over a bitmap was baked again each time [T: `shaders.py`, "bake_cache"]. The fingerprint now leaves links out and counts their target's type and name instead (`ShaderFingerprint`). The Layer shader keeps its layers in a list of its own, not as links in its settings, and that still changes: in 2024 a Layer over a bitmap is baked again by every render (`shaders.py` allows that one rebake in 2024).
- *Volume Builder grids without a name, 2024*: a Volume Builder's grid in 2024.5 has an empty name (2027: the object's name), and so do the `.vdb` files written from it; Blender reads grids by name. The plugin names a nameless grid (`density` when it is the first and a fog grid, else `grid_<n>`) and then writes the grids itself instead of sending the file a Volume Loader read (`scene/volume_export.cpp`; the rename works on a copy of the volume, Cinema 4D's cache keeps its grid) [T: `volumes.py`]. Whether 2025 names its grids is [untested].
- *Undo and the render view's camera, 2024*: every undo and redo in 2024.5 drops the render view's camera link, also the undo of a step that only added a material; 2026 and 2027 keep it [T: probes, `ipr_add.py`, `ipr_window_checks.py`]. After the redo of the IPR's "Add camera" the view looks through no scene camera (c4dpy) or its previous camera (the application), so the plugin takes the view as the user's choice and stops following: in 2024 the new camera is not kept in the view after undo and redo.
- *The editor camera, 2024 and 2026*: the view's editor camera of 2024.5 and 2026.3 is an `Ocamera` with near clipping on at a distance of 0 (2027: an "RS Camera" with it off; 2026 seen in c4dpy only). With it Eevee rendered no light through the editor camera (B10, fixed for every version: "Cameras and views", the editor's views).
- *Inserting a document in c4dpy 2024*: `InsertBaseDocument` drops the inserted document's caches (2027 keeps them), and in c4dpy nothing evaluates the active document again; a test evaluates it after inserting (`cycles_nodes.py`) [T].
- *Redshift under 2024 and 2026 in c4dpy* [T, `tests/c4d/redshift.py` and probes]: for some of the test's Redshift lights, each in a new document, `RenderDocument` with Redshift returned a black picture, also when rendered again (2026.3.4: the 2nd light every time, the spot and the normalised area light in some runs; 2024.5.1: four of the seven lights); one document rendered eight times never did, and keeping the documents alive changed nothing. The same lights render under 2027, and Cycles Render gives the same numbers in all versions. Redshift's, not the plugin's: the test renders a black reference up to three times and, in 2024 and 2026, reports a light that stays black as not compared. *Corrected 2026-11-18 (F24) for 2024:* the four lights there are the point lights, the spot and the normalised area light, and they are not black but about 10000 times darker, by Redshift 3.6.04's own rule (its unit scale, 1 cm by default; "Redshift lights", "Redshift 3.6.04"); they render the same every time. Cinema 4D 2024 here has Redshift 3.6.04, which also offers fewer units; 2026's black second light was not looked into again.
- *Another instance*: a regular Cinema 4D finds a running instance of the same installation and hands its command line over to it ("Detected another instance of the same installation running. Forwarding command line parameters...") and ends, also with another `g_prefsPath`. `g_allowParallelInstance=true` (known to 2024 to 2027) starts an instance of its own; the test runner sets it.
- *A fresh preferences folder*: c4dpy asks on its console for the licence method. The choice is `licensetype.prf` at the top of the preferences folder (56 bytes, value 6 for the Maxon App, the same file in all four versions); the test runner writes it into the folders it makes.
- *Python*: 2024 to 2027 bring Python 3.11 or later [read: `python311` folders]; c4dpy and the test harness need `resource\modules\python\libs` in the installation, which the 2025 installation on the development machine lacks (c4dpy 2025 ends at start with an access violation and prints nothing). Names the tests meet: the particles' Basic Emitter is `c4d.Ofpbasicemitter` from 2025 on and `c4d.Ofpshapeemitter` in 2024 (the same id), a node graph's root is `GetViewRoot()` from 2025 on and `GetRoot()` in 2024 (`crtest`).
- *Logs*: only 2027 writes its start-up lines (versions, the module loader's warnings, the module list when two modules compete) into the `g_logFile`. 2025 and 2026 logged the plugin's own "module loaded" line, 2024 showed it on the console but not in the log.

## Renderer (VideoPostData)

Headers: `CF/c4d_videopostdata.h`, `CF/c4d_tools.h` (`VPBuffer`, `Render`, `VideoPostStruct`), `CF/ge_prepass.h` (flags).

Proven by `plugin/cyclesrender/source/videopost/cycles_videopost.cpp` [T]:

- `Execute` runs on the render thread and may block for the whole frame: the plugin starts Blender, sends the scene and waits for the pixels inside the call that closes the render stage (`vps->vp == VIDEOPOSTCALL::RENDER && !vps->open`).
- Cancel: `vps->thread->TestBreak()` becomes true when the render is stopped, including when the thread passed to `RenderDocument` is ended. Polled every 100 ms while waiting for Blender, a 1920×1080 render stopped 0.09 s after the signal.
- Once a stage has returned an error, `*vps->error` holds it and `Execute` is still called for the remaining closing stages. Return `*vps->error` from those calls: returning `FAILED` (as the SDK example does) turns a user cancel into a failed render.
- A Picture Viewer render of 640×360 through Blender took 6 s, about 3 s of it Blender starting.

- Registered with `PLUGINFLAG_VIDEOPOST_ISRENDERER`, the renderer appears in the Render Settings' Renderer dropdown and gets its own page in the list.
- Returning `VIDEOPOSTINFO::EVALUATES_SCENE` from `GetRenderInfo` is accepted. `vps->doc` then arrives evaluated: caches and deform caches are built when the render stage closes, for `RenderDocument`, the Picture Viewer and `Commandline.exe`, and for every frame of a sequence. The plugin calls no `ExecutePasses` itself. [T]
- One render job is one instance of the video post: `FRAMESEQUENCE` opens once, every frame runs `FRAME` to `INNER`, and `FRAMESEQUENCE` closes once, also after an error or a cancel. The plugin keeps its Blender session in the instance between those two calls (`OpenSession`, `CloseSession`). [T: four frames, one Blender]
- `RenderDocument` and view transforms [T, `tests\c4d\colour.py`]: by default Cinema 4D's own renderers bake the view transform (tone mapping) into the pixels they return. With `RENDERFLAGS::OCIO_RAW_RENDERING` they return render-space values. A video post renderer has to do the same itself: `vps->render->GetRenderData().GetBool(RDATA_BAKE_OCIO_VIEW_TRANSFORM_RENDER, true)` (absent means on) tells whether to apply `OcioConverter::TransformColors(…, OCIO_RENDERING_TO_VIEW)` before writing the picture. For a Picture Viewer or command-line render the switch is off, and Cinema 4D applies the view transform when showing or saving (8-bit PNG and 32-bit EXR both matched the Standard renderer without the plugin doing anything).
- "Basic" colour management (`DOCUMENT_COLOR_MANAGEMENT_BASIC`) [T, `tests\c4d\colour.py`]: with Linear Workflow on, the Standard renderer's picture holds its linear values with the sRGB curve applied, in memory and in the Picture Viewer, raw flag or not, **unless Multi-Pass is on**: then the picture and every layer hold linear values and the Picture Viewer applies the curve when showing them. With Linear Workflow off the picture holds the sRGB numbers it calculated with, Multi-Pass or not. The Picture Viewer shows a float picture without a colour profile as it is. The rules for everything that goes in are under "Colour management" below; the plugin keeps them in `scene/document_colors`. (A linear image colour profile in the Render Settings is taken to mean no curve: untested.)
- Motion blur [T]: inside `Execute` (render stage closing) the render document can be moved in time and evaluated: `doc->SetTime(BaseTime(seconds))`, `doc->ExecutePasses(vps->thread, true, true, true, BUILDFLAGS::EXTERNALRENDERER)`, read the caches, and set the frame's time back the same way. Worked for `RenderDocument` and gave the expected streak lengths.

## Threads, messages, change detection

- Worker threads: `C4DThread` (`Main`, `Start`, `End`, `TestBreak`). Main-thread calls: `maxon::ExecuteOnMainThread`.
- Worker → UI: `SpecialEventAdd(id, p1, p2)`; received in `GeDialog::CoreMessage` (parameters in `BFM_CORE_PAR1/2`).
- Scene changed: core message `EVMSG_CHANGE`. `MessageData` plugins (`RegisterMessagePlugin`) also receive core messages and timers.
- Threading rule: only the main thread may modify the active document, add events, or touch GUI. Manual: `SDK/docs/page_manual_cinemathreads.html`. What the plugin's one piece of work on an evaluating thread keeps to (the IPR's step in the scene hook: objects of the evaluated document only, no view, no active document), and that jobs of the main thread's queue run inside Cinema 4D's own calls: "What the IPR sends while a change is in progress", "What each thread may touch".
- Caches of the active document are valid only after C4D has evaluated the scene. A `SceneHookData` (`CF/c4d_scenehookdata.h`, `RegisterSceneHookPlugin`) can execute after generators and also receives `MSG_DOCUMENTINFO` (document loaded, activated, undo, redo). The priorities of an evaluation (`ge_prepass.h`, the same in the four SDKs): initial 1000, animation 2000, expressions 3000, dynamics 4000, generators 5000, scene nodes 10000; at "generators + 1" every generator's and deformer's cache was that evaluation's [T, 2024.5.1 and 2027.0.0, 0.2.0, F23].
- Dirty counters: `C4DAtom::GetDirty(DIRTYFLAGS::MATRIX | DATA | CACHE)`, `GetHDirty(HDIRTYFLAGS::OBJECT | OBJECT_MATRIX | MATERIAL | SHADER | TAG | RENDERSETTINGS | ANIMATION)`, usable on the document.
- Content hashes: `VariableTag::GetDataHash()` — compare the `Tpolygon` hash for topology change and the `Tpoint` hash for point-only change. Tag data is copy-on-write and shared between identical caches.
- Identity: `BaseObject::GetGUID()` (works for cache objects), `GetUniqueIP()`, `FindUniqueID(MAXON_CREATOR_ID, …)` (persists across save/load).
- **A document's identity through a render's copy** [T, probes in c4dpy; `tests/c4d/baked_files.py`, `baked_files_window.py`]: a document has a `MAXON_CREATOR_ID` (16 bytes) from the start, also one made by `BaseDocument()` that was never in the document list. `GetClone(COPYFLAGS::DOCUMENT)` and `GetClone(0)` give the copy, its materials and its objects new ids; with `COPYFLAGS::PRIVATE_IDENTMARKER` all keep theirs. The copy that `RenderDocument` renders (c4dpy) and the copy of a render to the Picture Viewer (the application) carry the document's id, keep its name, are not in the document list, and reach the video post on a thread that is not the main thread. `materials/baked_files.cpp` uses that id to give baked textures an owner.
- **Seeing a document closed** [T, `tests/c4d/baked_files_window.py`]: File > Close (command 12664) sends `EVMSG_CHANGE` to a `MessageData`'s `CoreMessage`, and by then the document is gone from `GetFirstDocument()`/`GetNext()`: comparing the list with the documents seen before finds it. The hook in `materials/baked_files.cpp` also checks on its timer (once a second); in the test the change message was the one that found it. `MSG_DOCUMENTINFO_TYPE_REMOVE` would need a `SceneHookData`, which was not tried. - Launch a long-running process [T]: `maxon::SystemProcessInterface::CreateProcess(url, args, flags, nullptr)` → `StartProcess()`, then `IsRunning()`, `GetExitCode()`, `KillProcess()`, and `SystemProcessInterface::WaitForProcess(process, maxon::Seconds(n))`. ## Scene traversal

Implemented in `plugin/cyclesrender/source/scene/scene_exporter.cpp` (`SceneExporter::Walk`) and checked by `tests/c4d/traversal.py` against what the Standard renderer shows. [T]

```
Walk(op, mg, inherited):
  apply op's render dot to inherited.visible        (MODE_ON / MODE_OFF; MODE_UNDEF keeps the parent's)
  take op's unrestricted texture tag as inherited.material, if it has one
  if op is a light / sky: record it (a light only while its green check is on; the check is not inherited)
  else if op is a render instance: Walk(reference object, mg, …)
  else if (cache = op->GetDeformCache() or op->GetCache()): Walk(cache, …)
  else if op is a polygon object and not BIT_CONTROLOBJECT: renderable mesh
  for each child: Walk(child, mg * child->GetMl(), inherited)
```

- A deform cache replaces the cache. Objects consumed by a generator carry `BIT_CONTROLOBJECT`.
- Matrices: cache objects have no parent pointer, so `GetMg()` is wrong for them. Accumulate from `GetMl()`: a generator's cache root gets `mg * cache->GetMl()`; a deform cache sits exactly where its object is and gets `mg` unchanged. [T]
- Visibility: the render dot is inherited down the hierarchy and into caches, and a child can switch it on again under a hidden parent. [T]
- Layers: `op->GetLayerData(doc)->render == false` hides the object and everything in its cache, but not its children in the Object Manager. [T]
- Instances [T]: a plain instance has a cache holding a copy of the original, and the copy keeps the original's own render dot. So an instance of an object whose own dot is off renders nothing, while an instance of an object hidden by its parent renders. A render instance has no cache: walk `InstanceObject::GetReferenceObject(doc)` with the instance's matrix, apply the reference's own dot, ignore its `BIT_CONTROLOBJECT`. Multi-instances are not exported yet.
- Materials: the last texture tag without a selection restriction wins; children and caches inherit it when they have none. [T]
- A render document is already evaluated (see "Renderer"). For any other document: `doc->ExecutePasses(thread, true, true, true, BUILDFLAGS::EXTERNALRENDERER)`.
- The exporter's view of a document as text: `SceneExporter::GetListing()`, reachable from tests (see `g_cyclesRenderDumpFile` in `docs/development.md`).

## Coordinates

`plugin/cyclesrender/source/scene/coords.h`. [T: `tests/c4d/coords.py`, `cameras.py`]

- A position (x, y, z) in Cinema 4D becomes (x, z, y) × metres-per-unit in Blender. The unit comes from the document (`DOCUMENT_DOCUNIT`, a `UnitScaleData`; centimetres by default).
- The swap mirrors space, so every face is sent with its corners in reverse order, and per-corner data (normals, UVs) in the same order.
- Object matrix: Blender's local X, Y, Z axes are Cinema 4D's local X, Z, Y axes, each swapped (`Coords::ObjectMatrix`).
- Cameras and lights look along +Z in Cinema 4D and along −Z in Blender, both with +Y up (`Coords::AimedMatrix`: X and Y axes swapped as above, Z negated, all normalised).
- UV: Blender's v is `1 - v` of Cinema 4D's.
- Camera: `CAMERA_FOCUS` and `CAMERAOBJECT_APERTURE` map to `lens` and `sensor_width` with horizontal sensor fit. Parallel projection shows 1024 units across the image at `CAMERA_ZOOM` 1, whatever the resolution. Film offset X is Blender's `shift_x`; offset Y is `-offsetY / aspect`, because Blender measures both shifts in image widths. When the image is larger than the camera's picture (the IPR's "Fit Window", `CameraFraming`), sensor width and parallel width are multiplied by image width / picture width, `shift_x` is `offsetX · pictureWidth / imageWidth` and `shift_y` is `-offsetY · pictureHeight / imageWidth`; the first two are tested, the shifts are not. Without clipping set on the camera the exporter sends 0.01 m to 10 km. Projections other than perspective and parallel, clipping of parallel views and the spherical camera: "Cameras and views" below.

## Light conversion

`plugin/cyclesrender/source/scene/light_export.cpp`. Both halves are measured, not assumed. [T]

Cinema 4D, Standard renderer (`tests/c4d/measure_c4d_lights.py`): a white diffuse surface facing a light of brightness B renders as

- B, at any distance, for an omni, spot, infinite or small area light without falloff;
- B × (r / d)² with "Inverse Square" falloff, r being the light's Radius/Decay and d the distance (3.98 at half of r, 0.989 at r, 0.30 at 1.8 r).
- A 200 × 200 area light at 500 gives 0.974, and the same value on the side it faces away from: area lights shine both ways.
- `LIGHT_DETAILS_OUTERANGLE` is the full cone angle: 30° lit a patch of radius 134 at distance 500.

Blender 5.2.3, Cycles (`tests/bridge/measure_lights.py`): the same surface renders as

- S / π for a sun of strength S;
- P / (4 π² d²) for a point or spot light of power P at distance d in metres;
- P / (π² d²) on the axis of a small area light, four times a point light of the same power.

Hence, with r in metres:

| Light | Blender | Power |
|---|---|---|
| infinite | `SUN`, angle 0 | S = π B |
| omni | `POINT`, radius 0 | P = 4 π² r² B |
| spot | `SPOT` | P = 4 π² r² B; `spot_size` = outer angle; `spot_blend` = (cos(inner/2) − cos(outer/2)) / (1 − cos(outer/2)) |
| area | `AREA` rectangle or disk | P = π² r² B |
| area, sphere shape | `POINT` with radius | P = 4 π² r² B |

A light with inverse-square falloff then matches at every distance. Blender has no light without falloff, so such a light gets the same power and matches Cinema 4D exactly at the distance r, its Radius/Decay value (500 cm unless changed), brighter closer and darker beyond. The other falloff types are treated the same way. Every standard light is sent with `use_shadow = true`, whatever its `LIGHT_SHADOWTYPE`, also `LIGHT_SHADOWTYPE_NONE` (Cinema 4D's default): since 0.2.0, see "Shadows of Cinema 4D's lights" (before, None became `false`). The shadow type sets the light's size (radius, or a sun's angle): "Soft and area shadows". A light whose green check is off is not sent ("Lights switched off").

## Material conversion

`plugin/cyclesrender/source/materials/material_export.cpp` turns a classic material into a Principled BSDF graph; `tests/c4d/materials.py` shows every channel next to the Standard renderer. [T]

- Colour → Base Color; a bitmap is mixed in as the channel's mix mode and strength say. Luminance → Emission at strength 1. Without a colour channel the base colour is black.
- Transparency → Transmission Weight (the brightest component) and IOR; the base colour moves towards the transparency colour by that weight.
- Reflectance (an approximation for the usual one or two layers): diffuse layers are skipped; the first other layer decides the specular lobe by the rules that follow. With two layers, the one with a dielectric Fresnel becomes the clear coat (Coat Weight = reflection strength, with its roughness and IOR) and the other the lobe; two layers of the same kind, and any layer after the second, are left out with a warning. The lobe: Legacy specular (a new material's "Default Specular"): roughness = width, Specular IOR Level 0.5 at 20 % strength. No Fresnel: Metallic = reflection strength, and at full strength the layer colour becomes the base colour. Dielectric: Specular IOR Level = 0.5 × strength, IOR from the layer. Conductor: Metallic = strength, base colour = layer colour. Reflectance off: Specular IOR Level 0.
- Alpha: the image's alpha channel when "Image Alpha" is on and the file type can hold one, otherwise its brightness; optional invert.
- Normal: a tangent-space Normal Map node, with the texture as it is. No channel flip is needed although v is flipped: the test's ridges are lit from the same side (correlation 0.97).
- Bump [T: measured against the Standard renderer]: Cinema 4D tilts the normal by the height difference between neighbouring texels times the strength. The result does not depend on the object's size, and a finer texture of the same pattern gives a shallower relief. At 100 % strength a step of 1 (black to white) between two texels is a slope of 7.4. Blender's Bump node works in space instead, so the exporter builds the rule from nodes: three texture look-ups one texel apart, their differences as the slopes of a normal fed to a Normal Map node (`ClassicMaterialGraph::Bump`). Matches at 5–100 % strength, 128 and 512 pixel textures, and two object sizes.
- Bitmaps: `GenerateTexturePath(doc->GetDocumentPath(), name, Filename(), &resolved)` finds a file the way Cinema 4D does (next to the scene, in `tex`, in the search paths). Colour textures are sent as `sRGB` (`Linear Rec.709` for .exr and .hdr), data textures as `Non-Color`. With Blender's working space set to the document's render space, an sRGB texture renders with the same numbers as in the Standard renderer. With "Basic" colour management the colour space follows the document and the bitmap's "Color Profile" ("Colour management" below).
- An object without a material: 80 % grey, which is 0.604 in linear light.
- Sky [T: `tests/c4d/sky_orientation.py`]: a Sky object needs its texture tag in spherical projection (UVW shows one flat colour). Seen from inside, the panorama's left edge is towards +X and its quarter point towards +Z, running on towards −X: mirrored compared with Blender's equirectangular lookup. `environment_export.cpp` mirrors X in a Mapping node and turns it with the Sky object.

## Standard renderer facts for comparisons

- It computes direct light only, and its picture sits about 0.28 px to the lower right of the exact projection. [T]
- A Sphere primitive with "Render Perfect" (default on) is drawn as a perfect sphere regardless of its segments. [T]
- It reflects and refracts the scene but shows no highlight of a light in a layer whose specular strength is 0; Cycles always mirrors lights. [T]

- `InstanceObject` (`CF/c4d_libs/lib_instanceobject.h`): `IsMultiInstance()`, `GetReferenceObject(doc)`, `GetInstanceCount()`, `GetInstanceMatrix(i)`, `GetInstanceColor(i)`, `GetInstancePersistentHashes()`.

- **What a Cloner's cache holds** [T, probe in c4dpy]. Mode "Instance" (0): a Null whose children are the clones, one per visible MoData entry, in MoData's order. "Render Instance" (1): the same, but from the second clone of each kind on the child is a render-instance `Oinstance` referring to the first. Clones with `MOGENFLAG_CLONE_ON` unset or `MOGENFLAG_DISABLE` set are not in the cache.
- Cloner instance mode: `MGCLONER_VOLUMEINSTANCES_MODE` (none, render instance, multi-instance).
- Effectors and fields are fully baked into MoData and caches after `ExecutePasses`.

- Classic material (`Mmaterial`, `DESC/mmaterial.h`): channels switched by `MATERIAL_USE_*`. - Shaders (`BaseShader`, `CF/c4d_basechannel.h`): type ids `Xbitmap`, `Xnoise`, `Xgradient`, `Xfresnel`, `Xlayer`, `Xcolorizer`, `Xfilter`, `Xfusion`, `Xtiles`, `Xvertexmap`, `Xmgcolor`. - Bake any shader: `BaseShader::BakeShaderIntoBaseBitmap(bmp, doc, thread, alpha, colorSpace, lwf, hdr, xmin, xmax, ymin, ymax)`.
- Texture paths: `GenerateTexturePath`; `asset:///` URLs resolve to an in-memory URL, so copy the file out with `maxon::Url::IoCopyFile` before giving Blender a path.
- Node materials: `mat->IsNodeBased()`, cast to `NodeMaterial`, `GetGraph(spaceId)`. Space ids: `net.maxon.nodespace.standard`, `com.redshift3d.redshift4c4d.class.nodespace`. Graph reading: `SDK/frameworks/graph.framework/source/maxon/graph.h`.
- **Neutral PBR export for any material:** `maxon::material::MaterialExportInterface::Export(material, config)` requesting the Standard Surface bundle (`SDK/frameworks/exchange.framework/source/maxon/material/materialexport.h`). Worked example: `SDK/plugins/example.nodes/source/exchange/materialexport_command.cpp`.
- Change detection: `mat->GetDirty(DIRTYFLAGS::DATA)`; node graphs `graph.GetModificationStamp()`.

Measured (`tests\c4d\shaders.py`) [T]:

- The shaders inside a shader are reached with `GetFirstShader()` on that shader (what Python's `InsertShader` fills), not with `GetDown()`. Walk both.
- Dirty counters do not identify a shader's state for caching: two shaders of one kind in one material had the same count, and the render's copy of the document differs. Hashing the container as Cinema 4D would save it works: `HyperFile` opened on a `Filename` in memory write mode (`SetMemoryWriteMode(MemoryFileStruct)`), `WriteContainer(shader->GetDataInstanceRef())`, then `MemoryFileStruct::GetData`.
- `BakeShaderIntoBaseBitmap(bitmap, doc, nullptr, false, colorProfile, linearWorkflow, true, 0, w-1, 0, h-1)` into a bitmap made with `Init(w, h, 96)` gives render-space floats; saved with `FILTER_EXR` and `SAVEBIT::USE32BITCHANNELS` and loaded in Blender as `Non-Color` they render like the shader itself (0.02–0.07 off, except the Filter shader).
- `BaseShader::GetRenderInfo()` [T, probe from Python]: a Noise shader with animation speed 0 answers 16 (`SHADERINFO::BUMP_SUPPORT`), with 1.0 it answers 1040 (`TIMEDEPENDENT` added). The plugin bakes such a shader per frame and every other shader once, whatever the frame (`IsTimeDependent` in `materials/material_export.cpp`); a bitmap whose timing range (`BITMAPSHADER_TIMING_FROM`/`_TO`) is not empty counts as changing too (untested).
- Bake reuse [T, `tests/c4d/baked_files.py`]: a second final render of an unchanged scene bakes nothing; at another frame only the shader that changes by itself and one whose settings are animated with keys are baked (the render's copy holds the animated values, so the fingerprint differs); an edited shader is baked again; the IPR at the same frame bakes nothing (it gets the final render's files). Before 0.2.0 the frame was part of every key, so every frame of an animation baked every shader again, and nothing was reused after a restart.
- Gradient shader: along V the gradient starts at the **bottom** of the UV square (V = 1 in Cinema 4D's terms), along U at the left. "Cycle" changes nothing between 0 and 1. Knots: `Gradient::GetKnot(i)` gives `maxon::GradientKnot` with `col`, `brightness`, `pos`, `bias`, `interpolation`; smooth knots match a Color Ramp set to Ease, linear knots Linear.
- Fresnel shader: the gradient's left end is where the surface is seen edge-on, its right end where it faces the viewer: position = |normal · view direction|.
- Checkerboard: U and V frequency count pairs of fields; the field at the top left of the UV square has colour 1.
- The Colorizer's "luminance" and the Fusion mask weigh red, green and blue equally (the test's inputs are grey, so other weights are not ruled out).
- A gradient's interpolation can be set from Python only for all knots at once (`SetData(c4d.GRADIENT_INTERPOLATION, …)`), and that did not change the render.
- Layer shader: `LayerShader::GetFirstLayer()` is the top layer, `GetNext()` goes down; `LAYER_S_PARAM_SHADER_LINK` holds a `BaseLink*` (`GeData::GetVoid`). The blend mode names (`BlendMultiply`, …) are in namespace `cinema`.

Texture tags, stacking, displacement, node materials (`tests\c4d\mapping.py`, `node_materials.py`) [T]:

- Offset and length of a texture tag, with V running down: u' = (u − offsetX) / lengthX, v' = (v − offsetY) / lengthY; tiles = 1 / length. With "Tile" off the Standard renderer shows nothing outside the one copy.
- `TextureTag::GetMl()` gives the tag's texture axes in the object's space. Flat projection: the tag's XY plane, −1…1 becomes 0…1, U to the right and V up the tag's Y. Spherical and cylindrical: around the tag's Y axis; U is 0.5 towards +X and grows towards −Z; V runs from the +Y pole (spherical) or +1 (cylindrical) down.
- A node material has the type `Mmaterial`, like a classic one. `static_cast<NodeMaterial*>(material)->HasSpace(maxon::Id("net.maxon.nodespace.standard"))` (or `"com.redshift3d.redshift4c4d.class.nodespace"`) tells them apart.
- `MaterialExportInterface::Export(material, config)` worked on the render thread in every test run. A Standard node material's colours come back with the sRGB curve applied (0.9 → 0.955); a Redshift material's come back as set. The parameters are read with `ParameterStorageInterface::Extract<TYPE>(data._parameters, maxon::MATERIAL::PORTBUNDLE::STANDARDSURFACE::BASE_COLOR)`.
- In Python a default node graph is made with `mat.GetNodeMaterialReference().CreateDefaultGraph(maxon.Id(space))` after the material is in a document. Standard space: node `bsdf` (asset `net.maxon.render.node.bsdf`), colour port `color`. Redshift: asset `com.redshift3d.redshift4c4d.nodes.core.standardmaterial`, port `…standardmaterial.base_color`. Set with `port.SetPortValue(maxon.Color(…))` inside `graph.BeginTransaction()`.
- "Image Alpha" on a file without an alpha channel uses the picture's brightness. `BaseBitmap::Init(file)` then `GetInternalChannel() != nullptr` tells whether there is one.
- Displacement type "Intensity (Centered)" is the default and moves by (value − 0.5) × 2 × height × strength along the normal.

Volumes, hair, particles, tags [T unless marked]:

- **Volumes.** A Volume Builder's cache is a volume object (`Ovolume`, `VolumeObject`); a Volume Loader's cache is a Volume Set (`Ovolumeset`) named after the frame's file, whose cache holds a Null with one volume object per grid; a Pyro Output's cache is a Volume Set with `density`, `temperature` (in Kelvin: the Pyro tag's defaults are 4000 and 1000) and `velocity`. `VolumeObject::GetVolume()` gives the `maxon::VolumeInterface`; ask it for `GetGridClass()` (`maxon::GRIDCLASS::FOG`, `SDF`) and `GetGridName()`. `maxon::VolumeToolsInterface::SaveVDBFile(url, 1.0, volumes)` writes them; needs `volume.framework` in the module's `apis`.
- A volume object's matrix **is** its grid's transform: voxel size as scale, and for a grid built in the scene the global position (`GetMl()` and `GetMg()` of a builder's volume both carry the voxel size, and the grid transform equals `GetMg()`). So a file saved from memory is already placed in the world, and a file read by a loader is placed by the volume object's parent.
- Two saves of the same grids give files that differ in some bytes, so a file's bytes cannot tell whether a volume changed. The plugin compares the grid objects' addresses and the owner's dirty count.
- **Pyro from a script:** setting the time frame by frame and calling `ExecutePasses` produces the grids but leaves them empty ("Voxel Count: 0"), headless and in the regular Cinema 4D. A Basic Emitter (`Ofpbasicemitter`) run the same way does fill its particle group.
- **Hair.** `HairObject::Lock(doc, nullptr, false, 0)`, `GenerateHair(HAIR_GENERATE_FLAGS_NONE)` (since 0.3.0; before it `HAIR_GENERATE_FLAGS_NO_MATERIAL`, see the next bullet), `Unlock()`; the returned `HairGuides` (free with `HairGuides::Free`) give `GetCount()`, `GetGuidePointCount()` and `GetPoints()`, which are in world space already. A Hair object carries `BIT_CONTROLOBJECT` itself, as does a Redshift light: do not treat them as consumed by a generator. The hair material hangs on a `Thairmaterial` tag (`HAIRMATERIAL_TAG_LINK`), not on a texture tag. Its colour gradient keeps its knots in the order they were made, not by position (knots inserted at 0, 1 and 0.5 read back in that order, c4dpy 2027.0.0, 2026-11-19, `tests/c4d/hair_particles.py`): the root and tip colours are those of the knots with the smallest and largest position.
- **The hair material's shape is in the generated hairs, at a price** (0.3.0, F2; measured 2026-11-23 in Cinema 4D 2027 on the maintainer's samples, `internal/Test Scenes/Hair_Samples.c4d`: two Hair objects of 50,000 hairs with 12 segments on 482 guides; `internal/f2/probe_generate.py`) [T]. `GenerateHair(HAIR_GENERATE_FLAGS_NO_MATERIAL)` returns the hairs along the guides only and took 13 ms per object; `HAIR_GENERATE_FLAGS_NONE` returns them as Cinema 4D renders them, with the material's bend, clump, curl, frizz, kink, twist, length and scale in the points (the first hair's second point at (-74.9, 27.5, -227.7) instead of (-77.7, 29.1, -230.3)), and took 87 ms for the material with five such channels on and 376 ms for the one with eight. Both give the same number of hairs and points, in world space. `tests/c4d/hair.py` compares the rendered hairs' box with the box of the points Python gets from the same call: equal to a pixel, straight and with a Bend of 60 %.
- **A Hair object's own change counters move with every evaluation** (0.3.0, F2; `internal/f2/probe_dirty.py`, `probe_container.py`, Cinema 4D 2027) [T]: each `ExecutePasses` with nothing changed raised its `GetDirty(DATA)` by 2, its `GetDirty(CACHE)` by 1 and its `GetHDirty` (all, and the object's own) by 1; generating the hairs raised none. Its hair material, the tags on it and the object it grows on kept theirs. The data count rises because the evaluation writes a count of its own into the object's container, under id 50004 (no name in the SDK), which went up by 1 each time while the container's `GetDirty()` went up by 2; no other plain value of the container changed. So whether a hair has to be generated again cannot be read from the object's counters: the exporter reads what the hairs are made from instead (`HairSignature` in `scene/curves_export.cpp`: the container's count less twice that entry, the guides' points and those dynamics moved, the tags' counts, the material's, the root object's data and cache counts and both places). Not measured: Cinema 4D 2024 to 2026 (where the container counts differently the hairs are generated at every export, as before, never kept wrongly).
- **What hair costs in the IPR, in the maintainer's samples** (0.3.0, F2; `internal/f2/run_probe.ps1`, c4dpy 2027, Blender 5.2.3, medians of five; the whole export from the change event, during which Cinema 4D's main thread is held) [T]: before 0.3.0, without the material's shape, every whole export generated both hairs again, 34 to 42 ms, whatever had changed. With the shape that would be about 465 ms at every finished edit. Now: an export with nothing changed, or with another object moved, generates no hair (0 ms; both hairs kept); a value of one hair material changed generates that hair only (99 ms); the object one hair grows on moved, that hair only (383 ms); the IPR's first export and Reload generate both (482 ms). Another frame generated both (472 ms) in these samples, whose guides move from frame to frame (hair dynamics); in the test's scene without dynamics another frame generated none. A hair material channel driven by a shader that changes over time without a counter is not seen (the document's time is not part of what is compared, so that playing a scene whose hair stands still costs nothing).
- **Particles.** A particle group (`Ofpgroup`, `ParticleGroupObject`) is a point object: `GetParticlePositionsR()`, `GetParticleRadiiR()`, `GetParticleColorsR()` (each empty when the group has no such channel). Points set on a group from Python are gone after the next evaluation; particles must come from an emitter.
- **Tags.** `RegisterTagPlugin(id, name, TAG_VISIBLE, Alloc, "Tcyclesobject"_s, nullptr, 0)` with a description that includes `Tbase`. From Python: `obj.MakeTag(<plugin id>)`.
- **Compositing tag**: `COMPOSITINGTAG_SEENBYCAMERA`, `_CASTSHADOW`, `_SEENBYGI`, `_SEENBYRAYS`, `_SEENBYREFLECTION`, `_SEENBYREFRACTION`, `_SEENBYTRANSPARENCY`; a tag on a parent counts for the objects below (measured against the Standard renderer).
- **Light lists**: `LIGHT_EXCLUSION_LIST` is an `InExcludeData` (`GetObjectCount()`, `ObjectFromIndex(doc, i)`), `LIGHT_EXCLUSION_MODE` include or exclude. An excluded object is neither lit by the light nor throws a shadow from it.

**Intensity.** With v = intensity × 2^exposure (EV) in the unit "Image" (the default of a light made from Python):

| Redshift light (`REDSHIFT_LIGHT_TYPE`) | What v is | Blender |
|---|---|---|
| Infinite (0) | irradiance: a white wall renders v / π | sun of strength v |
| Point (1), Spot (2) | radiant intensity v (W/sr): a white wall d m away renders v / (π d²) | power 4π v |
| Area (3), rectangle or disc | radiance v, or v / A with "Normalize Intensity" | `AREA`, power π L A |
| Area, sphere | radiance v (or v / A) on a sphere of diameter Size X | `POINT` with radius Size X / 2, power π L A, `use_soft_falloff` off |

A is the surface that emits, as Redshift counts it for "Normalize Intensity" and the units (each measured): rectangle Size X × Size Y, disc (an ellipse when the sizes differ) π/4 × Size X × Size Y, sphere π × Size X² (its Size Y and Size Z change how it looks, not its light: 1.00 and 0.99 of the round one), cylinder π × d × Size Z. **The object's scale counts** in Redshift: Size X and Size Y times the light's X and Y scale (a sphere's diameter times its X scale, a cylinder's length times its Z scale); with "Normalize Intensity" the power stays, without it the radiance. Before 0.2.0 the scale was ignored, so a scaled-up area light rendered too dark (scale 2 in X: 0.66 of Redshift under the light, 0.34 to 0.6 elsewhere) and a scaled-down one too bright (scale 0.5: 3.3 to 4.7 times).

**Units** (`REDSHIFT_LIGHT_PHYSICAL_UNITSTYPE`; Redshift's own description lists two more than the SDK headers: 5 Luminous Intensity (cd), 6 Luminous Exitance (lm/m²)). Every photometric unit is converted at 683 lm/W; "Luminous Efficacy (lm/W)" (`_LUMENSPERWATT`, 17 by default) only turns the radiometric units' watts into lumens first (34 gives twice 17's light); "Normalize Intensity" counts in "Image" only. Ω is the solid angle the light spreads over: 4π for a point (and, as measured, for the infinite light), 2π (1 − cos(cone / 2)) for a spot (its falloff angle does not change it). In terms of v of "Image":

| Unit | Point, spot | Area (A as above) | Infinite |
|---|---|---|---|
| 0 Image | v | v (v / A normalized) | v |
| 1 Luminous Power (lm) | v / (683 Ω) | v / (683 π A) | v / (683 × 4π) |
| 2 Luminance (cd/m²) | black (1e-6 of the light) | v / 683 | v / 683 |
| 3 Radiant Power (W) | v η / (683 Ω) | v η / (683 π A) | v η / (683 × 4π) |
| 4 Radiance (W/sr/m²) | black | v η / 683 | v η / 683 |
| 5 Luminous Intensity (cd) | v / 683 | v / (683 A) | v / 683 |
| 6 Luminous Exitance (lm/m²) | black | v / (683 π) | v / (683 × 4π) |

η is the light's efficacy. A point or spot light in an area light's unit is left out with a line in the console. Before 0.2.0 every unit was read as "Image" (with a line in the console): a light in lumens rendered 683 × 4π ≈ 8600 times too bright, one in watts 504 times, in candela 683 times.

**Colour temperature** (`REDSHIFT_LIGHT_PHYSICAL_COLORMODE`: Color 0, Temperature 1, Temperature and Color 2; `_TEMPERATURE` in kelvin). Redshift takes the chromaticity of the Planckian locus, by Kim et al. (2002) from 1667 K and by Krystek (1985) below (each matches where the other does not: at 1000 K Krystek 0.0086 for green, Redshift 0.0086; at 20000 K Kim 0.4053, Redshift 0.4060), holds the temperature to 1000 to 20000 K (500 and 800 K render as 1000 K, 25000 and 40000 K as 20000 K), makes it a colour of the **render space** (XYZ → linear Rec.709; for ACEScg on with OCIO's Bradford-adapted matrix), cuts negative parts off, and divides by the largest part: brightness is not kept (3000 K in ACEScg is (1, 0.650, 0.263), 10000 K (0.686, 0.724, 1)), and 6500 K is not white ((0.995, 0.961, 1) in ACEScg, (1, 0.942, 0.990) in linear Rec.709: the locus misses D65). "Temperature and Color" multiplies that by the colour. The plugin computes the same (`RedshiftTemperatureColor`, `DocumentColors::FromXyz`): within 0.003 of Redshift's colour at 1500 to 20000 K in ACEScg and in linear Rec.709. Before 0.2.0 the temperature was not read: such a light rendered in its colour (white by default), so a 3000 K light was 1.5 times too bright in green and 3.8 times in blue, a 10000 K light 1.5 times too bright in red. Blender's own temperature (`use_temperature`) is not used: Blender's black body keeps the brightness and is white at 6500 K, Redshift's does neither. In "Basic" colour management the colour is computed in linear Rec.709 [untested against Redshift: there Redshift's picture of the plain grey floor already differs from Cycles Render's, 0.53 against 0.62 with Linear Workflow, a matter of materials or the picture, not of lights].

**Area light settings.**

- *Spread* (`_AREA_SPREAD`, 1 by default): within the half angle s × 90° Redshift's light is the diffuse one times 1 / (1 − cos(s × 90°)), beyond it nothing (a 10 cm light 1 m over the floor: s 0.8 gives 1.447 to 72°, s 0.5 3.414 to 45°, s 0.3 9.17 to 27°; Redshift's picture caps a sample's luminance near 21, which hides more below 0.25). Cycles' spread (Blender's full angle) falls from the axis with the tangent of the angle to nothing at half the spread and keeps the power (`intern/cycles/kernel/light/area.h` and `scene/light.cpp`, read; this model reproduces Cycles' measured floor to 2 %). The two cannot agree everywhere; the plugin takes, per s, Blender's half angle and a factor for the power that come closest to Redshift's floor under a small light (least squares of its brightness, weighted by the floor's area, to 80°; a table in steps of 0.05 in `RedshiftSpread`, from (0°, × 2.0) at s = 0 over (36.4°, × 1.93) at 0.3 and (61.9°, × 1.84) at 0.5 to no spread and × 1.18 at 0.9). Residual on that floor: 2.8 % (s 0.8), 23 % (0.5), 34 % (0.3) RMS; a light with a spread is named in the console. Under a 2 × 2 m light 2 m above the floor (the test): 1.003 (s 0.8), 1.028 (0.5), 0.932 (0.3) of Redshift below the light, 0.95 to 1.33 at the other patches Redshift lights; the rule that matched only the small light's axis and its power gave 0.977, 0.846, 0.754 there (a model of both profiles integrated over the light reproduced these to 2 %, so the table was chosen by it). Before 0.2.0 the spread was not read: a 2 × 2 m light 2 m above the floor with s 0.5 rendered 0.29 of Redshift under it, with s 0.2 0.12: **the cause of area lights that looked too dark**, together with the scale.
- *Bi-Directional*: both sides shine, each as the light alone (the side below unchanged, 1.00). Blender's area light shines to one side: a second item, `<id>_back`, the same light turned half a turn about its Y axis (`BackLightId`).
- *Visible* to the camera: the ray contribution "Camera" (`REDSHIFT_LIGHT_CAMERA_RAY_CONTRIBUTION_SCALE`, 10042, in the 2025 SDK on; 1 by default; a light made from Python is seen). `_AREA_VISIBLE_IN_RENDER` (11012) is labelled "Blocks Rays" in this Redshift and changes nothing seen here. Sent as the light object's camera visibility for rectangles, discs and ellipses: seen from the front a rectangle of intensity 0.2 shows 0.2 in both. A sphere is seen by Redshift with twice its radiance (both sides of a shell that lets light through: 2.0 for intensity 1, from above) and Blender's sphere light with its radiance once; spheres and cylinders are not made visible.
- *Shapes:* a cylinder runs along the light's Z by Size Z with the diameters Size X and Size Y (seen from above unturned: 40 by 160 for 40, 80, 160) and emits from its side; a round tube lights the floor below it as a diffuse tube of **twice** its radiance would (1.92 to 2.14 at six patches; with elliptic sections Redshift departs from any diffuse tube, measured but not understood). Blender has no tube: it is sent as a sphere of the mean diameter as bright as the tube from its side (radiant intensity 2 L d l, power 4π of that); under its middle within 7 %, along its axis too bright (1.5 at the end beyond 250 cm). A mesh shape is not read (a rectangle of the light's size, named).
- Not read, each named in the console: the texture (`_TEXTURE`), a mesh shape; not named: opacity, "Blocks Rays".

**Decay** (`_DECAYTYPE`: Inverse-square 0, None 1, Linear 2; `_FALLOFFSTART`, `_FALLOFFSTOP` in document units, 0 and 100 by default). "None" is as bright at any distance as the inverse square is at 1 m (a floor 1 m below: 1.59 in both; at 1.41 m None 2.05 times the inverse square). "Linear" is None times a ramp from 1 at Start to 0 at Stop (with Start 0, Stop 300 cm: 1.059 at 1 m, (1 − 1/3) of None); Start and Stop do nothing for the other two. So a "Linear" light with Redshift's defaults renders nothing beyond 1 m. Blender has only the inverse square: "None" is matched at 1 m (the light unchanged), "Linear" halfway between Start and Stop (power × 0.5 × d², d that distance in metres); each named in the console. Measured with the rule: None 0.98 at 1 m (0.06 at 3.6 m), a 50 cm area light 0.95; Linear 1.05 at 1.41 m (0.90 to 1.67 elsewhere). Before 0.2.0 both were sent as the inverse square at full strength (None the same as now; Linear 0.94 at 1.41 m in this case, but with Redshift's default Stop of 1 m a light Redshift renders black beyond 1 m).

**Spot.** The cone angle is the full angle and the falloff angle lies inside it (Blender: `spot_size` = cone, blend from cone − 2 × falloff). Inside the cone the light is the same (1.000); the edge differs: Redshift fades linearly in the angle, Blender's spot by a smoothstep in its cosine, so in the fade Cycles differs by 0.68 to 1.1 (cone 60°, falloff 20°). The falloff curve (`_SPOT_CONE_FALLOFF_CURVE`, 0 by default) darkens the cone towards its edge like cos^curve (2: 0.78 at 27°, 5: 0.54); not translated, named.

**Eevee** with the corrected values (Blender 5.2.3, Light Threshold 1e-4, see below): as close to Redshift as Cycles for every exact case (worst patch 0.1 % to 3.4 %: rectangles, discs, ellipses and spheres in every unit, scaled, bi-directional, the point, spot and infinite light, the temperatures), the decays and the cylinder as Cycles (within 0.5 %). Eevee departs by itself in two ways. It **ignores Spread**: such a light is as wide as a plain one at the power the plugin gives it (s 0.8: 0.985 under the light, s 0.5: 0.54, s 0.3: 0.25 of Redshift; the plain light at that power is exactly that). And it leaves a light out beyond sqrt(max colour × power / 100 / Light Threshold) metres (`eevee_light.cc`, `attenuation_radius_get`; the Render Settings' Eevee "Light Threshold", 0.01 by default), and Redshift's physical intensities are small in Blender's terms: an area light of 2 × 2 m and intensity 1 is 12.6 W and ends 3.5 m away, one of 50 cm and intensity 4 (π W) 1.8 m away, a point light of 2000 lm (2.9 W) 1.7 m away; inside that distance it fades. Measured with the default threshold: 0.81, 0 and 0 of Redshift under these lights 2 m below. A lower Light Threshold (or Eevee's "Custom Distance" of a Cycles Light tag) brings them back; the test compares Eevee's own light with 1e-4.

**The Cycles Light tag** on a Redshift light: "Take Values from the Light" takes all of the above (the temperature as a colour of the document's render space, the size with the scale, spread, a sphere's soft falloff off; `DocumentColors::Stored`), and the Light tab then renders as the light (an area light with temperature and colour, scale and spread: difference 0.000); the light's camera visibility stays the light's own unless the tag's Visibility tab is on; the back side of a bi-directional light is not part of the tab (the tab replaces what the light emits). **The IPR**: each new value (temperature, scale, spread, unit, camera, bi-directional on and off, shape) is sent by the light-only update as one item (bi-directional: its other side as a second; moved, both; off, the other side removed) and agrees with a whole export ("verify" clean).

**Redshift's own render settings** (its video post, 1036219, in the document's render data; a scene set up for Redshift keeps it when Cycles Render is chosen) [T in 2027]: "Image Units Scale" (`REDSHIFT_RENDERER_IMAGE_UNITS_SCALE`, 1803, from Redshift 2026 on, 100 by default) makes a point or spot light in "Image" (scale / 100)² as strong (50: 0.25, 200: 4.00, 1: 1e-4); candela, the other units, area and infinite lights do not change. The plugin reads it (`RedshiftImageUnitsScale`; without a Redshift video post 100). "Photometric Units to Meter Scale" (1801, 100), "Candela Meters Squared Factor" (1802, 10000) and the unit scale (`REDSHIFT_RENDERER_INTEGRATION_EXPORT_SCALE`, 25002, 1 cm) changed nothing in Redshift 2027.0.0 (each doubled, or 1 m).

**Redshift 3.6.04** (the Redshift of Cinema 4D 2024.5.1 here; 2026.3.4's Redshift counts as 2027's, all units measured alike) [measured with probes, 2026-11-18, not translated]: its lights offer the units 0 to 4 only (setting 5 is refused). It counts otherwise: a point or spot light in "Image" depends on the unit scale (1 cm, the default of a new document from Python: 8.4e-5 where 2027 gives 0.792, about 1e-4; 1 m: 0.792, as 2027), so does a normalized area light (1 cm: 0.000367 where 2027 gives 3.653); the photometric units of area lights are 683/10000 = 0.0683 of 2027's (lumen, cd/m², watt, W/sr/m² alike: the constant 10000 where 2027 has 683), and follow "Photometric Units to Meter Scale" (doubled: 4 times) and "Candela Meters Squared Factor" (doubled: half); a point or spot light in lumen or watt is v / (10000 π) (η for watt) whatever the cone; an infinite light in lumen v / π, in watt v η / π (clamped at Redshift's 21.1), in cd/m² v / 10000. ### Soft and area shadows

[T: probes in c4dpy 2027.0.0 with Blender 5.2.3, 2026-11-17, then `tests/c4d/light_shadows.py`, section 6] Code: `ApplyShadowSoftness` in `scene/light_export.cpp`. With the light at height D and the plate at D_o, g = (D − D_o) / D_o, the ratio of the gaps (1 for the plate halfway).

- **Which settings count.** Raytraced (Hard) and None: sharp (W 1.4, a pixel). Area, omni or spot: the source is the Details tab's area shape (`LIGHT_AREADETAILS_SHAPE`, Rectangle by default, `_SIZEX`/`_SIZEY` 200 × 200; shown for these lights whatever the shadow type) with Accuracy and Minimum/Maximum Samples (noise only). Area, infinite light: `LIGHT_AREADETAILS_INFINITE_ANGLE` (100024, 0.5° by default). Shadow Maps (Soft): the map's size (`LIGHT_SHADOW_MAPSIZEX`/`Y`, 250 by default; the menu `LIGHT_SHADOW_MAPSIZE` sets them), its sample radius (`LIGHT_SHADOW_SAMPLERADIUS`, 3), for a spot the cone, for an omni "Shadow Cone" (`LIGHT_SHADOW_USECONE`, `_CONEANGLE`), for an infinite light the parallel width (`LIGHT_SHADOW_PARALLELWIDTH`, 500); the bias was not varied.
- **The Standard renderer, Area, omni or spot: physical.** A rectangle of side s across the edge: W = 0.795 s g (200: 159.1, 100: 79.0; 300 × 100 with 300 across the edge 236.2, the other way round 79.2; g = 1/3: 52.3 for 53.0 expected); a disc of diameter d: W = 0.678 d g (135.7); a sphere: W = 0.826 d g (165.2); a spot alike (156.9).
- **The Standard renderer, Area, infinite light:** W = 1.567 x · gap, x the Infinite Angle in radians (0.5°: 3.4; 5°: 34.2 at a gap of 250, 69.1 at 500).
- **The Standard renderer, Shadow Maps: not physical.** The blur is a fixed angle seen from the light, whatever the caster's place: W = 1.1 (R + 1) · 2 tan(F/2) / N · D, R the sample radius, N the map size, F the map's field (90° for an omni's cube face, the cone for a spot), D the light's distance to the floor (omni default 17.6; map 1000: 4.5; R 6: 30.9, R 1: 8.8; twice the distance 35.2, also with the caster at a quarter; a spot of 60° 10.3, of 150° 69.3). An infinite light's blur is a fixed width: W = 1.1 (R + 1) P / N, P the parallel width (8.8; P 1000: 17.6; map 1000: 2.5; the same at every gap).
- **Blender, Cycles:** a point or spot light of radius r gives W = 1.391 r g (r 50: 68.7, 100: 139.1, g = 1/3: 45.8); a sun of angle a (its angular diameter, radians) W = 0.692 a · gap (5°: 15.1). Eevee draws these edges narrower: r 100: 114 (0.82), sun 5°: 10.5 (0.70).
- **The rule** (Area as physical as the light allows; Soft an approximation):

  | Light | Area shadow | Shadow Maps (Soft) |
  |---|---|---|
  | omni, spot | radius = equal-area disc √(X·Y/π) for a rectangle (and, with a note in the console, the other shapes); X/2 for a disc; 0.594 X for a sphere or hemisphere (0.826/1.391, Cinema 4D's sphere casts a wider edge than a disc) | radius = 1.1 (R + 1) · 2 tan(F/2) / N · L / 1.391, L the light's Radius/Decay (its reference distance, the one the brightness is matched at): the same edge at that distance with the caster halfway |
  | infinite, parallel | angle = 1.567 / 0.692 · Infinite Angle = 2.26 x | angle = 1.1 (R + 1) P / N / (0.692 · L/2): the same edge with the caster at half the reference distance from the floor |
  | area light (also shaped as a sphere) | its own size, whatever the shadow type (the same picture for all four, tested) | the same |

  Measured with the rule (Cycles against the Standard renderer): Area square 200 158.6/157.8, 100 77.8/78.6, disc 139.1/133.6, sphere 166.5/164.3, caster at a quarter 51.6/52.5, spot 158.6/158.7; infinite 0.5° 3.7/3.5, 5° 34.0/34.7, gap 500 67.9/68.2; Soft omni 17.4/17.6, map 1000 4.5/4.5, R 6 30.4/30.9, spot 150° 64.9/69.3, infinite 8.8/8.8, P 1000 17.5/17.6. Eevee: square 200 125.3, Soft omni 16.7, infinite 5° 24.0 (narrower, as above). A Soft shadow away from the geometry it is matched at departs as a physical edge must: an omni with the caster at a quarter of the way gives 6.0 against Cinema 4D's 35.2 (a physical light's edge narrows as the caster nears the floor; a shadow map's does not).
- **Side effects of a light with a size:** a translated light is a sphere (or a sun with a disc) in Blender, so its highlights on glossy surfaces are a disc of that size and softer, and a mirror shows it as a disc; the Standard renderer's highlight of the same light does not change with its shadow type. It is not seen by the camera (Blender's default for these lights, as before). Its brightness is unchanged beyond its radius (power is kept); within about its radius Blender's "Soft Falloff" (on) evens the light out (by Blender's manual; not measured).
- **What wins:** an area light's own size (and a sphere-shaped area light's radius); a Cycles Light tag's Light tab (its radius or angle replace everything, as all its values do; "Take Values from the Light" takes the radius the shadow type gives); its Settings tab's Cast Shadow off (no shadow at all). The Cycles Light object and Redshift lights are not touched. A visible light's settings (Visibility tab) are not translated and play no part.
- **The IPR**: changing the shadow type, the area size or the sample radius is a light value like any other: it is sent alone during a drag (F18) and agrees with a full export (`ipr_lights`: four such changes, one item each, "verify" clean).

The green check off at the change event takes its items out (also `verify` clean).

Whether the Noise shader uses the same is not known (its picture was not compared).
- **The cost of the noise** (FBM, 3 octaves, a box of 200 x 140 x 200; the grid follows the box: 64 cells along the longest edge give 64 x 45 x 64): sampling 4 ms, saving 12 to 23 ms, 0.66 MB; 128 cells 19 ms and 54 to 64 ms, 5.0 MB; 256 cells 91 to 100 ms and 340 to 380 ms, 38 MB; 5 octaves at 128 cells 27 ms to sample. Saving costs more than sampling at every resolution. The file is reused while nothing it follows from changes (the noise's values, the size, the resolution; the time only while the speed is not 0; the fog's matrix only in world space): measured in the IPR, a whole export with nothing changed and one after a move kept the file, another seed and another frame of a moving noise wrote a new one. A render document is a copy with new GUIDs, so a final render writes the file once per render job (as Volume Builder grids).
- **In the IPR a fog with a noise is a volume**: a step that moves it needs a whole export (reason 6, `WHOLE::FIXED`); after it `verify` finds no difference.

- **A field list on the object itself works**: a `FIELDLIST` parameter (`FIELDLIST id { ANIM ON; NEWLINE; NOCOLOR; NODIRECTION; NOROTATION; }`, as Cinema 4D's own vertex map tag has one; its default `GeData(CUSTOMDATATYPE_FIELDLIST, DEFAULTVALUE)`), sampled with `FieldList::SampleListSimple(*scatter, FieldInput(positions, count, scatter's global matrix), FIELDSAMPLE_FLAG::VALUE)` (the same in the four SDKs): with a Spherical field of radius 100, 2,000 copies all within it (farthest 99.86) as density, and with "Scale" the copies scaled by it (1.0 at the centre, 0 outside).

## Cameras and views

Measured against the Standard renderer in c4dpy, 2026-11-12, on the arrows-and-ball scene of `tests/c4d/coords.py` and on glowing balls in known directions [T: `tests/c4d/cameras.py`, `tests/c4d/camera_tag.py`; the code is `scene/camera_export.cpp`]. - **Perspective and Parallel use the camera's rotation; the fixed views do not.** A camera turned by (32°, -22°, 12°) renders exactly the picture of an unturned one. A fixed view looks along its own axes from the camera's position (the picture is centred on it), with the width of a parallel view (1024 units at `CAMERA_ZOOM` 1). The axes are what `BaseView::GetMg()` gives for a view of that projection (right, up, forward): Left (0,0,-1) (0,1,0) (1,0,0); Right (0,0,1) (0,1,0) (-1,0,0); Front the identity; Back (-1,0,0) (0,1,0) (0,0,-1); Top (1,0,0) (0,0,1) (0,-1,0); Bottom (1,0,0) (0,0,-1) (0,1,0); Military, Frog and Bird (-√3/2,0,1/2) (-1/2,0,-√3/2) (0,-1,0), a top view turned by 30°; Gentleman the identity; Isometric (-1/√2,0,1/√2) (-1/√6,2/√6,-1/√6) (-1/√3,-1/√3,-1/√3); Dimetric (-0.937086259,0,-0.349097899) (0.115059725,0.944123613,-0.308855731) (0.32959157,-0.32959157,-0.884725265).
- **Oblique views.** Military, Frog, Bird and Gentleman are oblique parallel projections: `BaseView::GetViewParameter()`'s `scale_z` moves a point at depth z by (scale_z.x · z, -scale_z.y · z) across the picture (the SDK's `CameraToScreen`): Military (0, 1), Frog (0, 2), Bird (0, 0.5), Gentleman (0.3536, -0.3536). The rays then travel along right · (-scale_z.x) + up · scale_z.y + forward, not perpendicular to the picture. Blender's orthographic camera reproduces that when its matrix carries the slant (`docs/reference/blender.md`, "Cameras"); all four match the Standard renderer.
- **Clipping.** A parallel camera clips nothing behind its plane: the part of the scene behind the camera renders (a camera at z = 0 inside the scene showed the ball at z = -80). Its near and far clipping count, measured from the camera (near 400 left only what lies beyond 400, far 380 only what lies before it). A negative near clipping reads back as 0. The fixed views clip nothing at all and ignore both settings. Perspective clips as set. The exporter moves Blender's orthographic camera 10 km back along its rays where nothing is clipped (`UNCLIPPED_DEPTH`) and lets it see as far again beyond the camera's plane (or to the far clipping).
- **The editor's views** (no camera object: `GetRenderBaseDraw()->GetEditorCamera()`, or the active view's for the IPR): the view's projection is `BASEDRAW_DATA_PROJECTION`, and `GetEditorCamera()` then returns a camera of that view whose `CAMERA_PROJECTION` is the view's. For the fixed views it is a camera of its own, at the origin and unturned in a new document; its position (the pan: moved to (100, 500, 30), the Top view's picture moved with it) and its `CAMERA_ZOOM` count, its rotation does not (a turned one rendered the same). So the editor's views are read exactly as camera objects. In c4dpy, `BaseView::GetMg()` gives the view's axes but a stale position ((600, 300, -600), the Perspective view's camera), so the plugin does not use it. The Perspective view's editor camera is an `Ocamera` (5103) with near clipping **on at 0** in Cinema 4D 2024.5 and 2026.3 and an "RS Camera" (1057516) with it off in 2027.0 (2024 and 2027 in c4dpy and the application, 2026 in c4dpy; [T] 2026-11-17, `tests/c4d/editor_camera.py`); both at (600, 300, -600), 35 mm, sensor 36. A near clipping of 0 clips nothing in front of a perspective camera; the plugin had sent it as Blender's smallest clip start, which made Eevee render no light (B10; `docs/reference/blender.md`, "Cameras"). Now a near clipping of 0 gives the default start (1 cm), and every start is at least 1 mm and at least a millionth of the clip end (`ClipRange`); for Cycles that only clips what lies within 1 mm of the camera.
- **The spherical camera** (`CAMERAOBJECT_SPC_ENABLE` with the lat-long mapping, `SPC_MAPPING_LATLONG`): the Standard renderer draws an equirectangular picture. Longitude grows from the camera's forward axis towards its right, the whole turn across the width; latitude 90° at the top. The range `CAMERAOBJECT_SPC_LONG_MIN`/`_MAX`, `_LAT_MIN`/`_MAX` (radians) does three different things: without "Fit Frame" (`CAMERAOBJECT_SPC_FIT_FRAME`) the whole sphere is drawn and what lies outside the range is black; with it the range fills the frame, and then latitude is upside down: the picture's top is -(Lat Min) and its bottom -(Lat Max) (a range of -30° to 60° showed latitude 30° at the top and -60° at the bottom); "Full Range" (`CAMERAOBJECT_SPC_FULL_RANGE_ENABLE`) ignores the range. The exporter sends Blender's equirectangular panorama with longitude as it is and latitude turned over (matches within 0.6 pixels); the cropping without Fit Frame, the cubic mappings, the dome and a spherical camera with a parallel projection are named in the console and rendered as the whole lat-long sphere [the last three untested].
- **The camera's own focus object** (`CAMERAOBJECT_TARGETOBJECT`): once the document is evaluated, Cinema 4D writes its distance into `CAMERAOBJECT_TARGETDISTANCE`, measured along the camera's view axis (1400 for an object 1400 ahead and 300 aside; the straight distance is 1432). So the camera's own depth of field already follows it. Blender measures a focus object the same way (`docs/reference/blender.md`).

**The Cycles Camera tag** (`tags/camera_tag.cpp`, ids in `res/description/tcyclescamera.h`) [T: `tests/c4d/camera_tag.py`, `show_camera_tag.py`]:

- Two tabs, Depth of Field and Lens. With `DEFAULT 1` on both, the Attribute Manager shows both at once and the Lens tab's panorama settings fell below its lower edge (screenshot); with `DEFAULT 1` on the first only, opening the Lens page (`ActiveObjectManager_SetObject(..., page)`) shows it alone.

Verified on screenshots of every tab.
- **Depth of field of a tagged camera is the tag's alone** (the maintainer, 2026-11-12, as on Blender's camera): the box checked gives depth of field with the tab's values whatever the render setting says, unchecked (the default) none whatever the camera's own values and the render setting say. Measured (`camera_tag.py`, rim pixels of a near and a far box, sharp 327/434): the camera's own focus with the render setting on and no tag 467/3601; the same camera with a tag just added, unchecked, 327/434 (sharp). Cameras without the tag keep Cinema 4D's own depth of field through the render setting. Until that decision id 1000 was a choice of three ("as the camera says", "on", "off"); the tag was never released, so the id became the BOOL.
- A REAL field shows few decimals: Blender's default polynomial coefficients (about 1e-5 and less) read 0 in the Attribute Manager although they are stored and sent exactly. Not changed.
- A LINK field (`LINK id { ACCEPT { Obase; } }`) is read with `BaseContainer::GetObjectLink(id, tag->GetDocument())`; in a render's copy of the document the link resolves to the copy's object.
- The icon is `res/icons/camera_tag.png`, drawn by `tools/make_icons.py` (`camera_tag`): the plugin's hexagon in dark grey with a lighter, shaded circle. In the Object Manager at tag size the circle reads clearly; the dark hexagon stands only a little apart from the manager's dark background (screenshot).

## Volumes, hair, particles

- `VolumeObject` (`Ovolume`, `CF/c4d_libs/lib_volumeobject.h`): `GetVolume()`. Found inside the Volume Builder's cache.
- Volume Loader (`Ovolumeloader`): file path in `ID_VOLUMESEQUENCE_PATH`.
- Write VDB: `maxon::VolumeToolsInterface::SaveVDBFile(url, scale, volumes, meta)` (`SDK/frameworks/volume.framework/source/maxon/volumetools.h`).
- Pyro output (`Opyro`, `DESC/opyro.h`): cache path `PYRO_OBJECT_CACHE_PATH`.
- Hair: `HairObject` (`CF/c4d_libs/lib_hair.h`), `GenerateHair` → `HairGuides`.
- Particles: `ParticleGroupObject` (`CF/c4d_libs/lib_particlegroupobject.h`): `GetParticlePositionsR`, `ColorsR`, `VelocitiesR`, `RadiiR`.
- Compositing tag (`Tcompositing`, `DESC/tcompositing.h`): `COMPOSITINGTAG_CASTSHADOW`, `_SEENBYCAMERA`, `_SEENBYRAYS`, `_MATTEOBJECT`.

- **A .vdb file is right-handed; Cinema 4D reads and writes it with Z negated** [T: `tests/c4d/volumes.py`, `depth_from_the_side`]. Blender reads the file as it is, so the volume item's matrix negates the file's Z besides swapping the axes (`Coords::RawMatrix`). A check from the front cannot see the difference; this one looks from the side at a ball off-centre along Z.
- Grids from other programs have the class "unknown" (EmberGen: `density`, `flames`); only distance fields are left out. A fire grid that is no temperature (`flames`, 0 to about 4) drives the emission's strength instead of a black body's temperature (the tag's "Fire Grid Holds"; `volume_export.cpp`).
- Particle rotation: `GetParticleAlignmentsR()` gives `maxon::Quaternion<Float32>` (`w`, `v`). MoGraph matrices of a Matrix object: the `MoData` of its `ID_MOTAGDATA` tag, as for a Cloner; the matrices are in the Matrix object's axes.
- A Matrix object (`Omgmatrix`) carries `BIT_CONTROLOBJECT` itself, as a Hair object and a Redshift light do.
- The Cycles Object tag (`tags/object_tag.cpp`, ids in `res/description/tcyclesobject.h`): four tabs, each with an enable checkbox; an enabled tab counts for the object and everything below it until another tag with that tab enabled. An in/exclude list in a description: `IN_EXCLUDE ID { SCALE_V; NUM_FLAGS 0; INIT_STATE 0; ACCEPT { Obase; }; }`; read with `GeData::GetCustomDataType<InExcludeData>()` and `ObjectFromIndex(doc, i)`. In Python `InExcludeData.InsertObject(obj, flags)` puts each object on top of the list.

## Node space (the Cycles nodes)

All [T: `tests/c4d/cycles_nodes.py`] unless marked. Model: `SDK/plugins/example.nodes`. Frameworks: `nodes`, `nodespace`, `graph`, `corenodes`.

- A node space needs no description database (.json) to work (but see "How a node looks" below). Nodes can be made in code: a `Component<..., maxon::nodes::NodeTemplateInterface>` (base `NodeTemplateBaseClass`) whose `InstantiateImpl` creates the ports: `parent.CreateNodeSystem()` → `root.GetInputs().AddPort(id)`, `port.SetType<T>()`, `port.SetValue(maxon::NODE::BASE::NAME, label)`, `port.SetPortValue(default)`; an output gets `SetValue(maxon::nodes::Dynamic, true)` and every input a `Connect(output, Wires(Wires::DEPENDENCY))`; a value-only port gets `SetValue(maxon::nodes::ConstantParameter, true)`; order by `ReqOrderIndex`; `root.SetValue(NODE::BASE::NAME / COLOR, ...)` gives the node its title and header colour; end with `root.SetTemplate(self, args)` and `root.EndModification()`.
- A dropdown is a port of type `maxon::Id` whose options are in the node's description (`data.base.enum`); its value is the id of the option. (An enum type of its own, `DataTypeLib::GetEnumType`, works too but shows the ids instead of the labels.)
- Many nodes from one class: `Class.Create()`, set the instance's data through `Component::Get(ref)` (a `mutable` member, the reference is const), `SetId({id, Id()}, 0, AssetInterface::GetBuiltinRepository())`, then `maxon::nodes::BuiltinNodes::Register(id, template)` and keep the returned `GenericData`.
- The space: a `Component<..., NodeSpaceInterface>` (base `NodeSpaceBaseClass`); its data dictionary can be filled in code: `NODESPACE::SPACEID`, `SPACENAME`, `RENDERERS` (plugin ids of the renderers it belongs to: choosing that renderer makes it the active space), `SPACEKIND`; in `Init`: `CREATEMATERIALGRAPHFUNC` (the default graph), `MATERIALENDNODEIDS`, `NODESYSTEMCLASS`, `DISABLE_PREVIEWS`. Register with `MaterialNodeSpaces::Register(id, space)` in a `MAXON_INITIALIZATION`.
- **Register the space's component under the space's id** (`MAXON_COMPONENT_OBJECT_REGISTER(Class, "<space id>")`): `GetActiveNodeSpaceId()` and the key of a material's graph are the component's id, whatever `SPACEID` says.
- A node system class of its own (`Component<..., NodeSystemClassInterface>`, base `BaseCoreNodesNodeSystemClass().GetClass()`) lets the space's own nodes in: a node template answers `SupportsImpl(cls)` with `cls.GetClass() == OwnClass::GetClass()`. It does not keep all of Cinema 4D's own out: what else may join is the base class's rule, and the Wire Rerouter (`net.maxon.node.reroute`, its ports `in` and `out`) and a scaffold (`net.maxon.node.scaffold`) went into a Cycles graph from Python (`graph.AddChild`) [T: `tests/c4d/cycles_nodes.py`, section 10, c4dpy 2027.0.0, 2026-11-19]. The exporter leaves out every node without an entry in the table, with its wires, and names one that is wired (`maxon::GraphModelHelper::GetDirectPredecessors`/`GetDirectSuccessors`; its name is the `maxon::EffectiveName` attribute, "Wire Rerouter" for the reroute).
- **Only `Mmaterial` carries a node graph.** For a material type of a plugin (`MaterialData`), `NodeMaterial::CreateDefaultGraph` fails with "baseMaterial.IsInstanceOf(5703) not fulfilled", whatever `c4d_basematerial.h` says about any BaseMaterial. Settings that belong to the material as a whole are therefore value-only ports of the end node.
- Commands: Node Editor 465002211, its material mode 465002360 (call it after the editor has opened).- **An image dropped on the Node Editor** [code read in the SDK; T as far as a script reaches, `tests/c4d/image_nodes.py`]: the space names the node to make (`NODESPACE::IMAGENODEASSETID`) and four of its ports (`IMAGENODEPORTS`, NodePaths): a `maxon::Color` output, the `maxon::Url` input, and two `maxon::Int` inputs for the first and last frame of a sequence; the SDK's handbook ("Implementing Texture Nodes") says a texture node "has to provide at least" those four. The Cycles Image Texture node got the two frame ports as settings that never show (`tools/make_nodes.py`). `NodeSpaceHelpersInterface::GetNodeSpaceData(spaceId)` gives the data back; the test hook makes a node from it as the drop does, and that node renders the image. A real drop (a mouse) cannot be made by a script: untested.
- **A button on a node** [T in part]: Maxon's own Image node has buttons ("Reload Image" and others): in the description's layout, a "group" entry with `ui.base.groupcolumns` and per button an entry with the command "command", the identifier of a command, and `ui.base.commandtype` "button"; the label is a "command" entry with `string.base.translatedstring` in the names; nothing in the data (read in the installation's `resource.zip`, `shadernodes.module/net.maxon.patterns.module.db*.json`). The identifier is a command of the maxon command system: a `Component<..., maxon::CommandClassInterface>` registered with `MAXON_COMPONENT_OBJECT_REGISTER(Class, maxon::CommandClasses, "<id>")` (`command.framework` in the module's apis; no plugin id). Its data should carry `ARGUMENTS::NODECORE::GRAPHMODEL` and `NODEPATH` (`datadescription_nodes.h`; `INNERPORTPATH` is called "mandatory for all button messages" there, so the plugin's commands take a node from `NODEPATH`, `NODEPATHLIST` or that port, whichever comes). The buttons show in the Node Editor's attributes (screenshot `image_node_buttons`); invoking the command through `CommandDataRef::Invoke` with those two keys works (`image_nodes.py`). A posted mouse click on the button only highlighted it (as it only highlights a dropdown there, which does not open): neither `GetState` nor `Execute` was called, so what a real press hands over is untested; `g_cyclesRenderLogPathCommands=true` writes it to the console.
- **A relative path in a Url port:** `maxon::Url("tex/card.png")` has `URLSCHEME_RELATIVE`; the port's field shows it as "tex/card.png" (screenshot `image_node_relative_path`). `GetComponents` gives the parts of a file Url ("C:", folders, name); `Normalize()` resolves ".." after joining a relative Url to a folder with `+`.
- **Thumbnails of a node space's materials** [T: seen in the application, `tests/c4d/show_cycles_node_ui.py`]: the space names a function (`NODESPACE::CONFIGUREPREVIEWIMAGEREQUESTFUNC`) that puts the class of a `maxon::nodes::PreviewImageProviderInterface` component into each request (`PREVIEWIMAGEREQUEST::PROVIDER`). `Initialize` gets the size (`TEXTURESIZE`) and the node (`SUBJECT`; `subject.GetGraph()` is the graph) and runs while the graph may be read; `ComputeIteration` runs on a job thread and must not touch the graph or a document; `TakeOutput` hands over RGBA float samples, top row first, except for a request with `PREVIEWIMAGEREQUEST::FLIPVERTICALLY` true, which wants the bottom row first: the SDK header says that flip "is performed automatically on the provided buffer", but in 2027.0 it was not, and the Attribute Manager's big preview showed the ball upside down until the provider flipped the rows itself [T: `tests/c4d/show_material_preview.py`, a material red at the top, screenshot]. The requests seen for a material in the Attribute Manager and the Material Manager, all with `INTENT_NODE2D`: the big preview in the Attribute Manager 120 × 120 with the flag and `PROGRESSIONTHRESHOLD` 16; the thumbnail (Material Manager, the Attribute Manager's header, `BaseMaterial.GetPreview`) 90 × 90 without the flag, threshold 0. The same provider serves the material's thumbnail and the preview of every node. `NODESPACE::DISABLE_PREVIEWS` switches all of it off. To keep the thumbnail but nothing of it in the Node Editor, each node's description gets an attribute `net.maxon.node.base.displaypreview` with the default false (no preview on the node; setting `NODE::BASE::DISPLAYPREVIEW` on the template's root did nothing), and layout entries with `ui.base.show` "false" for the group `net.maxon.node.base.preview` (the "Preview" tab of a selected node), the attribute `net.maxon.node.base.nodepreviewimage` and `net.maxon.node.base.displaypreview` (the preview button on the node). Since 0.2.0 nodes newer than the oldest supported Blender keep a preview, their version card (see "A node the chosen Blender does not have"). Where a sample's alpha is below 1, Cinema 4D draws a checkerboard in the thumbnail, so a background has to be part of the picture. In `c4dpy` no preview is ever asked for: `GetPreview()` returns the checkerboard placeholder.
- **The samples are shown through the plain sRGB curve, whatever the document's colour management** [T, 2026-11-12, application, clean preferences: the thumbnail of a Cycles material that is one Emission of 0.5 read back with `GetPreview(0)`]: 188 in an OCIO document (ACEScg, ACES 2.0 SDR-video view, also for thumbnails), 188 in a "Basic" document with Linear Workflow and 188 without; an Emission of (0.8, 0.3, 0.1) shows (231, 149, 89) in all three. The request carries no document and no colour setting. A final frame of the same value shows as 144 in OCIO (through the view transform), 188 in Basic with Linear Workflow and 128 without (the strips under "Colour management"), so the thumbnails agree with renders only in Basic mode with Linear Workflow.
- A regular Cinema 4D for a test without the user's preferences: `g_prefsPath=<empty folder>`. Needed when a copy of the plugin is installed: of two modules with one id Cinema 4D loads one and skips the other ("Skipping module ... for better matching version"), and `g_additionalModulePath` does not decide which. Such a start shows the "Cinema 4D Home" window, and its layout has no Material Manager: `c4d.CallCommand(12159)` docks one [T: `tests/c4d/show_material_preview.py`].

### How a node looks: the description database

All [T: `tests/c4d/show_cycles_node_ui.py`] unless marked.

- Cinema 4D looks up a description by the node's id. A node built in code needs no description processor: registering a database with a description under the same id is enough (`DataDescriptionDefinitionDatabaseInterface::RegisterDatabaseWithUrl(databaseId, folder)`; the files are `<databaseId>.db.json` for data and layout and `<databaseId>.db.<language>.json` for names; unregister on exit). The SDK's example node "invertnode" is made this way.
- The file is the serialised form the Resource Editor writes; `tools/make_nodes.py` writes it directly. A description is a list of entries (dictionaries) under the node's id, once per category: data (`_descriptions`), layout (`_guiDescriptions`), names (`_db` in the language file). Every list starts with an include of `net.maxon.node.base`. Model: `SDK/plugins/example.nodes/res/nodes/*.json`.
- An entry has `net.maxon.description.base.command` ("attribute" for a port, "group", "string" for the name of a dropdown option, "exportedstring" for the node's own name under the identifier `net.maxon.object.base.name`) and `...base.identifier` (the port's id).
- Data of a port: `data.base.classification` (input, output), `data.base.datatype`, `data.base.defaultvalue`, `data.base.enum` (the options of a dropdown), `net.maxon.node.attribute.constantparameter` (takes no wire), `net.maxon.node.attribute.hideportinnodegraph` (not on the node at first; the Attribute Manager shows it and its circle brings it onto the node).
- Layout of a port: `ui.base.groupid` (`net.maxon.node.base.group.inputs` or `.outputs`, or the id of a group of one's own), `ui.base.guitypeid` (`net.maxon.ui.number`, `.bool`, `.color`, `.vector`, `.string`, `.url`, `.enum`), `ui.base.show` (a condition; while false the Attribute Manager hides the port): `prop.data_type=="RGBA" || prop.data_type=="ROTATION"`, a switch by its id alone or with `!`, joined with `&&`; "false" hides for good.
- A foldable group on the node: an entry with the command "group" in data and in layout; in layout `ui.base.groupid` (its parent), `ui.base.groupdefaultopen`, `ui.base.showgroupinportlist` (true: the group folds on the node as well); its title is a "group" entry in the names.
- A dropdown option's label: a "string" entry named `<port id>#enum#<option id>`.
- `ui.base.show` works on settings (constant ports) as on sockets: the Color Ramp's stops beyond the chosen count are hidden with `(prop.ramp_stops=="s3" || prop.ramp_stops=="s4" ...)`. Colour and vector settings take `net.maxon.ui.color` and `.vector` like sockets do.
- There is no gradient control among the GUI types (`SDK/frameworks/cinema_hybrid.framework/source/maxon/uiconversions.h` lists them; the installed `resource/modules/misc.module` names the same set). There is a spline control; see the next section.

### A node the chosen Blender does not have (the version card)

All [T: screenshots of the Node Editor in the application with clean preferences, `tests/c4d/show_version_nodes.py` with `g_cyclesRenderBlender` set to each version, 2026-11-16; build instrumented to log what the preview provider and the port description provider are asked] unless marked. Screenshots: `internal/screenshots-0.2.0/f8/`.

- **A description cannot follow the Preferences.** The database is read from files once at start (`RegisterDatabaseWithUrl`). The port description provider (`PortDescriptionProviders`) was called for input and output ports only, never for the node itself or its attributes (`displaypreview`, `comment`), so it cannot switch a node's preview. A value set on the template's root in `InstantiateImpl` is overridden by the description for `DISPLAYPREVIEW` (set to true: no preview, with the description's default false, and also with no default in the description, where `net.maxon.node.base`'s default, off, counted).
- **What `InstantiateImpl` can set and does show:** `NODE::BASE::COMMENT` with `DISPLAYCOMMENT` true shows the text under the node, as does `NODE::BASE::COLOR` for the header. They are the node's own values: set when the node is made and again when a scene is loaded, not when the Preferences change. Measured in `c4dpy` (`tests/c4d/cycles_nodes.py` section 9): a comment the user writes, a comment the user empties, and the comment switched off, are stored with the scene and win over the node's own value after saving and loading; loading such a scene leaves the document unchanged (`GetChanged` false) and adds no undo step.
- **A preview on some nodes only** works from the description: `displaypreview` default true, and in the layout neither the group `net.maxon.node.base.preview` nor the attribute `net.maxon.node.base.nodepreviewimage` hidden (with either hidden, nothing shows on the node). Cinema 4D then asked the space's preview provider for the nodes with inputs and a colour output only (Light Accumulation, Shadow Raycast); Light Evaluation, Light Info and Raycast kept Cinema 4D's grey placeholder ball, until their first output got `net.maxon.node.attribute.ispreviewport` true in the description. The request's `SUBJECT` is that output port (kind `OUTPORT`, "lightaccumulation>out.shader"), the size 120 x 120 with `FLIPVERTICALLY`, as for the Attribute Manager's big preview. The selected node's Attribute Manager then has a "Preview" tab showing the same picture large.
- **What the plugin does** (`tools/make_nodes.py`, `VersionCard()` in `nodespace/cycles_nodespace.cpp`): every node newer than the oldest supported Blender (5.0) has such a preview, a card drawn with `GeClipMap` (the system font, sized to the card): red with "Unsupported in / Blender 5.2.3 / needs 5.3" when the Blender of the Preferences lacks the node, grey "Blender 5.1+" when it has it, "Needs Blender 5.3" when no Blender is known. The card is drawn when Cinema 4D asks for the preview, from the Blender in use at that moment (`GetBlenderInUse()`); Cinema 4D asks again when the node's graph changes [untested: whether it asks again after the Blender is changed in the Preferences without a change of the graph]. Next to the card, the same nodes carry a comment under them, "Needs Blender 5.3 or later" (the maintainer wanted both, 2026-11-16; screenshots `card_and_comment_blender_5.2.png`, `_5.3.png`): it names only the version the node needs, so it stays true whichever Blender is chosen later and is set as the node's own value in `InstantiateImpl` (above), never written into the user's graph. The attribute that switches the preview stays hidden in the Attribute Manager; whether a click on the preview button of the node's header hides the card was not tried (posted clicks do not press buttons in Cinema 4D 2027) [untested].

### The spline control (the curves of the curve nodes)

All [T: screenshots of the Node Editor in the application with clean preferences (`tests/c4d/show_cycles_node_ui.py` with `"select": "floatcurve"`, `"rgbcurve"`, `"vectorcurve"`), probes through the IPR test hook's `curve` command, `tests/c4d/cycles_nodes.py`, 2026-11-12] unless marked.

- **A port of type `maxon::SplineMapper`** (`SDK/frameworks/math.framework/source/maxon/splinemapper.h`): in the description the data type is `net.maxon.interface.splinemapper-C`, the GUI `net.maxon.ui.splinemapper`, as in Maxon's own descriptions in the installation's `resource.zip` (`neutron.module`'s Sweep command, `tool_system.module`'s cloth brush), which also show the default's form: `{"referenceDataType": "net.maxon.interface.splinemapper-C", "_knots": [{"position": {"x", "y"}, "interpolation", "tangentLeft": {"x", "y"}, "tangentRight": {"x", "y"}, "flags"}, …], "_min", "_max", "_tension", "_linkTangent", "_linkPosition", "_snap"}`. - **In the Node Editor's attribute area** the port shows as a graph with "Load Preset..." and "Save Preset..." below it, a straight line for the default, and nothing of it on the node (`constantparameter`, `hideportinnodegraph`). - **Selecting a knot changes the port's value:** the selection is the knot's `SELECTED` flag (64) in the data (flags 131072 became 131136).
- **The control shows and keeps only the square 0 to 1.** A spline whose range is -1 to 1 is drawn into 0 to 1 with labels 0 to 1, and the first edit writes it back with the range 0 to 1 and its knots moved into it ((-1, -1) became (0, 0)). Neither `data.base.minvalue`/`maxvalue` (as a number or as a 2D vector, with `limitvalue` "both") nor `ui.base.addminmax.minvalue`/`maxvalue` changed that. So the plugin keeps every spline in that square and maps it onto Blender's area (-1 to 1 for Vector Curves; `GetCyclesCurveArea`).
- **The data** (`SplineMapperKnot`): `position`, `interpolation` (0 `BEZIER`, 1 `LINEAR`, 2 `CUBIC`), `tangentLeft` and `tangentRight` relative to the knot, `flags` (the knot's id in the upper 16 bits, `SELECTED` 64, `BREAK_TANGENTS` 1 and the locks); `GetRange`, `GetTension` (1 by default), `GetKnots`, `GetKnotCount`.
- **Evaluating it:** `GetPoint(x)` gives the point on the curve at x, as the control draws it; it wants the knots sorted (`SortKnots` on a copy: the reference is copy-on-write). Measured: within 0.000001 of the exact value on a straight line; left of the first and right of the last knot the knot's own y (flat); with one knot that y everywhere; **with no knots 0 everywhere**; at two knots of one x a jump. `InsertKnot` moves a knot's x into the range (-0.5 and 1.5 became 0 and 1; y is kept).
- **Pitfalls:** `spline == nullptr` on a copy-on-write reference compares contents (`IsEqual`) and crashed in `math.module` for a spline that has a value: test `spline.GetPointer() == nullptr`. `SPLINEMAPPER_KNOT_SET_ID` compiles only inside `namespace maxon` (it names `Int` unqualified): set `flags = maxon::SPLINEMAPPER_KNOT_FLAGS(id << 16)`. Unrelated but met here: in `FormatString` an `@` followed by `{` starts a format specifier, so `"@{\"p\": …}"` swallows the text up to the next `}`.
- **Python** has no `SplineMapper` class: a port's value comes back as a `maxon.Data` that cannot be built or changed, and `SetPortValue(c4d.SplineData())` is refused ("not convertible"). Tests set curves through the IPR test hook (`curve <node> <port> <knots>`, `ipr/ipr_testhook.h`).
- **How a spline reaches Blender** (`materials/cycles_curves.cpp`): Blender's points have no free tangents (`AUTO`, `AUTO_CLAMPED`, `VECTOR`), so the knots alone cannot carry a Bezier curve. Measured against `GetPoint` at 1001 positions, Blender's `mapping.evaluate` of what would be sent, largest difference (shapes: an S curve of four Bezier knots, Bezier knots with tangents set by hand that overshoot to 1.26, a Bezier corner, four cubic knots, three linear knots with a corner):

  | Sent | S curve | hand-set tangents | Bezier corner | cubic | linear corner |
  |---|---|---|---|---|---|
  | the knots (Bezier and cubic as `AUTO`, linear as `VECTOR`) | 0.015 | 0.76 | 0.51 | 0.40 | 0.0028 |
  | `GetPoint` in 50 even steps, `VECTOR` | 0.00089 | 0.0012 | 0.00082 | 0.0018 | 0.0028 |
  | `GetPoint` in 250 even steps | 0.000057 | 0.000073 | 0.000065 | 0.00014 | 0.0028 |
  | **what the plugin sends:** 256 even steps and every knot, points a straight line between their neighbours already gives within 0.0001 of the range's height left out (115, 85, 125, 182 and 3 points) | **0.00011** | **0.00010** | **0.00011** | **0.00011** | **0.0028** |

  The 0.0028 of the corner is Blender's own: its table of 256 steps rounds every corner. A straight line sends its two ends, and Blender then evaluates exactly what its own new node does (difference 0.0 at all 1001 positions, also for Vector Curves' -1 to 1). Two knots at one x give a rise over one 256th of the span. Renders (`cycles_nodes.py`): within 0.0001 of the value `GetPoint` gives, for each node.

**What the Standard renderer calculates with in Basic mode** [T: strips of colour sources rendered in every combination of Linear Workflow and input profile, `tests\c4d\colour.py`; values below are what lands in the buffer, linear values with the curve when Linear Workflow is on]:

- Colour parameters (a material channel's colour times its brightness, a light's colour, gradient knots, a Sky's material, a shader's colour) go through `InitRenderStruct::TransformColor`: with Linear Workflow and input profile sRGB the sRGB curve is undone (a colour of 0.5 renders as linear 0.214, shown as 0.5); with Linear Workflow off and profile Linear the curve is applied (0.5 is calculated as 0.735); otherwise the stored value is used. The brightness multiplies **before** the conversion: (0.8, 0.3, 0.1) at 50 % renders as the linear of (0.4, 0.15, 0.05).
- Images are brought from their own space into the space of the calculation, linear with Linear Workflow and the stored sRGB numbers without it. Their own space is the bitmap shader's "Color Profile" when that is sRGB or Linear (`BITMAPSHADER_COLORPROFILE`), and otherwise linear for an EXR and sRGB for an 8-bit PNG. An embedded ICC profile made no difference (a PNG with and one without an iCCP chunk rendered the same), and the document's input profile sRGB or Linear does not change images either. With the input profile Off nothing is converted, files or colours, with Linear Workflow on or off. So: a PNG of 128 renders as linear 0.216 with Linear Workflow (shown 0.502) and as 0.502 without; an EXR of 0.2 as 0.2 with Linear Workflow and as 0.485 (the curve applied) without; a PNG whose bitmap is set to Linear as 0.502 linear with Linear Workflow (shown 0.737) and 0.737 without.
- A shader baked with `BakeShaderIntoBaseBitmap(…, colorProfile, linearWorkflow, …)` holds exactly what is calculated with, in every combination (a Noise of one colour matched to 0.000).
- Cinema 4D's own 32-bit EXR of a final frame holds the buffer linearised: 0.5 in the buffer is 0.214 in the file, with Linear Workflow on and off (read back with `BaseBitmap.InitWith`).
- Blender reproduces all of it in its working space `Linear Rec.709` (`scene/document_colors.cpp`): colour parameters converted as above; images loaded as `sRGB` (an sRGB file into a linear calculation), `Linear Rec.709` or `Non-Color` (no conversion); and with Linear Workflow off the sRGB numbers given to Blender as if they were linear and written back as they are, which is the same arithmetic. One case has no colour space in Blender: a linear file into a calculation without Linear Workflow needs the curve applied on loading. A bitmap shader is then baked instead (exact); a file named by a node material or a Redshift dome is used as it is, with a warning.
- Measured with the fix [T]: every strip of every combination within 0.0004 of the Standard renderer, also with Multi-Pass on; before it, colours typed in rendered too bright with Linear Workflow on (0.735 for 0.5; means 1.67 to 1.84 times the Standard renderer's) and textures too dark with it off (0.216 for 0.502; 0.55 times). What Cinema 4D's own view keeps as its point of interest (it moves with navigation) is not readable through the SDK; the plugin remembers where its last drag left it while the camera stays where that drag put it. "Deep" and "Sync Orthographic Views" are not followed, nor the Ctrl modifier's view snapping (Ctrl's trackball is).
- **Undo of a camera moved by a drag**: `StartUndo`, `AddUndo(UNDOTYPE::CHANGE_SMALL, camera)` before the first move (and on the Cycles Camera tag when its orthographic scale changes), `EndUndo` after the last: one step, which puts back the matrix (`SetMg`) and `CAMERA_ZOOM` exactly, and redo the moved state. An editor camera belongs to its view: `BaseDraw::InitUndo(doc)` before the move, and `BaseDraw::DoUndo(doc)` ("Undo View") puts it back; the document's undo does not see it (measured: a document undo after the drag undid the step before it and left the editor camera moved).
- **Cancelling an open undo step** (Escape): `BaseDocument::DoUndo(true)` between `AddUndo` and `EndUndo`, as the SDK's tools do (`liquidtool.cpp`), reverts the step and closes it; the step before stays the next to undo (probe `probe_flush.py`). The undone step goes to the redo list with the state at the time of the call: a redo brought back the cancelled move, unless the object was put back before `DoUndo(true)` (the plugin puts the camera back first, so a redo changes nothing). Python's `FlushUndoBuffer` takes no argument (the C++ `lastEntryOnly` is not reachable from Python).
- **Protection tag** (`Tprotection`, `description/tprotection.h`): `PROTECTION_P`, `PROTECTION_S`, `PROTECTION_R` are integers (0 none, 1 lock, 2 limit), set through `SetParameter`. A camera with position or rotation locked or limited is not moved. A locked layer: `GetLayerData(doc)->locked`.
- **The ray through a point of the picture** is the inverse of what the exporter sends (`CameraRay` in `scene/camera_export.cpp`): Blender's sensor fit is horizontal, so the sensor spans the camera's picture across, square pixels in the IPR's image, film offset as `ExportCamera` shifts. Checked: a point picked under the mouse stays at that pixel to 0.01 px through an orbit and a dolly towards it, and moves with the mouse exactly in a pan, for perspective and parallel cameras.

## Skipping unchanged meshes in the IPR

How the IPR decides that a mesh Blender holds need not be exported again (0.2.0, F16; `scene/scene_exporter.cpp`, `MeshSignature`; `scene/mesh_export.h`, `HashMeshContent`, `HashMeshIdentity`; the preference "Skip Unchanged Meshes").

**What changes when, measured** [T, `c4dpy`, 2026-11-13, scratch probe `probe_sources.py` with the test hook's `sources`]. For each change, after `ExecutePasses`, every mesh leaf's content hash (everything `ExportMesh` reads: points, polygons, Phong break edges, n-gons, every UVW, normal, vertex map and vertex colour tag by name and data, Phong settings, polygon selections), its identity (address, GUID, `GetDirty(DIRTYFLAGS::DATA)` of the object, and type, address, data dirty count and name of each tag), its address, and the dirty counts (data, matrix, cache, children) of the object of the document it belongs to:

| Change | Polygon object of the document | Generated or deformed meshes |
|---|---|---|
| point moved, with `MSG_UPDATE` / without / in an undo step | content and identity | the instance's copy: content and identity |
| undo of that, redo of that | content, identity, address (undo and redo each put a copy in place) | the instance's copy after the redo: **content only, same address, same identity** |
| UVW data changed (with or without a message), UVW tag renamed, Phong angle, vertex map added, selection tag changed | content and identity | the instance's copy: identity, sometimes content |
| cube size, take with a size override, Subdivision Surface child, Cloner child | — | content, identity, address |
| cube moved | — | identity and owner's counts, content the same |
| deformer moved, time with an animated deformer | — | content, identity (address the same) |
| nothing, evaluated once more | nothing (but the first evaluation after building a scene changed some identities) | nothing |
| material colour | nothing | nothing |

So for a polygon object of the document every content change came with an identity change; for what a generator, deformer or instance makes it did not (the redo row), and neither did the owner's counts reliably (UVW data changed the content without them). Rule: identity for polygon objects of the document that have no animation track and only tags of plain data (point, polygon, UVW, normal, Phong, vertex map and colour, tangent, the three selections, texture, compositing, display, protection, annotation, Cycles Object), because Point Level Animation, an expression (Python, XPresso) or a Pose Morph could change points during evaluation (none of them tried); the full content hash for everything else (since B11 read from Cinema 4D's own data hashes for what a generator or deformer made, see below; a pass over the bytes only for the polygon objects of the document that this rule sends to the hash). Other inputs of the mesh items go into the signature too: the material slot of every polygon, the UVW set textures use, the document's unit, the mesh id. Hashing a mesh's data is cheap next to exporting it: the 900 meshes of `ipr_reuse`'s large scene (300 of them generated and hashed in full, 800 polygons each) took 3–4.5 ms in all with reuse, 55–66 ms exported (with the data hashes of B11: 0.8 to 1.3 ms).

**Cinema 4D's own data hashes instead of a pass over the data** (0.2.0, B11; `MESHHASH::DATA_HASH` in `scene/mesh_export.h`) [T, 2024.5.1 and 2027.0.0, 2026-11-18; scratch probes `probe_dirty.py`, `probe_dirty2.py`, `probe_hash.py`, `probe_redraw.py` with the test hook's `sources`; `tests/c4d/ipr_optimized.py`, part 5]. The content hash above read every array of every generated or deformed mesh at every export: 10 ms for a plane generator of a million quads in 2024 and 21 ms in 2027, at every step of a drag of anything.

- **`VariableTag::GetDataHash()`** (all four SDKs; a `maxon::UniqueHash`, 128 bits, `low` and `high`) is a hash of the tag's data that Cinema 4D keeps with them: for that plane 0.05 to 0.17 ms a call for the point, polygon and UVW tags together (the hook's own call included), also right after the generator built the mesh anew. Points and polygons are tags too (`Tpoint`, `Tpolygon`, found by walking the object's tags). It is a hash of the content: a plane set to another width and back gave its first value again, a second plane with the same values the same hashes, another number of segments others.
- **It changed with every change of the content**, for every mesh leaf (editable, generated, deformed): compared with the pass over the bytes after each of 36 changes of `ipr_reuse.py`'s scene and its extras and 55 changes of a second scene (deformers on an editable object, in a group and on a generator; Cloners in linear and object mode with an effector; Boole, Extrude, Symmetry, Connect, Subdivision Surface, a Python generator; Instance objects in copy and render mode of a group; undo and redo; edits without `MSG_UPDATE`): no content change without a change of the data hash, in 2024 and in 2027. So what a generator or deformer made is judged by these hashes, with the Phong settings, tag names, polygon selections, Phong break edges and n-gons as before. A polygon object of the document that is hashed "when in doubt" (a track, an expression tag) keeps the pass over its bytes: whatever writes its points during the evaluation is the case nobody measured.
- **Cinema 4D 2027 makes some tag data only when asked** (`VariableTag::SetValidationDelegate`, new in the 2027 SDK: "called on data and count access functions ... to lazily create or modify the data just before access ... the data hash will be invalidated"). Measured on the plane generator's UVW tag: `GetDataCount()` or `GetLowlevelDataAddressR()` took 10.6 ms each time (a million polygons), **and the next redraw of the view took 20 ms instead of 2**, every time, with nothing changed and the IPR closed; `GetPointR()`, `GetPolygonR()`, `GetPhongBreak()`, `GetNgonCount()`, `GetDirty()` and a tag's `GetParameter()` cost nothing. That was the slow redraw of B11's measurements ("in 2027 only, Cinema 4D's next redraw after such an export takes 20 ms"): the old hash asked every UVW tag for its count and its data at every export. In 2024 the same calls cost nothing. A mesh is still read when it is exported, once.
- **A tag's data hash is another before and after its data were asked for** (2027, the same UVW tag: one value while the data were never asked for, another once they were made, 22 to 27 ms for the first `GetDataHash()` after that and 0.1 ms from then on; a new cache of the same generator starts with the first value again). So the IPR notes two signatures per mesh, the one read before its export and the one read right after (`SceneWriter::NoteMeshSource`), and keeps a mesh that shows either: without the second, every mesh with such a tag was exported twice; without the first, a cache built anew with the same content would be exported again.
- Measured after (`ipr_optimized`, part 5; `ipr_reuse`): an export with the unchanged plane beside the moved object 1.5 to 2.5 ms (its mesh 0.01 ms; before 12 and 21 ms); the 900-mesh scene's meshes 0.8 to 1.3 ms instead of 3.2 to 3.9 ms; every kind of change of `ipr_reuse` exports and keeps the same meshes as before, in 2024 and 2027. `verify` reads every mesh, so the export after one hashes such a tag again (25 ms): a test's cost, not a user's.

**Checked against a full export** [T, `tests/c4d/ipr_reuse.py`]: after each of 35 changes (object moved; points edited with and without `MSG_UPDATE`, in an undo step, undone, redone; UVW data, UVW name, Phong angle, vertex map added, selection grown; material colour; bitmap file; generator parameter and move; deformer moved; time with an animated deformer; Cloner child and count; Subdivision Surface child; parent moved; render dot off and on; layer render off and on; take switched and back; object deleted and the deletion undone; object added; a track added to an editable object and its points edited; nothing) the document exported whole without reuse gives exactly the items Blender holds, and the picture equals the one after reloading without reuse (difference 0.0). Found on the way: `BaseObject.MakeTag` in Python puts the new tag first, so of two texture tags made one after the other the first one made covers the second; and Python's `SelectionTag.GetBaseSelect()` is the tag's own selection (changes stick).

## What the IPR sends while a change is in progress

0.2.0, B11 and F23 (`IprController::FollowStep`, `FollowEvaluation`, `NoteRedraw`, `SyncAlone` in `ipr/ipr_controller.cpp`; `SceneExporter::WriteObjectAlone`, `CollectOwners`; Preferences > Renderer > Cycles Render > IPR, "Optimized Live Updates", page id 1012, stored key 1024, on by default, without effect while "Live Updates During Drags and Playback" is off). All [T: `tests/c4d/ipr_optimized.py` and `ipr_values.py` in `c4dpy`, `tests/c4d/ipr_optimized_window.py` and `ipr_values_window.py` in the application, 2024.5.1 and 2027.0.0, 2026-11-18] unless marked.

**The three ways a change arrives.**

- *A finished edit* (`EVMSG_CHANGE`, a tool's `MOVE_END`, another time of the document): the scene is exported whole, as since 0.1.0. This is also what corrects everything below.
- *A redraw* (`EVMSG_DOCUMENTRECALCULATED`, which follows every redraw of a view): exported only if `GetHDirty(ALL)` or the document's time differ from what the last export or update saw. Measured: 40 of 40 redraws while the view's own camera was moved exported nothing (the camera was sent 39 times), where every one exported the whole scene before. No switch.
- *A step of a change in progress* (a tool's `EVMSG_ASYNCEDITORMOVE`; an evaluation of the document in a modal loop, through the scene hook; and a redraw whose counters moved): with "Optimized Live Updates" only what changes is sent.

After steps, and after redraws that exported nothing, **the settle export** follows: the scene whole once more, at the change event or the tool's last step, or when nothing has happened for 0.25 s. It sends only what differs, which after steps is nothing (below), and it is what brings a change that no counter showed (the list in "Threads, messages, change detection").

**What a step sends alone**, each item the same, byte for byte, as a whole export writes it:

| What changes | Sent | Measured |
|---|---|---|
| The camera the IPR renders through (a tool's drag, the view navigated, its values dragged in the Attribute Manager) | the camera (`SyncCamera`): no scene request | 38 to 39 of 40 steps; no scene request during or after |
| A light: its values, its place, its green check | its `light` item (`WriteLightAlone`, as since F18), every light of the document at every step | 38 to 39 of 40 steps in an Attribute Manager drag |
| An object of the document, moved, turned or scaled: by a tool, in the Coordinates tab, by an expression (the object a Target tag turns towards the dragged one) | the `object` items of everything it and the objects below it show, if each is a plain `object` item | 39 to 40 of 40 steps; 0.02 to 0.15 ms a step to compare and write, also with a million-quad generator in the scene or as the dragged object |
| What an object of the document shows (F23): the parameter of a primitive or generator, the input of a generator, a deformer's value or place, a moved Cloner or instance | that object collected again (`SceneExporter::CollectOwners`) and its `mesh`, points, `object` and `instancer` items written; of the meshes only those whose content changed are exported | every step that changed the value, 38 to 40 of 40, in an emulated Attribute Manager drag of each of 12 values (7 of parametric objects, 5 of deformers) and of a deformer's place, also as a tool's drag and with the evaluations on the drawing thread; 0.06 to 0.55 ms a step for small objects |

An `object` item is written again from what the last whole export noted of it (`WrittenObject`: mesh, materials, visibility, properties) and a matrix formed as the walk forms it: the top object's `GetMl()` times each child's down to the item's owner, then the local matrices the walk met inside the owner's cache, in the same order (`GetMg()` and any other order of the products round differently in the last bit). Measured for each kind below: after the step `verify` finds no difference, and the whole export at the end has nothing left to send.

**Collecting single objects again** (F23). `CollectOwners` is the whole export's own walk, limited to the objects asked for: it goes down from the top of the document through the objects above them (for what they hand down: the render dot, texture tags, the Compositing and Cycles Object tags, the name path, and the matrix product in the walk's order) and looks only into the objects asked for; `Write` then writes their leaves as always (`Resolve`, the batching into instancers, the mesh signatures and `KeepMesh`). So the items are the whole export's by construction, as long as what an item depends on outside its own object is the same:

- *Material ids* count up in the order materials are first asked for in a whole export, so only that export can name them: it hands its table over (`MaterialIdTable`, the stack of materials and mappings to the id), and a step looks ids up there and writes no material (`MaterialExporter::SetKnownIds`). A stack the whole export did not write (a restricted texture tag whose selection the mesh did not have) refuses the step.
- *A mesh is named after the first leaf that shows its polygon object.* One polygon object is reached through several objects of the document when a render instance, a multi-instance or a Cycles Object tag shows it. So what shows the same object goes together (`SceneExporter::GetReferences`: who shows whom): an object that changed, or moved, at or below one an instance shows takes the instance with it, and an instance takes the object it shows and everything below that; they are collected in the document's order. An Instance object in copy mode is taken along the same way (its copy changes without a counter of its own).
- *Equal copies inside generators that make many* (16 leaves or more, or a Cloner's clones) share one mesh by content, also between two generators: which of them names it follows from the whole walk. Two objects of the document that share a mesh this way are noted (`GetFixedOwners`) and a step that would collect one of them is exported whole.
- *A light's include or exclude list* names items. A step that collects leaves them as the last whole export wrote them, which is right while the items of the collected objects are the same ones; when items come or go (a generator switched off) and any light has such a list, the step is exported whole.
- *Only meshes.* An object that shows a volume, hair, particles, a light made by a generator, the sky or a dome light is the whole export's (`GetFixedOwners`, and `IsRefused` when one turns up while collecting).

**What a step compares**, for every object of the document against what the last whole export saw (a walk of the document's objects, not of their caches; 0.03 ms for the test scene's 24 objects):

- its matrix counter: it moved (its `object` items are written at the new place; if it shows something without an item of its own place, a Cloner's clones or an instance, it is collected again);
- its own data counter (`GetDirty(DATA)` of the object) and its mark "used by a generator" (`BIT_CONTROLOBJECT`): it is collected again, unless it is a light or a camera, whose data are sent as above. If its name changed too, the step is exported whole (the name is part of the keys of Redshift's random nodes for the objects below it);
- its tags' data counters: a change is the whole export's (a material's tag, a selection, a Compositing or Cycles Object tag that the objects below inherit), except for a light or a camera, and for a deformer with nothing below it, whose points are tag data (the cage of an FFD);
- its cache counter (for an object that shows a deformed mesh: the counters of every object inside its cache): its cache was built anew, it is collected again;
- for a deformer (`OBJECT_MODIFIER`), any of these: the object above it and every object below that are collected again;
- its render dot: the whole export's (the objects below inherit it);
- and `GetHDirty` of everything but objects, matrices, tags and node bits (materials, render settings, layers, takes, the hierarchy, tracks) and the document's time: the whole export's.

**The rules: what goes alone and what is exported whole in that step.**

| Kind | A step is | Why |
|---|---|---|
| An editable polygon object; a generator (primitive, Subdivision Surface, Boole, Extrude, ...) moved as a whole; a group with such objects below it | alone | only their places change |
| A camera; a light; a group with lights below it | alone | |
| A parameter of a primitive or generator (size, segments, an Extrude's offset, a Sweep's growth, a Subdivision Surface's level, a generator's green check) | alone since F23 | the object is collected again: its meshes |
| The input of a generator, its value or its place (the spline of an Extrude or Sweep, a Text spline, the cage of a Subdivision Surface, the child of a Boole or Cloner) | alone since F23 | the generator's cache counter moved: the generator is collected again |
| A deformer: its values (Bend, Twist, Bulge, Taper, an FFD's size and its cage), its place, also below the input of a generator | alone since F23 | the object above it and everything below that are collected again; the data hashes tell which meshes changed |
| An object that carries a deformer below it, moved | alone | in 2024 it is collected again (2024 makes the deformed copy anew when its object moves) |
| A Cloner moved, its count, its child; a multi-instance, a render instance, an Instance object in copy mode, moved; the object they show, changed or moved, and the objects below it | alone since F23 | collected again together with what shows them: the `instancer` items, the shared meshes |
| The sky, a Redshift dome light, a volume, hair, particles, a light made by a generator; two generators that share a mesh by content | whole | only a whole export writes them right |
| The Cycles Environment that is the world: its values and its place | alone since F4 of 0.3.0 | the world written by itself at every step; another type, image or the check off: whole |
| Points of an editable object, a tag's value (Compositing, Cycles Object, texture, selection), a material, the render dot, an object's name, objects added or removed, another time | whole | not looked into by a step |

Inside an evaluation of the document (the scene hook: a drag in the Attribute Manager) a step is never exported whole: what cannot go alone waits for the end of the drag, as before; the lights and the camera go on meanwhile (measured: a material's colour and a Compositing tag's switch dragged, nothing sent until the end; a light changed in between, sent).

**A tool's drag makes two calls a step, and can run one step behind** [T: 24 emulated tool drags of a deformer's place, 40 steps 25 ms apart, application 2027.0.0, 2026-11-19, a scratch probe; `tests/c4d/ipr_values_window.py`, `deformer_place_by_tool`]. The tool's message (`EVMSG_ASYNCEDITORMOVE`) comes before the step's change is evaluated: its call sends what the evaluation of the step before built, if that has not been sent, and asks for another look. A few milliseconds later the scene hook's call comes, at the end of the evaluation, and sends what this step built, unless Blender is still busy with what the message's call sent; then it waits for the next step, where the message's call sends it. So the picture is either with the drag or one step behind it, and which of the two can change from step to step with how quickly Blender answers (1.6 ms measured for a small update) against how long Cinema 4D takes to evaluate and draw. Measured: the hook's call sent 20 to 39 of the 40 steps in 21 of 24 drags and none in 3 (every mesh went with the message's call, a step late); in 4 of 24 the last step's one mesh was left for the export at the end of the drag, which sends it at once. `verify` was clean after every drag. An Attribute Manager drag makes one call a step and leaves nothing.

**Caches at the scene hook** (F23) [T, `c4dpy` 2024.5.1 and 2027.0.0, the local `internal/f23/probe_cache_at_hook.py`: a Python tag at priority "Generators, 1", five evaluations each with `BUILDFLAGS_NONE` and `BUILDFLAGS_EXTERNALRENDERER`]. At "Generators + 1" every cache read was the one of that evaluation: a Cube's, a bent Cube's deform cache, a Subdivision Surface's after its cage changed, a Cloner's after its child changed, an Extrude's after its spline changed, and the copy of an Instance object that stands before its source in the document. The hook is registered at `EXECUTIONPRIORITY_SCENENODE + 1` (10001; the generators' is 5000, the scene nodes' 10000), so that whatever the scene nodes build is there too [the scene nodes themselves untested].

**Which thread, and why the hook does the work itself** (F23) [T, application 2027.0.0 and 2024.5.1, mouse messages posted to sliders of the Attribute Manager, 40 moves 25 ms apart: a Bend's Strength in both versions, a Sweep's End Growth and a spot's Intensity in 2027; the local `internal/f23/probe_am_*.py`, which need the screen point of the slider's knob on the machine they run on]. The evaluations of a real slider's drag ran on a thread that is not the main thread, 32 to 39 of them in a drag (as measured for a light's Intensity in F18). A job handed to the main thread's queue from there ran when the next mouse message arrived, not before: it waited 15 to 19 ms at the median and up to 27 ms with the messages 25 ms apart, and a `WM_NULL` posted to the main thread did not hurry it. That next mouse message also sets the next value and starts the next evaluation, which builds the caches anew, so a call that comes through the queue must not read a cache, and an evaluation that waits in the hook for the main thread to make the call holds up its own thread, which is the one that then draws the view, until the next mouse message (tried: the waits were those 15 to 19 ms, and two of 38 evaluations gave up after 25 ms). So the evaluation is followed where it happens: `IprController::FollowEvaluation` runs in the hook, on the evaluating thread, at the end of the evaluation, when nothing builds a cache; the controller's lock (`IprLock`) keeps the main thread out for that long, and the evaluating thread itself never waits for the lock: it gives the step up when the main thread holds it (the main thread may be waiting for that thread to stop; 0 steps were given up in these drags). Measured with it: every evaluation of a slider's drag sent what it changed, alone, during the drag (a Bend's Strength 32 of 32 and 39 of 39 in 2027 and 39 of 39 in 2024, the bent mesh in 0.09 to 0.13 ms at the median and 0.2 to 1.1 ms at most; a Sweep's End Growth 39 of 39, 0.12 ms; a spot's Intensity 38 of 38, the light in 0.04 ms), nothing was left for the export at the release, and `verify` was clean. Before, such an update left with the next mouse message (the queue's call), one step late. What the window does with the queue's call afterwards (and with a frame's) reads no cache: it sends the lights and the camera, and compares the objects only when none of them shows a deformed mesh (the counters of those are inside their caches). `CheckIsRunning(CHECKISRUNNING::VIEWDRAWING)`, asked on the main thread, was true at every call made while an evaluation stood still in the hook (16 and 21 of them), and at 2 to 14 of 33 to 52 calls for a frame [measured, not built on].

**What each thread may touch** (the review before 0.2.0; the contract is the class comment of `IprController`) [T: `tests/c4d/ipr_threads_window.py`, application 2027.0.0 and 2024.5.1, Blender 5.2.3, 2026-11-19: emulated drags of 24 steps 25 ms apart with the redraws on Cinema 4D's drawing thread; read: the SDK's `page_manual_cinemathreads.html`]. The SDK reserves for the main thread: adding an event, changing materials or the structure of the scene, drawing, every GUI call, undo; it says the execution pipeline may run in a thread while other threads read the document, and that whoever changes the active document has to stop those threads first. It does not say that a view can be asked on another thread (`GetActiveBaseDraw`, `GetRenderBaseDraw`, `BaseDraw::GetSceneCamera`, `GetEditorCamera`), and the active document is the main thread's. So a step that runs in the scene hook on the evaluating thread keeps to this:

- *It reads objects of the evaluated document only*, at the end of the evaluation: the hook runs inside the evaluation and on its thread, after the generators and the scene nodes, so nothing of that evaluation builds a cache meanwhile, and the main thread, the only one that may change the document, has to stop this thread first, which waits for the hook to return.
- *It asks for no view and no active document.* The main thread resolves the camera (the view, its scene camera, the IPR's camera list) at each look of its own and notes it as a `BaseLink` if it is an object of the document; the evaluating thread reads that link (`GetLink(doc)`, and the object's `GetDocument()` must be that document) and nothing else. Measured: a camera's field of view dragged, 21 to 23 of 24 steps sent from the drawing thread; the camera taken out of the document in the middle of the drag while its value went on changing, nothing more sent from that thread (6 of 6), and the main thread sent the view's own camera once; another camera chosen in the IPR's list in the middle, nothing sent from that thread before the main thread had looked (3 of 3). A camera changed in the view itself is not noticed there: that thread goes on with the camera it was handed, still an object of the document, until the main thread looks (3 of 3: it sent that camera for the 11 steps that remained, and the picture at the end was the new camera's). With the evaluating thread asking the view itself, as before, the same checks fail (a camera sent from that thread after the deletion in 6 of 6 drags, 11 to 12 after a choice in the list).
- *It touches no window, adds no event, changes nothing in the document, reads no preference* (the window's timer hands it "Optimized Live Updates" and "is this a modal loop" as atomics) *and waits for nobody*: it only tries the controller's lock, and a failure is only noted for the main thread's next tick.
- *The controller cannot go away under it.* It enters through `IprController::FollowEvaluation` alone, which counts it before reading the (atomic) pointer to the controller; `IprController::Free` (Cinema 4D's shutdown) takes the pointer away first, then waits for the count, then deletes. Measured, in 2027 and in 2024: the controller freed 6 times while a step exported a plane of 360,000 quads on the drawing thread (26 to 27 ms in 2027, 20 ms in 2024): each call met the step (by the trace's times) and returned 250 to 305 ms later, with the step finished and Blender ended; the IPR stopped 8 times into such a step: each call waited 9 to 38 ms for it and nothing was sent afterwards.

**Jobs of the main thread's queue run inside Cinema 4D's own calls** [T, the same test]. A job enqueued on `JobQueueRef::GetMainThreadQueue()` from the scene hook during a script's loop of `StopAllThreads()`, a threaded `DrawViews()` and a sleep per step ran before the loop gave the main thread back to Cinema 4D in about half of the drags (once, at the loop's end), and right after the loop in the others. So a queued call can arrive while the main thread is in the middle of something else of the plugin, and a lock that lets its own thread in again does not keep it out: `IprController` therefore does not follow a `Tick` or a `Follow...` call that arrives while its thread is inside an export or a step (`_exporting`, trace `reentered`) [built from reading; no call was seen to arrive inside an export].

**What the counters showed** (F23) [T, `c4dpy` 2024.5.1 and 2027.0.0, the local `internal/f23/probe_hdirty.py` and `probe_bits.py`]:

- In Cinema 4D 2027 `HDIRTYFLAGS::NBITS` moves whenever a generator with an input builds its cache anew (a Cloner's child, its count, an effector, a moved Cloner with an effector, the spline of an Extrude, a Text spline's height), not for a primitive's own size, a Bend's strength or a moved Bend; in 2024 it never moved. A step therefore leaves the node bits out of "anything else in the document" (it compares the one bit the exporter reads, `BIT_CONTROLOBJECT`, object by object). 2027 also counts the document's unit and its Linear Workflow switch there: a step sees those as little as Cinema 4D 2024 does, and they arrive with the whole export.
- `BIT_CONTROLOBJECT` is set on a generator's inputs and on generators that have a cache (a Cube, an Extrude). It was off on an Extrude and on its Rectangle for the one evaluation in which the rectangle's Rounding was switched on, and on again at the next change; it goes off with a generator's green check (whose cache is gone then, cache counter +1). A step treats a change of the bit like a change of the object's own data: the object is collected again.
- An FFD's grid size and its cage points move the data counter of its point tag (the FFD is a point object; Python gives no `PointObject` for it, the cage is `Tpoint` tag data): 27 points for the default cage.
- A generator's parameter moves only `HDIRTYFLAGS::OBJECT`, a deformer's place only `OBJECT_MATRIX`; one more evaluation without a change moves nothing.

**What a step costs, and the guard** (F23) [T, `tests/c4d/ipr_values.py` part 5 in `c4dpy`; `internal/f23/probe_f23.py` in the application, 960 × 540, Cycles on the GPU, emulated Attribute Manager drags of 40 steps 25 ms apart on the main thread, 2026-11-18]. Collecting an object again reads its cache and exports the meshes that changed, on the thread that evaluates (the main thread for a tool's step, for the colour sliders measured in F18 and in the emulated loops; the drawing thread for the sliders measured):

| A step that changes | 2027.0.0 | 2024.5.1 |
|---|---|---|
| a small primitive (a Cube's size) | 0.05 to 0.07 ms | 0.05 to 0.07 ms |
| a Bend on a plane of 250,000 quads | 20 to 27 ms | 16 to 18 ms |
| the width of a plane of 1,000,000 quads | 98 to 101 ms | 69 to 71 ms |

After a step that collected and took longer than 4 ms, no step collects for three times its length (`MESH_STEP_FREE_MILLISECONDS`, `MESH_STEP_QUIET_FACTOR` in `ipr/ipr_controller.cpp`): such steps take at most a quarter of the time however heavy the mesh, a step in between is left out as a whole (its change goes with the next one that runs, or with the export at the end), and a step also waits while Blender is still busy with the last one, as before. In the application, a whole drag of 40 steps:

| Drag | IPR closed | IPR running, before F23 ("Optimized Live Updates" off: the mesh at the end) | IPR running, F23 |
|---|---|---|---|
| a Cube's size, 2027 | step 3.3 ms, main thread 14 % busy | 4.3 ms, 14 % | 4.0 ms, 13 %; 39 of 40 steps sent, the hook's call 0.16 ms |
| a Bend on 250,000 quads, 2027 | 6.6 ms, 34 % | 9.6 ms, 28 % | 24.6 ms on the steps sent, 40 %; 20 of 40 sent (hook's call 17.9 ms), 16 left out by the guard |

A Cube's size 39 of 40 steps sent, the hook's call 0.18 ms, main thread 13 % busy; the Bend 20 of 40 sent (17.1 ms), 16 left out, 40 %; the plane 13 of 40 sent, 14 left out, 78 %, the drag 4.6 s.

**What can be wrong until the settle export** [read, by construction; none measured]: something that depends on a changed object without any counter of the document or of its objects moving. Known kinds: a shader that reads an object's place (baked textures of such shaders), a plugin's generator that reads another object without declaring it. A light's include or exclude list is that of the last whole export. After a step, two generators that came to make the same mesh keep one each until the whole export gives them one to share (the picture is the same). A wrong picture after the settle export would need a difference that a whole export does not see either.

**Off.** With "Optimized Live Updates" off a tool's step exports the whole scene and an evaluation in a modal loop sends the lights alone, as before the switch [T: 39 scene requests and no single items in a tool's drag of 40 steps; 38 to 39 times the lights alone; a Cube's size and a Bend's strength dragged, nothing during the drag and one scene request at its end]. Redraws that changed nothing still export nothing, and meshes are still judged by their data hashes: those are not switched.

**The manual mode** (0.3.0, F3; "Refresh Whole Scene Only on Reload", design decision 31). Measured with `tests/c4d/ipr_manual.py` (2026-11-23, Cinema 4D 2027, Blender 5.2.3; through the test hook, without a window) [T]: with the switch off a change event is one whole export; with it on, an object moved, a Cube's size, a Bend's strength and a light's brightness each go as one update of single items at the change event, with no whole export in the 0.6 s after it and no difference left against a whole export from scratch; five redraws that changed nothing and a camera move send no scene request (the camera goes as its own request). A material's colour sends nothing and leaves exactly the material's item different (`material_0`); an object moved and a light changed afterwards still go, with the same one item different. Reload then makes one whole export with 1 changed item, 0 meshes exported and all 3 kept; Reload again, with nothing waiting, exports all 3 meshes. A Phong tag's angle changed together with a move of its object: the move goes, the scene waits (reason TAG). Another time: no export, the scene waits; an object moved at that time goes alone. An object added: nothing is sent, also not a later move of another object (reason HIERARCHY), a light's value still is, and Reload leaves no difference. Switched off while a material waits: one whole export at the next tick, no difference. With "Optimized Live Updates" off the mode reports off. Not measured: what the mode saves in a big scene, and anything in a window.

**Not tested** (the rule covers them by construction): volumes, hair, particles and Cycles Object tag instances as the changed object (exported whole by rule); a real tool's `MOVE_END`; a real hand at a tool, at the Coordinates tab, at a number field's arrows, at an object's handles in the view, navigating a view; a real slider's drag of anything but the three named above (and in 2024 of anything but a Bend's Strength); scene nodes; fields, constraints, XPresso, dynamics.

## The device a scene renders on

- **The Render Settings' Device decides, the Preferences only say what "GPU" means** [T: `tests/c4d/ipr_device.py`, 2027.0.0 and 2024.5.1, 2026-11-17]. Up to 0.2.0 new render settings started with "CPU Compute" (Blender's default), and a device type chosen under Preferences > Cycles Render Devices (CUDA, OptiX) did nothing until the Render Settings said "GPU Compute": the lag reported from the 0.2.0 test release was exactly this (B11). Since 0.2.0 the Device has a third value, `CYCLES_DEVICE_AUTOMATIC` (2), first in the dropdown and written by `InitRenderSettings` into new settings: the GPU when Blender lists one, else the CPU, said in the console. A scene stores its device: scenes saved with CPU, GPU and Automatic load with them; the stored scenes of 0.1.0 and of the test release load with CPU (0). On "CPU Compute" with a GPU type chosen in the Preferences, final frames and the IPR say in the console that the type does not apply (`WriteRenderSettings`). The description has no `DEFAULT` for the Device, so "Reset to Default" gives 0, CPU [untested by hand].
- **What renders is checked, not assumed**: Blender's CPU time over 1.5 s of an IPR render at 640 × 360 (a cube on a floor): 1.1 cores on OptiX, 29.6 on the CPU with 30 threads, 1.1 on Automatic; a final frame on Automatic sends `AUTO` and Blender answers `GPU`, `OPTIX` without a warning. The IPR's status line shows Blender's answer (`IprController::GetDeviceText`).
- **Warnings of the settings reply in the IPR**: up to 0.2.0 the IPR's worker did not read the reply of a `settings` request, so its warnings (a type this machine lacks, nothing ticked, no GPU) never reached the console in the IPR; final frames printed them. The worker now collects them like a scene's (`IprWorker::Run`).

## Priority and cores of the IPR's Blender

- **Cinema 4D runs below normal** a few seconds after it starts (its preference, on by default; `internal/b11/measurements.md`). The bridge used to put Blender below normal too, so both shared one class and a CPU render's 30 threads took the processors Cinema 4D's main thread and job threads wanted.
- **Blender at idle stalls** [T: `internal/b11/priority_probe.py`, bridge alone, i9-13900K, 2026-11-17]: with every logical processor kept busy by processes at below normal (a stand-in for Cinema 4D's job threads), a Blender at idle answered no request within 10 s and published no frame, on the GPU and on the CPU, also with its main thread raised to `THREAD_PRIORITY_HIGHEST` or `TIME_CRITICAL`; at below normal it went on (GPU: replies 1.3 ms, 28 frames a second; CPU: half the machine's cores). Without that load idle changed nothing (same samples per second on this hybrid CPU). So the rule (`IprController::FollowPriority`, `platform/process_stats`): one class below Cinema 4D's current class, but not below "below normal" unless Cinema 4D is there, looked at once a second; never Cinema 4D's own class. A Blender started by the plugin does not inherit Cinema 4D's processor affinity (Cycles kept 30 cores busy with Cinema 4D limited to 8; a `subprocess.Popen` child does inherit it): whatever is set for Blender is set on its process.
- **Cores left free** (Preferences > IPR, "CPU Threads Left Free", page id 1011, key 1023): a CPU render in the IPR gets `render.threads_mode` FIXED and the logical processors less this many (`GetSystemInfo`, as Blender counts them). Changing the count recreates Cycles' session (`SessionParams::modified` compares `threads`), so it travels with the settings and is resent only when they or the preference change. Measured with the probe (Cycles on the CPU, 960 × 540, an object dragged with the event loop running, both processes below normal):

| Threads left free | Main thread busy | Wait p95 / max | Frames shown per s |
|---|---|---|---|
| 0 (before) | 94 % | 125 / 386 ms | 17 |
| 2 of 32 | 84 % | 24 / 116 ms | 34 |
| 4 of 32 | 65 % | 14 / 57 ms | 45 |
| 8 of 32 | 24 % | 3.5 / 13 ms | 48 |
| 2 of 8 (stand-in: both processes limited to 8 logical processors, frames unlimited) | 14 % (71 % with 0) | 1.8 / 4 ms | 48 |

  The default is therefore a quarter of the logical processors, at least 2 (`DefaultIprThreadsFree`). With 4 of 8 the stand-in measured worse than with 2 in one run (92 %, a 2.8 s wait), which was not repeated: the stand-in's numbers spread more than the full machine's.

## Frames the IPR shows

- **At most about 30 a second, the last one always** (0.2.0, B11). The window takes a frame from the frame thread at most every 1/30 s (`FrameWatcher::Take` with a minimum interval, in `IprDialog::ShowNewFrame`, which every path uses: the timer, the core message, the main-thread job in a modal loop, the scene hook, the navigation loop). A frame asked for sooner is held; the frame thread wakes when its time has come and announces it again with `SpecialEventAdd` and the arrival callback (`frame_due` in the trace), so the newest frame reaches the window also when nothing follows it. The test hook's windowless reading (`status`, `frame`) has no limit. The bridge publishes at most as often (Blender reference, "The viewport driver").
- **A frame equal to the one on screen is skipped**: the frame thread hashes each frame (size and every value, four 64-bit lanes, about 2 ms at 1920 × 1080 on that thread) and `ShowNewFrame` compares before converting (`same` in the trace). Cycles publishes many: 26 to 32 of 66 to 72 frames in a drag with the event loop running were equal to the one before (Eevee none).
- **Measured** [T: `tests/c4d/ipr_frames_window.py`, application 2027.0.0, Blender 5.2.3, 960 × 540 on the GPU, 2026-11-17, three runs]: in every second of an emulated tool drag, a pumped drag and an Attribute Manager drag of a light, at most 30 to 32 frames arrived and 17 to 28 were shown (Cycles 17 to 18, Eevee 28; before: 50 to 230 arrived and as many shown); after the render finished, the window's picture equalled the newest published frame pixel for pixel (Cycles and Eevee; its id one lower, because the last published frame was equal to the one on screen and skipped). Main thread and step times before and after: `internal/b11/measurements.md`, "After steps 1 and 2".
